## 1. 2.2.37.3 不是已经固定 tick 了吗？

**问：** 2.2.37.3 不是已经固定了 tick，为什么还会发生 45 / 24？

**答：** 2.2.37.3 只在部分情况下固定 tick。

```text
120 / 144 / 165 / 240 Hz → 59.94 Hz timer
60 Hz（包括 exclusive_60hz 切出来的 60 Hz）→ 跟 display / kernel vblank
```

所以：

```text
高刷：固定 tick
60 Hz：不固定，仍然跟屏幕
```

`exclusive_60hz = 1` 把显示切成 60 Hz 后，进入“60 Hz 跟屏幕”分支；kernel vblank 掉到 47，tick 也跟着掉到 47。

新加的“稳定游戏速度”开关做的是：

```text
timer_vblank = 1
→ 即使 display_near_60
→ 也强制 timer
```

**结论：** 不是 2.2.37.3 已经固定 tick 还出问题；它只在高刷固定，60 Hz 仍跟 display。

## 2. 为什么 30fps CG 会变成 24？

**问：** 为什么 30fps 的 CG 会降成 24？

**答：** 30fps CG 是每 2 个游戏 tick 推进一帧影片。

```text
tick 60 → 60 / 2 = 30fps
tick 47 → 47 / 2 = 23.5 ≈ 24fps
```

这不是 CG 解码成 24，而是**驱动 CG 的 tick 变成 47**。

日志：

```text
vblank: 2929 of the last 3600 from the display, 47.023 Hz
```

**结论：** 24 是 47 / 2 的结果。

## 3. kernel vblank 是什么？

**问：** kernel vblank 是什么？

**答：** 是 Windows 内核/显示驱动提供的垂直空白等待：

```text
D3DKMTWaitForVerticalBlankEvent
```

它不是 timer，也不是 `DwmFlush`。

```text
timer：QPC 自己数 59.94
DwmFlush：等桌面合成
kernel vblank：等显示器的垂直空白事件
```

在独占 60 Hz 时，2.2.37.3 走 kernel vblank；事件回来一次，游戏 tick 才前进一步。

问题在于：它是**事件驱动**，不是时间驱动。

```text
收到一次事件 → ++tick
事件漏掉 / 合并 / 晚回来 → 不会补 tick
```

## 4. 为什么“显示器 / Present 实际刷新”会变成 47？

**问：** 为什么显示器 / Present 实际刷新会在特定情况下变成 47，导致 vblank 变慢？

**答：** 更准确地说：**显示器不一定真的变成 47 Hz，而是 vblank 等待每秒只完成 47 次。**

面板很可能仍是 60 Hz。少掉的是事件。

可能原因（按目前证据排序）：

1. **事件合并 / 漏掉**  
   vblank 是同步事件，不是计数器。等待者处理前若又发生一次，可能只记得“有响过”，不会排队。

2. **30fps CG 呈现活动变少**  
   正常游戏每 tick 都 Present；CG 每 2 tick 才 Present。  
   如果 kernel vblank 与 flip / Present 管线的同步点有关，没有新 frame 的刷新就可能没有独立事件，或事件被延后。

3. **独占全屏的 flip queue**  
   D3D9Ex 独占 Present 进入 flip queue；队列空、back buffer 等待或只有 30fps 时，同步点可能晚到。

4. **模式切换后的状态不同步**  
   165 → 60、Alt+Tab 可能改变 display source、VidPn 模式、flip queue；旧等待可能到新模式才回来。

5. **线程调度**  
   vblank thread 即使 time-critical，如果正在处理上一个 tick 或被抢占，事件也可能在它处理前再次发生而合并。

**待验证：** 目前只有平均值，没有逐次 `kv.wait` 耗时，所以不能断定“就是 driver 合并”。

## 5. 没懂“被拖慢”的原理

**问：** 还是没懂它被拖慢的原理。

**答：** 核心差别是：

```text
timer：看 QPC 时间，时间到了就是到了
kernel vblank：门铃响一次，才走一步
```

timer 即使被晚唤醒，也会按绝对时间保持 cadence；  
kernel vblank 如果少收到事件，就直接少 tick，而且不会补。

```text
60 次事件 → 60 tick
47 次事件 → 47 tick
```

30fps CG 每 2 tick 一帧，于是 47 → 23.5 ≈ 24。

**结论：** 不是电脑性能不够，而是事件驱动的时间源漏了事件。

## 6. 为什么电脑性能不差，事件还是会慢？

**问：** 是什么导致事件慢？明明电脑性能不差。

**答：** 性能好只代表 CPU/GPU 算得快，不代表显示管线每个刷新都通知你。

这是时序 / 呈现管线问题，不是算力问题。

```text
CPU / GPU 快
≠ vblank 事件准时
```

事件少一次，tick 就少一次；timer 不会这样。

## 7. 为什么连续 Alt+Tab 几次又能好？

**问：** D3D 没有处理 occlusion / exclusive mode change，为什么连续切换几次又能好？

**答：** 因为这是 Windows / 驱动 / Present 的**隐式重新同步**，不是程序有恢复逻辑。

每次切换可能发生：

```text
失去前景 → OCCLUDED
Windows 恢复桌面模式
回到游戏 → 重新取得前景
D3D9Ex 重新 Present
swap chain 重新对上显示模式
kernel vblank 重新稳定
```

`OCCLUDED` 不是永久状态；下一次成功 Present 可能让它消失。  
模式也可能被 Windows/驱动重新套用。

但这不是保证：

```text
有时切几次就好
有时更糟
有时一直 47 / 57
```

因为程序没有明确的：

```text
WM_ACTIVATE → CheckDeviceState → ResetEx / 重套模式
```

**结论：** 能好是 incidental recovery，不是设计保证。

## 8. 焦点为什么不会恢复？

**问：** 焦点为什么不会恢复？

**答：** Windows 的“焦点”会恢复，D3D 的“呈现状态”不会自动恢复。

```text
Windows：窗口又在前景
D3D9Ex：可能仍然 OCCLUDED / MODE_CHANGED
```

目前程序在 `WM_ACTIVATE` 只处理鼠标捕获，没有：

```text
CheckDeviceState
ResetEx
重套 60 Hz
重新同步 vblank
```

所以：

```text
焦点：已恢复
D3D 状态：没人叫它恢复
```

**结论：** 不是焦点没恢复，是 D3D / swap chain / vblank 状态没跟着恢复。

## 9. 完全没处理 D3D 状态吗？

**问：** 我们完全没处理 D3D 状态吗？

**答：** 不是，只处理了一部分。

### 已处理

```text
DEVICELOST / DEVICEHUNG / DEVICEREMOVED / OUTOFVIDEOMEMORY → recover_device
窗口模式 MODE_CHANGED 连续 30 帧 → Reset
Alt+Enter / 解析度切换 → Reset
Alt+Tab 后不把 OCCLUDED / MODE_CHANGED 当 device lost（D3D9Ex）
最小化也 Present（避免命令积在 driver）
```

### 没处理

```text
独占全屏 MODE_CHANGED
OCCLUDED 的明确恢复
焦点回来后的 CheckDeviceState / ResetEx
重套 60 Hz
swap chain / back buffer 状态恢复
```

**结论：** 处理了“device lost”和“窗口模式模式变化”，没有处理“独占全屏被遮挡 / 模式变化后的恢复”。

## 10. 什么时候 Reset？

**问：** 什么时候 Reset？

**答：** 目前会在这些情况 Reset：

```text
用户 Alt+Enter / 切全屏 / 改解析度 / 改显示设置
DEVICELOST / HUNG / REMOVED / OUTOFVIDEOMEMORY
窗口模式 MODE_CHANGED 连续 30 帧
建立装置 / 套用显示模式（CreateDeviceEx / ResetEx）
```

目前**不会**因为：

```text
Alt+Tab
OCCLUDED
独占全屏 MODE_CHANGED
```

自动 Reset。

**结论：** 卡住时不会自己 Reset，除非手动切换或重开。

## 11. 只会造成模式切换“一段时间”的卡顿吗？

**问：** 只会造成模式切换一段时间内的卡顿吗？

**答：** 不是。

模式切换事件本身是短暂的：

```text
黑屏约 1.5 秒
Present 暂停
MODE_CHANGED / OCCLUDED
```

但它留下的错误状态可以持续：

```text
vblank 47 / 57
tick 47
CG 24
Present 一直 OCCLUDED
frame pacing 一直不对
```

直到下一次 Reset / 切换 / 重开。

**结论：** 事件短暂，状态可持续。

## 12. 好修吗？

**问：** 好修吗？

**答：** 基本恢复不难；修到稳定不乱 Reset 是中等难度。

现成零件：

```text
CheckDeviceState
request_device_reset
reset_device_here
exclusive_mode()
exclusive_params()
```

要补：

```text
WM_ACTIVATE / WM_ACTIVATEAPP
OCCLUDED 不立刻 Reset，等前景
独占 MODE_CHANGED debounce
WM_DISPLAYCHANGE → 重套 60 Hz
Reset 后同步 vblank
防 Reset 循环
```

真正难的是：

```text
Alt+Tab 一次 → 连续 Reset 三次
Reset 时又触发 WM_DISPLAYCHANGE
Reset 时窗口还没在前景 → 失败
```

**结论：** 焦點恢复约 100–200 行 + 测试；Present 阻塞另算。

## 13. 这是曲线救国还是架构重构？

**问：** 如果修，这算曲线救国，还是重构架构？

**答：** 都不是。

```text
timer 开关：止血 / 兼容开关（曲线救国）
```

## 14. 架构代码是不是很垃圾？另一个 AI 说状态切换把刷新率值带过来了

**问：** 架构代码是不是很垃圾，所以没办法直接看代码判断？另一个 AI 说可能是状态切换时刷新率的值带过来了。

**答：** 不是垃圾，但状态分散，静态阅读容易抓错因果。

状态散在：

```text
host.cpp：g_exclusive_now、g_dev_exclusive、g_pp、exclusive_mode、reset_device_here
device.cpp：near_60、display_near_60、display_sync、KernelVblank、D3DDevice_Swap、recover_device
window thread：WM_ACTIVATE、WM_SIZE、WM_DISPLAYCHANGE、Alt+Enter
```

三个线程：

```text
游戏线程
vblank 线程
窗口线程
```

另一个 AI 的说法有可能，最像：

```text
near_60 每 300 tick 才更新
g_pp / g_dev_exclusive / g_exclusive_now 短暂不一致
KernelVblank handle 在模式切换后是否仍对应正确 source
```

但它和现有 log 不完全吻合：

```text
如果只是刷新率值带错，tick 可能变成 165 / 120 / 60
但实际是 47 / 57
```

**判断：** 刷新率值带错是次要因素，不是主因；主因仍是 kernel vblank / Present 状态被拖慢。

## 15. 打开开关就正常，关掉马上复现，说明什么？

**问：** 打开固定帧率开关后就不会发生，要靠频繁切窗口恢复的问题也没了；关掉马上复现。

**答：** 这是因果级证据。

```text
开 timer → 正常
关 timer → 复现
```

如果只是刷新率变量带错，开 timer 也应该被那个错误值影响；但开 timer 就正常，说明问题在 tick 的来源，不在某个刷新率值。

**结论：**

```text
主因：游戏 tick 跟 display / kernel vblank 耦合
不是主因：刷新率值带错 / near_60 / g_pp
```

## 16. frame pacing、Present、tick、vblank 是什么？哪些要解耦？

**问：** frame pacing、Present、tick、vblank 都是什么？哪些要解耦？

**答：**

### tick

游戏逻辑心跳；原版 Xbox 每个 vblank 一次。

### vblank

垂直空白 / 节拍事件；PC 上可用 timer、DwmFlush、kernel vblank。

### Present

把画好的帧交给 Windows / 显示器；V-Sync 下可能等 vblank，会阻塞游戏线程。

### frame pacing

决定哪个刷新显示哪一帧，例如 120 Hz 重复两次、30fps 影片重复上一帧。  
它属于呈现层，不应改变游戏 tick。

### 要解耦的

```text
已解：tick ← 显示器（timer 开关）
未解：Present ← 游戏线程
未解：焦点 / Reset ← 游戏循环
未解：frame pacing ← tick
```

目标：

```text
tick 固定 59.94
Present 独立
frame pacing 由呈现层决定
焦点 / Reset 由呈现层处理
```

## 17. 其他未解耦是从始至终都存在吗？

**问：** 其他未解耦的从始至终都存在吗？

**答：** 要分清楚。

| 耦合 | 从什么时候开始 | 性质 |
|---|---|---|
| Present ↔ 游戏线程 | 原版游戏就是这样 | 原本设计 |
| frame pacing ↔ tick | 原版就是 vblank / Swap | 原本设计 |
| 焦点 / Reset ↔ 游戏循环 | 移植到 PC 后就有 | D3D 移植本质 |
| tick ↔ 显示器 | 2026-10-05 才改 | 上游后加 |
| 60 Hz 模式切换 | 2.2.34 才加 | 后来的功能 |

原版主机固定 60 Hz、没有 VRR、没有 Alt+Tab、没有显示模式切换，所以这些耦合没有暴露。

## 18. 60 Hz 关掉就等于没加吗？

**问：** `exclusive_60hz` 关掉就等于没加吗？

**答：** 对“切 60 Hz”这件事来说，是。

```text
exclusive_60hz = 0
→ exclusive_mode() 不再找 60 Hz 模式
→ 直接用桌面刷新率
```

行为等于 2.2.34 之前。

但它只是不切模式，不是把整个 D3D 显示层还原；V-Sync、低延迟、tick 来源仍照旧。

如果桌面本来就是 60 Hz，开或关没有差别。

## 19. 这个 60 Hz 是把什么改成 60 Hz？

**问：** 这个 60 Hz 是把什么改成 60 Hz？

**答：** 把**独占全屏的显示模式刷新率**改成 60 Hz。

```text
1920×1200 @ 165 Hz → 1920×1200 @ 60 Hz
```

改的是：

```text
D3DDISPLAYMODEEX.RefreshRate
D3DPRESENT_PARAMETERS.FullScreen_RefreshRateInHz
```

不是：

```text
解析度
游戏 tick
渲染帧率上限
```

目的是让 165 Hz 下 60fps 的 3/3/3/2 刷新变成每帧一次。

## 20. 开关的历史：哪个版本之前默认就是开的？

**问：** 这个新开关在哪个版本之前默认就是开的？是我们移植黑之章时关了吗？

**答：** 不是我们关的。

```text
2026-10-05 之前：black-pc 默认自由运行 59.94 Hz timer
2026-10-05 commit 16e9bc2：
  vblank 改成跟 display（DwmFlush）
  加 --timer-vblank 作为回退
```

commit 原因：

```text
timer 59.94 vs 螢幕 59.95
→ 漂移
→ 畫面偶爾晚一個刷新 / 跳帧
→ 100% 速度但看起來不順
```

所以：

```text
16e9bc2 之前：timer 是預設
16e9bc2 之後：跟 display 是預設
```

我们的 2.x 全部继承“跟 display”；`--timer-vblank` 一直存在，只是没有启动器开关。

2.2.34 又加 `exclusive_60hz`，让独占 60 Hz 走 kernel vblank，进一步强化了跟 display。

新开关等于恢复 2026-10-05 之前的 timer 预设。

## 21. 新开关会实时生效吗？关掉不开始游戏会怎样？

**问：** 新开关会实时生效吗？改完不开始游戏，下次打开按钮会怎样？

**答：**

- 切换开关会**立即写入** `black.ini` 的 `timer_vblank = 1/0`；
- 游戏只在启动时读取 `black.ini`，运行中不会实时切换；
- 关掉启动器、不开始游戏，也会保留选择；
- 下次打开启动器按钮显示新状态；
- 下次启动游戏生效。

它不像图形页其他开关那样进入 pending；它像 CPU 核心分配一样立即写。

## 23. 开关关掉后 tick 一定跟 vblank 吗？

**问：** 定死速度的开关关了，tick 就跟随 vblank 了对吧？

**答：** 只在 60 Hz 时跟随；高刷仍然用 timer。

```text
timer_vblank = 0
```

### 60 Hz / 独占 60 Hz

```text
tick 跟 vblank
```

- 独占 60：kernel vblank；
- 窗口 60：DwmFlush。

### 120 / 144 / 165 / 240 Hz

```text
tick 仍用 59.94 timer
```

因为 display 不是 59–61 Hz，2.2.37.3 本来就不跟 vblank。

### 120 Hz + exclusive_60hz = 1

```text
切成 60 Hz
→ tick 跟 kernel vblank
```

### 程序路径

```text
if (timer_vblank)
    timer
else if (near_60 && exclusive)
    kernel vblank
else if (near_60)
    DwmFlush
else
    timer
```

**结论：** 关掉开关只会在 60 Hz 时把 tick 交回 vblank；120/165/240 仍然用 timer。

## 24. DwmFlush 是什么？谁设计的？

**问：** DwmFlush 是什么？跟随它又是谁设计的？

**答：** `DwmFlush` 是 Microsoft Windows 的 API：

```text
DwmFlush()
→ 等 Windows 桌面合成器（DWM）合成下一次画面
→ 60 Hz 下约 16.7 ms 一次
```

它不是显示器的垂直空白，也不是 timer。

真正决定“让游戏 vblank 跟 DwmFlush”的是：

```text
black-pc 原作者 Spark198rus
commit 16e9bc2
2026-10-05
"Smooth 60 fps: vblank follows the display"
```

当时原因：

```text
timer 59.94 Hz
螢幕 59.95 Hz
→ 漂移
→ 畫面偶爾晚一個刷新 / 跳帧
→ 100% 速度但看起來不順
```

所以 60 Hz 視窗模式改成跟 DwmFlush。  
2.2.34 的獨佔 60 Hz → kernel vblank 則是我們這個移植後來加的。

```text
tick 來源固定 59.94
```

## 26. DwmFlush 適合什麼情況？

## 27. 若想让画面丝滑不跳帧，还要解决什么架构问题？

**问：** 若想让画面丝滑不跳帧，还要解决什么架构问题？

**答：** 固定时钟只保证游戏速度正确，不保证画面丝滑。

### 1. 把 Present 从游戏线程拆开

现在：

```text
游戏线程画完 → 自己 Present
```

Present 一卡，游戏线程就卡。

目标：

```text
游戏线程 → 最新帧 queue → Presenter thread → Present
```

第一优先。

### 2. 帧的交接与丢弃策略

```text
queue 深度 1 或 2
只保留最新完整帧
Presenter 落后 → 丢旧帧
Presenter 超前 → 等 / 重复上一帧
```

不能无限加深 queue，否则延迟越来越大。

### 3. Frame pacing

现在没有真正的 frame pacing：

```text
游戏 tick 固定 59.94
但「哪一帧在哪个刷新显示」没有独立控制
```

Presenter 要对每个刷新决定：

```text
有帧 → 显示最新
没帧 → 重复上一帧
两帧 → 丢旧的
```

### 4. 59.94 与 60 / 59.95 的漂移

```text
游戏 tick：59.94
屏幕：59.95 或 60.00
```

长期一定会漂。  
不能靠“每次刚好对上”，要有重复帧 / 丢帧规则，而且要在呈现层做，不能改游戏 tick。

### 5. 高刷 / VRR 的呈现方式

```text
120 / 180 / 240
→ 同一帧允许重复刷新
→ 不能让 tick 跟着变

VRR
→ 准备好就送
→ 不能假设 n×60
```

需要 Presenter 自己判断，不是 `exclusive_60hz` 切模式就能解决。

### 6. Swap chain / 显示模式

D3D9Ex 的限制：

```text
没有 DXGI ALLOW_TEARING
没有 waitable swap chain
Present / Reset 不能并发
```

Presenter 要自己选：

```text
视窗 / 无边框 → DwmFlush / FLIPEX
独占 → flip + vblank
VRR → 驱动决定
```

### 7. 不要让 D3D Reset / 焦点拖 Presenter

```text
Alt+Tab
模式切换
OCCLUDED
```

Presenter 要能：

```text
丢帧
暂停
重建
不影响游戏 tick
```

这和焦点状态机是同一层。

### 8. 消除长帧

就算 tick 固定，如果某一帧花 50 ms：

```text
→ Present 错过刷新
→ 重复 / 跳帧
```

所以要：

```text
shader 预编译
贴图预热
避免执行中大量上传
控制 render scale / MSAA
```

### 9. 输入延迟 vs 丝滑

```text
queue 越深 → 越平滑
但输入延迟越大
```

通常选：

```text
深度 1
丢旧帧
```

### 10. 不可能的保证

```text
59.94 游戏
60.00 屏幕
```

数学上不可能永远每帧刚好一次刷新。  
一定会有：

```text
偶尔重复
偶尔丢帧
```

目标是：

```text
不是「零重复」
而是「节奏稳定、没有突发长停顿」
```

### 优先顺序

```text
1. Presenter / Present 解耦
2. latest-frame queue
3. frame pacing
4. 焦点 / Reset 不拖 Presenter
5. shader / 资源预热
6. 高刷 / VRR 呈现策略
```

**结论：** 固定时钟只让游戏时间不乱；要丝滑，还要让 Present 不拖游戏、由 Presenter 按刷新节奏选帧 / 重复帧 / 丢帧，并且把长帧和 Reset 挡在呈现层。

## 28. 60 Hz 显示模式下开固定时钟反而不如关闭顺，165 Hz 却很好？

**问：** 把屏幕刷新率改成 60 Hz 后，打开固定帧率开关反而没有关闭流畅；165 Hz 下非常丝滑。

**答：** 因为 `timer_vblank` 只固定游戏时钟，没有固定 Present。

### 60 Hz 模式

```text
显示模式：60.00 Hz
timer_vblank = 1
→ tick：59.94 Hz
```

两者只差 0.06 Hz，但会慢慢漂：

```text
tick 59.94
螢幕 60.00
→ 相位逐渐错开
→ Present 偶尔晚一帧
→ 看得到轻微不順
```

关闭开关：

```text
tick 跟 display / DwmFlush
→ 和 60 Hz 刷新对齐
→ 每帧比较容易刚好一次
→ 更顺
```

### 165 Hz

```text
60fps 在 165 Hz
→ 每帧有 2.75 次刷新机会
→ 相位误差不容易看出
→ 固定 timer 更稳
```

### 实務建議

```text
60 Hz：没有速度问题 → 关掉
60 Hz：CG 变慢 / 速度不对 → 才打开
165 Hz / VRR：打开
```

## 29. 为什么关了开关后，窗口模式 60 Hz 也很顺？

**问：** 为什么关了开关后，在窗口模式下显示器 60 Hz 也非常丝滑？

**答：** 窗口 60 Hz 正是 `DwmFlush` 最適合的情況。

关闭开关后：

```text
60 Hz 窗口
→ display_near_60 = true
→ vblank_thread 跟 DwmFlush
```

`DwmFlush` 等的是：

```text
Windows 桌面合成器（DWM）下一次合成
```

而窗口画面本来就是 DWM 合成的：

```text
tick 跟着 DWM
Present 也交给 DWM
→ 同一條節拍
→ 每帧比较容易刚好显示一次
→ 很顺
```

打开开关后：

```text
tick：独立 59.94 timer
Present：还是 DWM
→ 59.94 vs 60.00 又开始漂
→ DWM 偶尔重复 / 晚一帧
```

### 为什么独佔 60 没窗口顺

```text
窗口：DWM 合成，DwmFlush
独佔：DWM 不参与，kernel vblank
```

DwmFlush 对窗口 60 Hz 很成熟；  
kernel vblank 在模式切换 / 30fps CG 下可能被拖慢。

## 30. 窗口模式下 Present 是不是不适合解耦？

**问：** 窗口模式下 Present 是不是又不能、也不适合解耦了？

**答：** 不是不适合，是呈现路径不同。

窗口现在：

```text
游戏线程 → Present → DWM 合成 → 显示
```

DWM 本身有 buffering / frame pacing，  
所以 60 Hz 窗口关闭开关已经很顺。

解耦后应变成：

```text
游戏线程 → 画到 offscreen → latest-frame queue

Presenter
→ 用 DwmFlush / DWM 节奏
→ Present
```

也就是：

```text
DwmFlush 从「游戏 tick」搬到「Presenter」
```

不是不能用，而是不该再驱动 tick。

窗口解耦的难點：

```text
D3D9Ex windowed swap chain 绑 window
Present 和 Draw 不能共用同一 device 并发
DWM 已经有 queue
```

所以不能只把 Present 丢到另一个线程，  
还是要 offscreen / 共享 surface / presenter device。

### 优先级

```text
60 Hz 窗口：DWM 已经很顺 → 不急
60 Hz 独佔：kernel vblank 不穩 → 需要修复
高刷 / VRR：需要 timer + Presenter
```

## 31. 是不是所有模式都不需要 Present 耦合？

**问：** 是不是所有模式都不需要 Present 耦合？

**答：** 概念上是：

> 所有模式都不应该让游戏 tick 依赖 Present。

但不是「不需要 Present」：

```text
tick 不应该等 Present
Present 卡住不应该改变游戏时间
```

### 60 Hz 窗口

```text
DWM 已有 buffering / pacing
→ Present 通常不会严重卡
→ 不急，但概念上一样要解耦
```

### 60 Hz 独佔

```text
kernel vblank / Present 可能被模式切换拖慢
→ 最需要解耦
```

### 高刷 / VRR

```text
刷新率不固定
→ tick 必须 timer
→ Present 由 Presenter pacing
→ 必须解耦
```

### 最小目标

```text
Present 卡 1 秒
→ 游戏 tick 仍然前进
→ 只是画面掉帧 / 重复
```

### 准确说法

```text
所有模式：不应该有「tick 依赖 Present」的耦合
60 Hz 窗口：DWM 让耦合不明显，但不代表不需要
60 Hz 独佔 / 高刷 / VRR：必须解
```

**结论：** 所有模式都不需要「Present 驱动 tick」；但所有模式仍然需要 Present，只是应该由呈现层负责，而不是拖住游戏时间。

## 32. 窗口模式运行中切换刷新率，为什么速度有时跟屏幕、有时不跟？

**问：** 窗口模式运行中切换屏幕刷新率，游戏速度有时变成屏幕刷新率，有时又不变；关掉固定时钟开关也一样。

**答：** 因为程序只在**启动时看一次**屏幕是不是 60 Hz。

### 通俗说法

```text
出门前看一次天气
决定今天带不带伞
```

之后天气变了，它不会重新看。

程序也是：

```text
启动时 60 Hz
→ 决定「跟桌面合成 DwmFlush」

启动时 100 / 165 Hz
→ 决定「用固定 timer」
```

启动之后，即使刷新率变了，这个决定不会更新。

### 60 → 100

```text
启动 60
→ 选择 DwmFlush
→ 后来切 100
→ 还是 DwmFlush
→ 跟着 100 Hz 合成
→ 游戏速度变 100
```

### 100 → 165

```text
启动 100
→ 选择 timer
→ 后来切 165
→ 还是 timer
→ 游戏速度仍 60
```

### 不是“不绝对”

```text
不是随机
是看你启动时是多少 Hz
```

### 程序原因

```cpp
DwmFlushFn flush = display_sync();  // 只在 vblank_thread 启动时调用一次
```

`flush` 为非 null 后，windowed 分支就一直用它：

```cpp
else if (flush && SUCCEEDED(flush()))
```

没有在切换刷新率后重新判断。

`near_60` 虽然每 300 tick 更新，  
但 windowed 分支没有用 `near_60` 去关掉 `flush`。

### 正确行为

```text
显示 59–61 Hz → 才用 DwmFlush
显示 >61 Hz      → 用 timer
切换刷新率 → 立即重新判断
```

### 修法

```text
1. 不要只在启动时决定 flush
2. 每个循环或 WM_DISPLAYCHANGE 重新检查 display_near_60()
3. 非 59–61 Hz → 改 timer
4. 从高刷切回 60 → 可重新启用 DwmFlush
```

### 和新开关的关系

```text
timer_vblank = 1
→ flush = nullptr
→ 一律 timer
→ 不会发生这个 bug
```

但这只是避开，不是修好原本的 `flush` 逻辑。

**结论：** 窗口模式切换刷新率后速度跟屏幕，是 `DwmFlush` 只在启动时决定一次；启动 60 再切 100 会跟 100，启动 100 再切 165 仍是 timer 60。这是真 bug，不是“不一定”。

## 33. 为什么从 60 启动、切到 165，速度却没有变？

**问：** 从 60 启动，切到 165，游戏速度没有变；但 60 → 100 时速度变成了 100。为什么？

**答：** 这修正了“切到高刷就一定跟高刷”的说法。

`DwmFlush` 跟的是 **DWM 合成节奏**，不是直接跟面板刷新率。

```text
面板切 165 Hz
≠ DWM 一定用 165 Hz 合成
≠ DwmFlush 一定 165 次/秒
```

### 程序还有一层判断

```cpp
if (flush && SUCCEEDED(flush())) {
    synced = now - last > period / 2;
}
if (!synced) {
    timer 59.94
}
```

所以：

```text
DwmFlush 回来太早
→ synced = false
→ fallback timer 60
```

### 60 → 100 变 100

```text
DWM 实际合成真的变成 100
→ DwmFlush 每 10 ms 回来
→ synced = true
→ tick 100
```

### 60 → 165 没变

可能是：

```text
DWM 仍用 60 Hz 合成
或 DwmFlush 回来太早
→ synced = false
→ fallback timer 60
```

### 原本的 bug 还在

```text
启动 60
→ flush 被设成 DwmFlush
→ 之后切 165
→ 没有重新判断 flush
```

但实际结果取决于 DWM：

```text
DWM 真的跑 165 → tick 165
DWM 还是 60 → tick 60
DwmFlush 太早 → timer 60
```

### 更准确的说法

```text
不是「速度一定变成屏幕刷新率」
是「速度可能跟着 DwmFlush 的实际节奏」
```

`DwmFlush` 的节奏和面板 Hz 不是同一个东西。

### 要确认只能量

```text
切换后实际显示模式
DwmFlush 每次耗时
synced 是 true 还是 false
tick 是 100 还是 60
```

没有这些，只能說「可能」。

**结论：** 60 → 100 变快，是 DWM 合成真的变 100；60 → 165 不变，可能是 DWM 仍用 60 或 DwmFlush 太早而 fallback timer。`DwmFlush` 跟的是 DWM，不是面板 Hz，所以不能直接推成「切 165 就会 165」。

## 34. 高刷下窗口和独占全屏一样顺吗？

**问：** 高刷的窗口和独占全屏一样顺吗？

**答：** 稳定状态下通常都顺，但不完全一样。

### 高刷窗口 / 无边框

```text
游戏 → Present → DWM 合成 → 显示
```

优点：

```text
DWM 有 buffering，late frame 比较容易吸收
不需要切显示模式
Alt+Tab 风险较低
不会 tearing
```

缺点：

```text
多一层合成，延迟通常高一点
DWM / overlay 可能影响 pacing
```

### 高刷独占全屏

```text
游戏 → Present → flip → 显示
```

优点：

```text
bypass DWM，延迟最低
没有桌面合成干扰
```

缺点：

```text
切模式 / Alt+Tab 有 Reset / 黑屏风险
exclusive_60hz 开著會切成 60，失去高刷
焦點 / OCCLUDED 目前處理不完整
GPU 重载时 late frame 更容易变成重复 / 跳帧
```

### 实际比较

```text
稳定、不切换：
  两者都顺
  独占延迟略低
  窗口缓冲略多

Alt+Tab / 切模式：
  窗口较安全
  独占风险较高
```

### 建议

```text
高刷窗口：优先，安全
高刷独占：要最低延迟才用，并且关 exclusive_60hz
```

**结论：** 高刷下两者稳定时都顺；独占延迟略低但切换风险高，窗口有 DWM 缓冲、较安全。真正要两者都完美，还是需要 Presenter 接管 pacing。

## 35. Presenter 接管 pacing 是什么意思？是解耦吗？

**问：** Presenter 接管 pacing 是什么意思？是解耦吗？

**答：** 是解耦的一部分，但不只是解耦。

### 三层

```text
1. tick 解耦
   遊戲時間固定 59.94
   不跟 display

2. Present 解耦
   遊戲執行緒不再自己 Present
   只提交帧
   Presenter 執行緒負責 Present

3. Presenter pacing
   Presenter 決定：
     哪一帧在哪个刷新显示
     没有新帧 → 重复上一帧
     落后 → 丢旧帧
     高刷 → 重复刷新
     VRR → 准备好就送
```

### 所以

```text
解耦：把 Present 从游戏线程拿走
Pacing：拿走之后，决定何时显示哪一帧
```

两者通常一起做，但不是同一件事。

### 为什么需要它

现在：

```text
tick 固定
但 Present 还在游戏线程
frame pacing 没有独立控制
```

所以 60 Hz 下 timer 59.94 和 display 60 还是会漂；  
Presenter 才能：

```text
用 59.94 的遊戲時間
搭配 60 Hz 的显示节奏
→ 该重复就重复
→ 该丢就丢
→ 不让游戏线程等
```

**结论：** 解耦是「不要让游戏线程自己做 Present」；pacing 是「Presenter 决定哪一帧什么时候显示」。Presenter 接管 pacing = 两者一起做。

## 36. ngbrecomp 最新代码解耦了什么？为什么它任何刷新都稳定 60？

**问：** 拉取 ngbrecomp 最新代码，分析它哪些解耦了，为什么它能做到任何刷新下都稳定 60、均匀丝滑？

**答：** 分析的最新代码：

```text
f218709fb5f7a268b8caff47e851939eb56d9a12
2026-11-20 16:59:22 +0000
README: 21:9 on phones, HUD Aspect Corrected's shape
```

### 解耦一：游戏 vblank ↔ 显示器

`xboxrecomp/src/nv2a_vk/host/nv2a_host.c`：

```text
vblank thread
→ 绝对时间 deadline
→ s_refresh_hz = 60.0
→ 每 1/60 秒 raise vblank interrupt
```

默认不跟显示器。

只有明确设：

```text
NGB_VBLANK_SYNC=1
```

且 V-Sync 开、屏幕 59–61 Hz，才改成跟显示器的 `IDXGIOutput_WaitForVBlank`。  
注释说这个模式在 PC 上反而让 stutter 立刻出现。

### 解耦二：Present ↔ 游戏线程

`xboxrecomp/src/nv2a_vk/host/present_sdl.c`：

```text
swapchain lives on the PFIFO thread
Mailbox presentation when the driver offers it
presenting never blocks the thread that executes the pushbuffer
```

也就是：

```text
游戏执行 pushbuffer
→ Present 只是交出去
→ swapchain 由 PFIFO thread 处理
→ 游戏线程不等 swapchain
```

### 解耦三：呈现模式 ↔ 游戏速度

`present_sdl.c` 选择：

```text
Mailbox
→ 不然 Immediate
→ 不然 FIFO
```

Mailbox 下：

```text
新画面来了就替换
旧画面可以丢
不阻塞送出的线程
```

所以高刷只是重复 / 丢帧，不改变游戏时间。

### 解耦四：Render thread ↔ Guest CPU

`src/d3d/gpu/threaded.cpp`：

```text
游戏线程把 draw / present 放进 queue
render thread 执行
frame_wait 只等上一个 render batch
```

不是等 swapchain。

### 可选：Frame interpolation

```text
120 Hz 显示器
→ 在 60 帧之间插画面
```

额外呈现功能，不改变游戏时钟。

### 为什么稳定

```text
1. 绝对 deadline，不累积漂移
2. Present 不驱动 tick
3. Mailbox 不反压游戏
4. Render thread 独立
5. 高刷只是重复刷新
```

### 但也不是魔法

```text
NGB_VBLANK_SYNC=1 会重新耦合
FIFO fallback 仍可能阻塞
GPU / render thread 太慢，frame_wait 还是可能拖
Mailbox 不保证零重复 / 零掉帧
```

## 37. 我们能照抄 ngbrecomp 吗？

**问：** 我们能照抄 ngbrecomp 吗？

**答：** 不能直接抄代码，但可以照架构自己做。

### 授权

```text
ngbrecomp 本体：GPL-3.0-or-later
xboxrecomp/：MIT
route B：GPL-2.0-or-later
```

直接把 GPL-3 的 `nv2a_host.c` / `threaded.cpp` 贴进来，  
整个专案就要按 GPL-3 处理，不能只写「参考」。

`xboxrecomp/` 虽然是 MIT，  
但它是 Vulkan + SDL，和 route B 的 D3D9Ex 不相容。

### 可以借镜的架构

```text
固定 60 Hz 绝对时钟
Present 不驱动 tick
Render / Present 在另一条线程
只保留最新帧
不让 swapchain 反压游戏
```

这些是想法，不是特定代码。

### 不能直接搬的原因

```text
ngbrecomp：静态重编译 + 自定义 Vulkan renderer
route B：原版 x86 + D3D8 HLE → D3D9Ex
```

D3D9Ex 没有：

```text
Vulkan Mailbox
waitable swapchain
```

而且游戏直接呼叫 D3D8 Swap，  
不能把 `present_sdl.c` 直接搬过来。

## 38. route B 理论上能做到和 ngbrecomp 完全等价吗？

**问：** route B 理论上能做到和 ngbrecomp 完全等价的效果吗？

**答：** 行为可以接近，所有可观测细节不能保证完全相同。

### 可以等价的

```text
遊戲速度固定 60
任何刷新率下不变速
Present 不拖游戏线程
只保留最新帧
重复 / 丢帧有规律
焦点 / Reset 不影响 tick
```

### 很难完全等价的

```text
Present 模式：Vulkan Mailbox vs D3D9Ex
延迟：可能多一次 offscreen copy
驱动 / DWM / 独占 flip 行为
D3D8 Swap 的 front / back buffer 语义
每一帧的 drop / repeat 图案
```

### 结论

```text
架构等价：可以
行为接近：可以
像素 / 延迟 / 驱动层完全等價：不行
```

## 39. ngbrecomp 能保证所有驱动 / 所有刷新都零重复吗？

**问：** ngbrecomp 能做到保证所有驱动 / 所有刷新都零重复吗？

**答：** 不能。

### 零重复在数学上就不成立

```text
60 Hz：每帧一次
120 Hz：每帧必须显示 2 次
240 Hz：每帧必须显示 4 次
165 Hz：每帧 2.75 次，一定有 3/3/3/2
```

120 / 240 的重複是必要的，不是 bug。

### 真正的目标

```text
重複是规律的
不要突然多一次
不要突然少一次
不要卡顿
```

### ngbrecomp 能保证

```text
游戏速度稳定 60
Present 不拖游戏线程
高刷下节奏稳定
```

不能保证：

```text
所有驱动
所有刷新率
零重複
零掉帧
```

它自己也有：

```text
Mailbox / Immediate / FIFO fallback
NGB_VBLANK_SYNC 可能反而 stutter
frame interpolation 可选
```

### 一句话

> **60fps 在 120/240 下本来就必须重複；ngbrecomp 保证的是「游戏速度稳、节奏稳、Present 不拖游戏」，不是「所有驱动、所有刷新率零重複」。**

## 40. 为什么 ngbrecomp 在 60 Hz 窗口 / 无边框下反而不如 route B 顺？

**问：** 为什么 ngbrecomp 在 60 Hz 窗口和无边框下没有 route B 丝滑？

**答：** 因为 60 Hz 窗口下，DWM 本身就是很好的 Presenter。

route B 关掉固定时钟后：

```text
tick 跟 DwmFlush
Present 交给 DWM
→ 同一条 60 Hz 合成节奏
```

ngbrecomp 预设：

```text
固定 60 Hz timer
+ 自己的 Presenter
+ Mailbox / Immediate
```

问题是：

```text
timer 59.94
DWM 60.00
→ 会漂
```

高刷还有多余刷新可以吸收；  
60 Hz 窗口没有，漂一次就重复或晚一帧。

它其实有：

```text
NGB_VBLANK_SYNC=1
```

可以改成跟显示器 vblank，  
但预设关闭，注释说 PC 上反而可能 stutter。

**结论：** 不是 ngbrecomp 差，是它的设计目标不同；60 Hz 窗口是 DWM 的强项。

**问：** ngbrecomp 的所有模式做法，我们都很难做到吗？

### 已经不难 / 已有

```text
固定 60 时钟
窗口 / 无边框 / 独占
基本 Present
```

### 中等

```text
焦点 / OCCLUDED / MODE_CHANGED 恢复
非阻塞 Present

```

### 难

```text
D3D8 Swap 语义
```

### 很难

```text
Vulkan Mailbox
所有刷新率完全等价
插帧
```

**结论：** 显示模式本身不难；难的是所有模式背后的 Present 所有权、pacing、Swap 语义和插帧。

## 42. stutter 是什么意思？

**问：** stutter 是什么意思？

**答：** 画面卡顿、一頓一頓，不一定 FPS 低。

```text
平均 60fps
但偶尔多停一次
或突然少显示一帧
→ 看起来就是 stutter
```

和 FPS 低的差别：

```text
FPS 低：整体都慢
stutter：平均正常，但节奏不匀
```

常见原因：

```text
frame pacing 不稳
重复 / 跳帧
vblank 漂移
Present 卡一下
shader 编译
```

## 43. 解耦 Present 会倒退吗？

**问：** 如果我们解耦了 Present，会倒退吗？

**答：** 解耦本身不一定，做错会。

60 Hz 窗口现在：

```text
tick 跟 DwmFlush
Present 交给 DWM
```

DWM 已经在做 pacing。

解耦后如果：

```text
多一次 copy
queue 太深
pacing 做错
同步没做好
```

就可能变差。

要避免倒退：

```text
60 Hz 窗口的 Presenter 也跟 DwmFlush
queue 深度 1
不要多余 copy
```

**结论：** 60 Hz 窗口是风险最高的一组；不是不能拆，是不能拆完丢掉 DWM 对齐。

## 44. Present 绑定游戏执行绪影响大吗？在 DWM 下呢？

**问：** Present 和执行绪绑定在一起，对游戏影响很大吗？在 DWM 下呢？

**答：** 看 Present 会不会阻塞。

绑定：

```text
游戏执行绪画完
→ 自己 Present
→ 卡住就下一帧也卡
```

### DWM 窗口

```text
Present 通常只是交给 DWM
→ 很快回来
```

影响通常较小。  
但 DWM 队列满、被遮挡、Alt+Tab 时仍可能卡。

### 独占全屏

```text
Present 等 vblank / flip
→ 游戏执行绪停住
```

影响大。

### 高刷 / VRR

```text
可能等 swapchain / 队列
```

影响中等。

**结论：** 60 Hz 窗口影响小，独占 / 高刷 / VRR 影响大；tick 固定也不能保护 Present 卡住。

## 45. 「交给 DWM」是什么意思？

**问：** 「Present 多半只是交给 DWM」是什么意思？

**答：** 窗口模式下，游戏不是直接画到屏幕。

```text
游戏画到 back buffer
→ Present
→ 把画面交给 DWM
→ DWM 合成多个窗口
→ 下一次刷新才显示
```

所以 Present 很多时候只是：

```text
「这張画好了，交给 Windows」
```

交出去就回来，  
不用等真的显示。

但 DWM 队列满 / 被遮挡时，还是会等。

---

## 46. 为什么独占全屏不用 DWM？

**问：** 为什么独占全屏不用 DWM？

**答：** 因为独占的意思就是绕过 DWM。

```text
窗口：游戏 → DWM → 屏幕
独占：游戏 → 直接 flip → 屏幕
```

DWM 不参与游戏画面合成，  
所以 `DwmFlush` 等的是桌面合成，  
不是游戏的 flip。

**结论：** 独占不是「不用」DWM，而是本质就是 bypass DWM；所以只能等 kernel vblank 或 timer。

---

## 47. 独占全屏用 vblank 合理吗？

**问：** 独占全屏用 vblank 是否合理？

**答：** 分用途。

### 用来同步画面：合理

```text
Present 等 vblank
→ 对齐刷新
→ 避免撕裂
```

### 用来驱动游戏 tick：不合理

```text
vblank 事件被合并 / 延后
→ tick 跟着掉
→ CG 24
```

正确分工：

```text
tick：固定 timer
画面：vblank / vsync
```

**结论：** vblank 适合管画面，不适合管游戏时间。

## 48. 那要怎么解决？只做第一步是否就和 DWM 一样？

**问：** 那要怎么解决？只做第一步，是不是 Present 对游戏的影响就和 DWM 一样了？

**答：** 不是。

### 短期

```text
60 Hz 窗口：保持 DWM
60 独占 / 高刷 / VRR：tick 用 timer
```

### 中期

```text
补焦点 / OCCLUDED / MODE_CHANGED 恢复
```

### 长期

```text
Presenter thread
latest-frame queue
frame pacing
```

只做第一步：

```text
tick 不跟 vblank 了
但 Present 还在游戏执行绪
```

独占下 Present 仍可能卡住游戏，  
不会变成跟 DWM 窗口一样。

**结论：** 第一步只解决「tick 跟 vblank」，没有解决「Present 卡住游戏执行绪」。

## 50. 60 Hz 独佔全屏：垂直同步开关分别会发生什么？

**问：** 60Hz 显示器、独佔全屏，垂直同步关掉后游戏内能稳 60，但画面撕裂；CG 仍然约 24。为什么？

**答：** 说明 Present 和 vblank 确实绑在一起。

### 垂直同步开

```text
Present 等 flip / vblank
→ kernel vblank 事件可能被 Present 节奏拖慢
→ vblank 50 左右
→ 游戏内跟着掉
```

### 垂直同步关

```text
Present 不再等 flip
→ 送得更连续
→ kernel vblank 能维持 60
→ 游戏内稳 60
```

代价：

```text
画面撕裂
```

### CG 仍然 24

关闭垂直同步救了游戏内，但没有救 CG。

可能原因：

```text
CG 有自己的影片时钟
CG 每 2 tick 才换一帧
Present 节奏仍然限制 CG
```

要分清：

```text
游戏内 60：tick + Present 都跟上了
CG 24：影片播放 / 呈现节奏仍然不对
```

**结论：** 垂直同步是影响 vblank 的一个点；关掉能换回游戏内 60，但会撕裂，而且 CG 不一定跟着好。

## 51. CG 是 30fps，Presenter 和 frame pacing 能同时解决 CG 和游戏吗？

**问：** CG 确实是 30，Presenter 和 frame pacing 能解决 CG 和游戏吗？

**答：** 能解决大部分，但要看 CG 变慢是不是 Present 造成的。

### 如果 CG 慢是 Present 造成

```text
游戏每 2 tick 交一帧 CG
Presenter 按显示节奏重复
60Hz：每帧显示 2 次
120Hz：每帧显示 4 次
→ CG 30
```

同时：

```text
游戏线程不等 Present
→ 游戏内 60
```

### 如果 CG 有自己的影片时钟

```text
影片时钟 / 音频时钟 / 解码器本身就是 24
→ Presenter 变不出 30
```

### 前提

```text
Presenter 能拿到每一帧 CG 和时间信息
游戏确实交了 30 帧
```

如果游戏只交 24 帧，Presenter 只能重复 24 帧，不能变成 30。

**结论：** Presenter + frame pacing 能解决「Present 拖慢 CG 和游戏」，也能同时做到不撕裂 + 游戏内 60；但如果 CG 有独立时钟问题，需要另外处理。

## 52. Presenter 和 frame pacing 好做吗？

**问：** Presenter 和 frame pacing 好做吗？

**答：** 不算好做，但也不是做不到。

### 基础 Presenter

```text
Present 移到另一条线程
latest-frame queue
```

难度：中等。  
能解决 Present 卡游戏线程。

### Frame pacing

```text
哪一帧在哪个刷新显示
没有新帧 → 重复上一帧
落后 → 丢旧帧
```

难度：难。  
要配合 V-Sync、DWM、独佔、VRR。

### D3D9Ex 的限制

```text
没有 Vulkan Mailbox
没有 waitable swapchain
Present 仍可能阻塞
```

不能照搬 ngbrecomp。

### route B 额外的麻烦

```text
D3D8 Swap 的 front / back buffer 语义
device 不能跨线程同时 Draw / Present
可能需要 offscreen / shared surface / copy
```

### 难度分级

```text
基础 Presenter：中等
完整 frame pacing：难
接近 ngbrecomp：很难
所有驱动完全等價：不现实
```

**结论：** 基础 Presenter 可以做；完整 frame pacing 很难；最现实是先修焦點 / Reset，再做非阻塞 Present，最后才做 Presenter。

## 54. 为什么只有主菜单和 CG 错误，游戏内却正常？

**问：** 为什么只有主菜单和 CG 错误，游戏内速度却正常？

**答：** 因为它们的呈现节奏不同。

游戏内：

```text
每个 tick 都 Present
→ 呈现持续
→ kernel vblank 比较容易被维持
→ tick / 速度正常
```

CG：

```text
每 2 个 tick 才 Present 一帧
→ 呈现活动减半
→ vblank 更容易被合并 / 延后
→ 30fps 掉成 24
```

主菜单：

```text
不是每个 tick 都严格 Present
或 UI 动画按呈现帧数走
→ 呈现节奏一乱就掉到 52 左右
```

所以不是菜单 / CG 的代码坏了，  
是它们对 vblank 变慢更敏感。

**结论：** 游戏内一直送画面，vblank 比较稳；CG 两拍才送一次，最容易掉；菜单介于两者之间。

## 55. 60 Hz 显示器下，CG 和主菜单比其他高刷更容易变速吗？

**问：** 60Hz 显示器下，CG 和主菜单和其他高刷比起来，更容易变速吗？

**答：** 要分窗口 / 独占。

```text
60 Hz 窗口
→ DwmFlush / DWM
→ 通常较稳

60 Hz 独占
→ kernel vblank
→ 最容易掉

高刷 + exclusive_60hz 关
→ timer
→ 速度稳

高刷 + exclusive_60hz 开
→ 切 60
→ 回到 kernel vblank
→ 和 60 Hz 独占一样有风险
```

CG / 菜单比游戏内敏感，  
因为 Present 次数少。

**结论：** 60Hz 独占最容易让 CG / 菜单变速；60Hz 窗口较稳；高刷只要不切 60，通常比 60Hz 独占稳。

## 59. 为什么当初这样设计？为什么这样更顺？


切成 60：

```text

→ 16.7ms 均匀
```

```text
tick、Present、刷新
三者同一条 60 Hz 节奏
→ 体感更顺
```

后来出问题，是因为 kernel vblank 在模式切换 / CG / Alt+Tab 下会掉到 47，  
不是当初目标错，是 tick 不该跟 vblank 一起被拖慢。

**结论：** 这次测试不能判断 2.2.37.3-t 的固定时钟；要装新版 / 跑新版 build 再测。

## 62. 为什么其他模式没问题，偏偏 kernel vblank 会被 Present 影响？

**问：** 为什么其他模式都没问题，就偏偏 vblank 受到了 Present 的影响？

**答：** 因为只有 kernel vblank 和 Present 走同一条硬件显示路径。

### 固定时钟

```text
自己看 QPC
→ 和 Present 无关
```

所以 Present 再卡，tick 也不受影响。

### 窗口 / DwmFlush

```text
Present 交给 DWM
→ DWM 自己合成 / 缓冲
→ DwmFlush 等的是 DWM
```

Present 晚一点，不一定拖慢 DwmFlush。

### 独占全屏 / kernel vblank

```text
绕过 DWM
→ Present 直接 flip
→ kernel vblank 等同一个显示器刷新
```

两者共用同一条显示路径：

```text
Present 卡 / Present 次数少
→ vblank 事件被合并 / 延后
→ tick 跟着掉
```

### 为什么 CG 更容易中招

```text
CG 30fps
→ 每 2 tick 才 Present 一次
→ Present 次数少
→ vblank 更容易断续
```

游戏内每个 tick 都 Present，  
反而能把这条路径撑住。

### 打比方

```text
timer：自己戴手表
窗口：柜台帮你排队
独占：你和 Present 共用一扇门
```

Present 卡在门口，vblank 也过不去。

**结论：** 不是 vblank 特别脆弱，是独占全屏下 kernel vblank 和 Present 共用了同一条显示路径；窗口有 DWM 缓冲，timer 根本不走这条路。

## 63. 从启动器设置看，哪些模式会走 kernel vblank？

**问：** 从启动器的启动设定来看，哪些场景 / 模式会走 vblank？

**答：** 看 fullscreen、桌面刷新率、exclusive_60hz、vsync、固定时钟。

### 会走 kernel vblank

```text
fullscreen = 2（真全屏）
桌面 59–61 Hz
timer_vblank = 0
```

即使 vsync 关掉，也可能走 kernel vblank，因为 vsync 不在条件里。

### 高刷要切 60 才走

```text
fullscreen = 2
桌面 120 / 144 / 165 / 240
exclusive_60hz = 1
vsync = 1
```

会先切成 60，等 near_60 更新后走 kernel vblank。

### 不会走 kernel vblank

```text
fullscreen = 0（窗口）
fullscreen = 1（无边框）
桌面高刷 + exclusive_60hz = 0
桌面高刷 + vsync = 0
timer_vblank = 1
```

窗口 / 无边框 60 Hz：

```text
走 DwmFlush
不是 kernel vblank
```

高刷窗口 / 无边框：

```text
走 timer
```

### 启动器判断表

| fullscreen | 桌面 | vsync | exclusive_60hz | 结果 |
|---|---|---|---|---|
| 2 | 60 | 开/关 | 任意 | kernel vblank |
| 2 | 高刷 | 开 | 开 | 切 60 后 kernel |
| 2 | 高刷 | 开 | 关 | timer |
| 2 | 高刷 | 关 | 任意 | timer |
| 0 / 1 | 60 | 任意 | 任意 | DwmFlush |
| 0 / 1 | 高刷 | 任意 | 任意 | timer |

固定时钟打开：

```text
全部 timer
```

还要注意：

```text
near_60 每 300 tick 才更新
→ 刚切模式可能延迟几秒
```

**结论：** 启动器設定裡真正決定 kernel vblank 的，是 fullscreen 是否為 2、桌面是否 59–61 Hz、以及 exclusive_60hz 有沒有把高刷切成 60。

## 64. 2.2.33 的 60Hz 独佔：低延迟为什么会让游戏变慢？

**问：** 2.2.33 在 60Hz 显示器、独佔全屏、垂直同步开、低延迟开时，游戏速度会变慢，CG 也慢；关掉低延迟后，游戏内和主菜单正常，CG 仍慢。为什么？

**答：** 2.2.33 的 60Hz 独佔还没有 kernel vblank，tick 来源是 DwmFlush。

但独佔全屏 + 垂直同步时，Present 本身要等 flip / 显示器的 vblank。

低延迟的代码顺序是：

```text
画完
→ 先 Present
→ Present 等 vblank / flip
→ 回来后才 pace
→ pace 又等 DwmFlush
```

等于等了两次。

关掉低延迟：

```text
画完
→ 先 pace / DwmFlush
→ 再 Present
```

只等一次，所以游戏内和主菜单恢复。

CG 仍慢，是因为 CG 每 2 tick 才换一帧，Present 次数少，还有自己的影片节奏；低延迟不是 CG 唯一原因。

**结论：** 2.2.33 的低延迟不是算得慢，是「先 Present 再 pace」在独佔 + 垂直同步下变成多等一次；关掉后少等一次，游戏速度恢复。

## 65. 不是说 DwmFlush 吗，怎么又扯到 vblank？

**问：** 不是说 2.2.33 走 DwmFlush 吗，怎么又扯到 vblank？

**答：** DwmFlush 是 tick 来源，Present 的 vsync 等待是另一件事。

```text
DwmFlush：决定 tick / 节拍
Present：把画面交给显示
```

2.2.33 的独佔 60：

```text
tick 来源：DwmFlush
Present：独佔 + 垂直同步
→ 仍要等 flip / 显示器的 vblank
```

低延迟先 Present：

```text
Present 等一次 vblank
→ pace 等一次 DwmFlush
```

窗口模式不同：

```text
Present 交给 DWM
→ 通常不等显示器 vblank
→ 主要是 pace 一次
```

**结论：** 2.2.33 的 tick 是 DwmFlush；但独佔的 Present 仍会等显示器的 vblank，两者不是同一个等待。

## 66. 窗口模式下低延迟要等几次？

**问：** 窗口模式下低延迟要等几次？

**答：** 正常情况主要等一次节拍。

普通模式：

```text
画完
→ pace / DwmFlush 一次
→ Present 交给 DWM
```

低延迟：

```text
画完
→ 先 Present 交给 DWM
→ 再 pace / DwmFlush 一次
```

通常还是一次节拍等待，因为窗口 Present 只是交给 DWM，不会像独佔那样先等 vblank。

例外：

```text
DWM 队列满
窗口被遮挡
Alt+Tab
overlay
```

这时 Present 可能额外卡住。

**结论：** 窗口 60 正常和低延迟通常都是一次节拍等待；独佔 + 垂直同步才容易变成两次。

## 69. 解耦 Present 一定要把 60Hz 窗口改成 timer 吗？

**问：** 解耦 Present 就一定要把 60Hz 窗口的 tick 改成 timer 吗？

**答：** 不一定。解耦 Present 和解耦 tick 是两件事。

### tick 来源

```text
固定 timer
或 DwmFlush / vblank
```

### Present 归属

```text
游戏执行绪自己 Present
或 Presenter 执行绪
```

### 可以保留 DWM 的组合

```text
60Hz 窗口
tick 跟 DwmFlush
Present 交给 Presenter
Presenter 也用 DwmFlush / DWM
```

这样游戏时间和画面都还是跟 DWM，  
只是 Present 不再卡在游戏执行绪。

### 什么时候才需要 timer

```text
高刷
VRR
60Hz 独佔
tick 跟 vblank 会掉速
```

### 结论

```text
60Hz 窗口：
  tick 可以继续跟 DwmFlush
  Present 可以解耦
  不强制变 timer

高刷 / 独佔：
  tick 用 timer
  Presenter 负责 Present / pacing
```

**结论：** 解耦 Present 不强制 60Hz 窗口的 tick 变 timer；两者可以独立选择。只有希望所有模式统一，或 tick 跟 vblank 会掉速时，才需要 timer。

## 70. 60Hz 独佔 + 固定速度 + 垂直同步，为什么比窗口顺？

**问：** 60Hz 独佔全屏下，固定游戏速度打开、垂直同步开，画面比窗口模式流畅。

**答：** 这个组合同时避开两个问题。

```text
tick：固定 59.94
→ 不跟 kernel vblank
→ 不会掉到 47
```

```text
Present：独佔直接 flip
→ 不经过 DWM
→ 没有桌面合成队列
→ 延迟更低
```

垂直同步开着：

```text
不撕裂
```

窗口模式：

```text
Present 经过 DWM
→ 多一层合成 / 缓冲
```

所以 60Hz 下，独佔 + 固定速度 + 垂直同步，  
可能比窗口 + 关固定速度更顺。

代价：

```text
切模式黑屏
Alt+Tab / 焦点风险
Present 仍可能卡
低延迟最好关闭
```

## 71. 高刷下打开 60Hz 开关 + 独佔，也能达到同样效果吗？

**问：** 是不是高刷下打开 exclusive_60hz、独佔全屏，也能达到 60Hz 独佔 + 固定速度的效果？

**答：** 如果固定游戏速度也开着，理论上可以，因为它们最后走同一条路。

```text
高刷
→ exclusive_60hz 切成 60
→ 固定速度开
→ tick 59.94
→ Present 独佔 60 + 垂直同步
```

结果：

```text
和 60Hz 独佔 + 固定速度开一样
```

但前提：

```text
固定游戏速度必须开
垂直同步开
显示器有 60Hz 模式
```

如果固定速度没开：

```text
切 60 后 tick 会跟 kernel vblank
→ 又回到 47 / 24
```

代价：

```text
高刷被切成 60
切模式黑屏
Alt+Tab 风险
```

所以：

```text
120 / 240：没必要
144 / 165：可以试，但会失去高刷
```

**结论：** 高刷 + exclusive_60hz + 固定速度 + 垂直同步，可以接近 60Hz 独佔 + 固定速度的效果；但必须同时开固定速度，否则又会走 kernel vblank。

## 72. 120Hz 真全屏为什么比窗口 / 无边框顺？不都是 tick 吗？

**问：** 120Hz 下，真全屏比窗口无边框流畅，不都是 tick 吗？

**答：** tick 一样，画面到屏幕的路径不一样。

真全屏：

```text
游戏 → 直接 flip → 显示器
```

窗口 / 无边框：

```text
游戏 → DWM 合成 → 显示器
```

两者 tick 都可以是固定 59.94，但窗口多一层 DWM 队列和缓冲，可能多一帧延迟、偶尔重复或晚一帧。真全屏 Present 路径短，延迟低，所以体感更顺。

120 能整除 60，两边理论节奏都是每帧 2 次刷新；差别在“送出时间”和 DWM 合成。

## 73. 真全屏的 DWM 和窗口的 DWM 有什么区别？

**问：** 真全屏不是也有 DWM 吗？

**答：** 不是两个 DWM，是 DWM 有没有参与游戏画面。

窗口 / 无边框：

```text
DWM 一定参与
游戏画面被合成进桌面
```

真全屏（独占）：

```text
游戏直接接管显示器
DWM 不参与游戏画面合成
```

DWM 进程可能还在，但游戏画面不经过它。所以真全屏下 `DwmFlush` 没有意义；窗口下 `DwmFlush` 等的就是 DWM 合成。

## 74. 没开垂直同步，为什么真全屏也不撕裂？

**问：** 没开垂直同步，为什么 120 / 165 真全屏完全看不到割裂？

**答：** 没开垂直同步不等于一定撕裂。

撕裂需要：

```text
Present 在显示器扫描中途换帧
且前后帧差异足够大
```

可能出现不撕裂的情况：

```text
驱动仍把 flip 排到刷新边界
Windows 全屏优化实际走了合成 / flip 路径
120 / 165 Hz 扫描很快，撕裂线很短
```

所以“没开垂直同步”只是有撕裂的可能，不是必然。快速平移镜头时仍可能偶尔看到。

## 75. 影响游戏速度的只有 vblank 组合吗？

**问：** 这么说来影响游戏速度的只有 vblank 的组合了？

**答：** 分两层。

tick 频率：

```text
由 vblank 来源决定
timer / DwmFlush / kernel vblank
```

游戏实际前进：

```text
还要看游戏线程有没有被 Present / Reset / GPU 长帧卡住
```

timer 可以保证 tick 继续发，但如果游戏线程卡在 Present，tick 来了也没人处理，游戏还是会慢。

所以：

```text
vblank 决定节拍
Present / 线程决定节拍有没有被执行
```

不是只有 vblank 会影响游戏速度。

## 76. 只有真全屏 60Hz 开关打开时才会减速吗？

**问：** 结合之前的总结，是不是只有真全屏 60Hz 开关打开的时候，游戏减速？

**答：** 不是只有开关打开时。

会因 vblank 减速：

```text
真全屏 60Hz，固定游戏速度关
高刷真全屏 + 60Hz 开关开，固定游戏速度关
```

前者不需要开 60Hz 开关，桌面本来就是 60，也会走 kernel vblank。

不会因 vblank 减速：

```text
固定游戏速度开
高刷不切 60
60Hz 窗口（DwmFlush）
```

仍可能因 Present / GPU 卡顿变慢：

```text
任何模式
```

所以准确说法是：

```text
tick 跟 kernel vblank，且 vblank 不稳 → 减速
60Hz 开关只是其中一种触发方式
```

## 77. kernel vblank 这条路径是不是有大问题？

**问：** 所以 kernel vblank 这条路径有大问题？

**答：** 作为“游戏时钟”有大问题；作为显示相位参考可以用。

问题：

```text
绑定显示器 / flip，不是独立时间
Present、垂直同步、30fps CG、Alt+Tab、模式切换都可能让事件晚到 / 合并 / 漏掉
游戏只认 vblank 次数，没有独立时间轴，不会补拍
near_60 每 300 tick 才更新
flush 启动时决定一次
```

结果：

```text
60Hz 独佔 / 切 60 后掉到 47
CG 30fps 变 24
```

正确方向：

```text
游戏 tick 永远用固定 timer
kernel vblank 只给 Present / frame pacing 用
事件晚到用时间补偿，不让游戏少走一拍
切模式重新初始化
```

**结论：** kernel vblank 不适合当唯一游戏节拍来源；不是要扔掉它，而是把“时间”和“显示”拆开。

## 78. 最终判断与待验证项

### 已证实

```text
2.2.37.3 在 60 Hz 跟 display / kernel vblank
165 → 60 后 kernel vblank 可掉到 47 / 57
30fps CG 变 24 = 47 / 2
timer_vblank = 1 → CG 30 / 游戏 60
关掉 timer → 问题复现
D3D9Ex 迁移解决的是 device lost / Reset / 最小化 Present 积压
不是刷新率值带错
```

### 待验证

```text
每次 kv.wait 实际等多久
47 是稳定值还是平均值（长停顿拉低）
Present / flip 与 vblank 事件的精确关系
near_60 / g_pp / g_dev_exclusive 在切换瞬间的值
```

### 建议顺序

```text
1. 量测 Present / vblank
2. 补焦點 / OCCLUDED / MODE_CHANGED 恢复

6. frame pacing
```

## 79. 2.3 的时钟怎么回应以上问题？

**问：** 2.3 换了新的帧节拍时钟（`frame_clock`，详见 `27_帧节拍时钟_2.3.md`），它和前面这些问答的结论是什么关系？

| 77 | kernel vblank 不能当游戏时钟，可以当显示相位参考 | tick 永远是计时器；显示器只提供“vblank 在哪”的时间戳，用来微调计时器，从不等待 |

### 改了前提的

2026-11-26 用户改了要求：“tick 可以在 60 左右，不一定 59.94”“不能等待 vblank”。2.3 因此把 tick 微调到屏幕的实际刷新率（每 k 次刷新一拍，k = 1、2、4…），速度偏差限制在 ±0.4%（用户的 60.008 Hz 面板是 +0.11%）。漂移从根上没有了，不需要呈现层再补：

```text

```

144 / 165 / 75 Hz 这类不是 60 整数倍的屏幕，仍然是固定 59.94（每帧停留次数本来就不可能相同），和 27 节第 5 条一致。

### 相位从哪里来（问答里没有的新发现）

- 扫描线（D3DKMTGetScanLine）线性时最准（3 µs），但用户的笔记本在一次独占切模式之后，计数器改数 1200 行源行号、跳到 1608，只有 0–15% 读数可用。
- DWM 的 qpcVBlank 是软件时间戳（中位偏差约 100 µs），94–98% 在 250 µs 内，**独占全屏下也照样更新**——这和 73 节“独占时 DwmFlush 没有意义”不矛盾：等 DwmFlush 没意义，但 DWM 记录的 vblank 时间戳仍是显示器的。
- GetPresentStats 在这台机器上一律失败；kernel vblank 事件只有 68–77% 可用。

所以两个来源各拟合一张网格，哪张稳定跟哪张，扫描线优先。

### 新踩到的两个坑

```text
Sleep(0) 自旋：TIME_CRITICAL 线程只让同级，饿死同核的 CG 解码线程（CG 帧停 3 次刷新）
→ 改用高精度可等待计时器

DWM 空闲：30fps CG 每隔一次刷新才来一帧，DWM 偶尔晚一拍
→ 窗口 / 无边框跟随时，独立线程循环 DwmFlush 让合成器保持工作
  （2.2 的 tick 本身就是 DwmFlush，所以以前没暴露）
```
