## 1. 2.2.37.3 不是已经固定 tick 了吗？

**问：** 2.2.37.3 不是已经固定了 tick，为什么还会发生 45 / 24？

**答：** 2.2.37.3 只在部分情况下固定 tick。

```text
120 / 144 / 165 / 240 Hz → 59.94 Hz timer
60 Hz（包括 exclusive_60hz 切出来的 60 Hz）→ 跟 display / kernel vblank
```

所以：

```text
高刷：固定 tick
60 Hz：不固定，仍然跟屏幕
```

`exclusive_60hz = 1` 把显示切成 60 Hz 后，进入“60 Hz 跟屏幕”分支；kernel vblank 掉到 47，tick 也跟着掉到 47。

新加的“稳定游戏速度”开关做的是：

```text
timer_vblank = 1
→ 即使 display_near_60
→ 也强制 timer
```

**结论：** 不是 2.2.37.3 已经固定 tick 还出问题；它只在高刷固定，60 Hz 仍跟 display。

## 2. 为什么 30fps CG 会变成 24？

**问：** 为什么 30fps 的 CG 会降成 24？

**答：** 30fps CG 是每 2 个游戏 tick 推进一帧影片。

```text
tick 60 → 60 / 2 = 30fps
tick 47 → 47 / 2 = 23.5 ≈ 24fps
```

这不是 CG 解码成 24，而是**驱动 CG 的 tick 变成 47**。

日志：

```text
vblank: 2929 of the last 3600 from the display, 47.023 Hz
```

**结论：** 24 是 47 / 2 的结果。

## 3. kernel vblank 是什么？

**问：** kernel vblank 是什么？

**答：** 是 Windows 内核/显示驱动提供的垂直空白等待：

```text
D3DKMTWaitForVerticalBlankEvent
```

它不是 timer，也不是 `DwmFlush`。

```text
timer：QPC 自己数 59.94
DwmFlush：等桌面合成
kernel vblank：等显示器的垂直空白事件
```

在独占 60 Hz 时，2.2.37.3 走 kernel vblank；事件回来一次，游戏 tick 才前进一步。

问题在于：它是**事件驱动**，不是时间驱动。

```text
收到一次事件 → ++tick
事件漏掉 / 合并 / 晚回来 → 不会补 tick
```

## 4. 为什么“显示器 / Present 实际刷新”会变成 47？

**问：** 为什么显示器 / Present 实际刷新会在特定情况下变成 47，导致 vblank 变慢？

**答：** 更准确地说：**显示器不一定真的变成 47 Hz，而是 vblank 等待每秒只完成 47 次。**

面板很可能仍是 60 Hz。少掉的是事件。

可能原因（按目前证据排序）：

1. **事件合并 / 漏掉**  
   vblank 是同步事件，不是计数器。等待者处理前若又发生一次，可能只记得“有响过”，不会排队。

2. **30fps CG 呈现活动变少**  
   正常游戏每 tick 都 Present；CG 每 2 tick 才 Present。  
   如果 kernel vblank 与 flip / Present 管线的同步点有关，没有新 frame 的刷新就可能没有独立事件，或事件被延后。

3. **独占全屏的 flip queue**  
   D3D9Ex 独占 Present 进入 flip queue；队列空、back buffer 等待或只有 30fps 时，同步点可能晚到。

4. **模式切换后的状态不同步**  
   165 → 60、Alt+Tab 可能改变 display source、VidPn 模式、flip queue；旧等待可能到新模式才回来。

5. **线程调度**  
   vblank thread 即使 time-critical，如果正在处理上一个 tick 或被抢占，事件也可能在它处理前再次发生而合并。

**待验证：** 目前只有平均值，没有逐次 `kv.wait` 耗时，所以不能断定“就是 driver 合并”。

## 5. 没懂“被拖慢”的原理

**问：** 还是没懂它被拖慢的原理。

**答：** 核心差别是：

```text
timer：看 QPC 时间，时间到了就是到了
kernel vblank：门铃响一次，才走一步
```

timer 即使被晚唤醒，也会按绝对时间保持 cadence；  
kernel vblank 如果少收到事件，就直接少 tick，而且不会补。

```text
60 次事件 → 60 tick
47 次事件 → 47 tick
```

30fps CG 每 2 tick 一帧，于是 47 → 23.5 ≈ 24。

**结论：** 不是电脑性能不够，而是事件驱动的时间源漏了事件。

## 6. 为什么电脑性能不差，事件还是会慢？

**问：** 是什么导致事件慢？明明电脑性能不差。

**答：** 性能好只代表 CPU/GPU 算得快，不代表显示管线每个刷新都通知你。

这是时序 / 呈现管线问题，不是算力问题。

```text
CPU / GPU 快
≠ vblank 事件准时
```

事件少一次，tick 就少一次；timer 不会这样。

## 7. 为什么连续 Alt+Tab 几次又能好？

**问：** D3D 没有处理 occlusion / exclusive mode change，为什么连续切换几次又能好？

**答：** 因为这是 Windows / 驱动 / Present 的**隐式重新同步**，不是程序有恢复逻辑。

每次切换可能发生：

```text
失去前景 → OCCLUDED
Windows 恢复桌面模式
回到游戏 → 重新取得前景
D3D9Ex 重新 Present
swap chain 重新对上显示模式
kernel vblank 重新稳定
```

`OCCLUDED` 不是永久状态；下一次成功 Present 可能让它消失。  
模式也可能被 Windows/驱动重新套用。

但这不是保证：

```text
有时切几次就好
有时更糟
有时一直 47 / 57
```

因为程序没有明确的：

```text
WM_ACTIVATE → CheckDeviceState → ResetEx / 重套模式
```

**结论：** 能好是 incidental recovery，不是设计保证。

## 8. 焦点为什么不会恢复？

**问：** 焦点为什么不会恢复？

**答：** Windows 的“焦点”会恢复，D3D 的“呈现状态”不会自动恢复。

```text
Windows：窗口又在前景
D3D9Ex：可能仍然 OCCLUDED / MODE_CHANGED
```

目前程序在 `WM_ACTIVATE` 只处理鼠标捕获，没有：

```text
CheckDeviceState
ResetEx
重套 60 Hz
重新同步 vblank
```

所以：

```text
焦点：已恢复
D3D 状态：没人叫它恢复
```

**结论：** 不是焦点没恢复，是 D3D / swap chain / vblank 状态没跟着恢复。

---

## 9. 完全没处理 D3D 状态吗？

**问：** 我们完全没处理 D3D 状态吗？

**答：** 不是，只处理了一部分。

### 已处理

```text
DEVICELOST / DEVICEHUNG / DEVICEREMOVED / OUTOFVIDEOMEMORY → recover_device
窗口模式 MODE_CHANGED 连续 30 帧 → Reset
Alt+Enter / 解析度切换 → Reset
Alt+Tab 后不把 OCCLUDED / MODE_CHANGED 当 device lost（D3D9Ex）
最小化也 Present（避免命令积在 driver）
```

### 没处理

```text
独占全屏 MODE_CHANGED
OCCLUDED 的明确恢复
焦点回来后的 CheckDeviceState / ResetEx
重套 60 Hz
swap chain / back buffer 状态恢复
```

**结论：** 处理了“device lost”和“窗口模式模式变化”，没有处理“独占全屏被遮挡 / 模式变化后的恢复”。

## 10. 什么时候 Reset？

**问：** 什么时候 Reset？

**答：** 目前会在这些情况 Reset：

```text
用户 Alt+Enter / 切全屏 / 改解析度 / 改显示设置
DEVICELOST / HUNG / REMOVED / OUTOFVIDEOMEMORY
窗口模式 MODE_CHANGED 连续 30 帧
建立装置 / 套用显示模式（CreateDeviceEx / ResetEx）
```

目前**不会**因为：

```text
Alt+Tab
OCCLUDED
独占全屏 MODE_CHANGED
```

自动 Reset。

**结论：** 卡住时不会自己 Reset，除非手动切换或重开。

## 11. 只会造成模式切换“一段时间”的卡顿吗？

**问：** 只会造成模式切换一段时间内的卡顿吗？

**答：** 不是。

模式切换事件本身是短暂的：

```text
黑屏约 1.5 秒
Present 暂停
MODE_CHANGED / OCCLUDED
```

但它留下的错误状态可以持续：

```text
vblank 47 / 57
tick 47
CG 24
Present 一直 OCCLUDED
frame pacing 一直不对
```

直到下一次 Reset / 切换 / 重开。

**结论：** 事件短暂，状态可持续。

## 12. 好修吗？

**问：** 好修吗？

**答：** 基本恢复不难；修到稳定不乱 Reset 是中等难度。

现成零件：

```text
CheckDeviceState
request_device_reset
reset_device_here
exclusive_mode()
exclusive_params()
```

要补：

```text
WM_ACTIVATE / WM_ACTIVATEAPP
OCCLUDED 不立刻 Reset，等前景
独占 MODE_CHANGED debounce
WM_DISPLAYCHANGE → 重套 60 Hz
Reset 后同步 vblank
防 Reset 循环
```

真正难的是：

```text
Alt+Tab 一次 → 连续 Reset 三次
Reset 时又触发 WM_DISPLAYCHANGE
Reset 时窗口还没在前景 → 失败
```

**结论：** 焦點恢复约 100–200 行 + 测试；Present 阻塞另算。

## 13. 这是曲线救国还是架构重构？

**问：** 如果修，这算曲线救国，还是重构架构？

**答：** 都不是。

```text
timer 开关：止血 / 兼容开关（曲线救国）
焦點 / OCCLUDED / MODE_CHANGED 恢复：正确性修复
```

焦點修复不是绕过问题，而是把原本就该处理的 D3D 状态补正确。

**结论：** 修现状 = 把现有架构做对；不是曲线救国，也不能取代 Presenter。

## 14. 架构代码是不是很垃圾？另一个 AI 说状态切换把刷新率值带过来了

**问：** 架构代码是不是很垃圾，所以没办法直接看代码判断？另一个 AI 说可能是状态切换时刷新率的值带过来了。

**答：** 不是垃圾，但状态分散，静态阅读容易抓错因果。

状态散在：

```text
host.cpp：g_exclusive_now、g_dev_exclusive、g_pp、exclusive_mode、reset_device_here
device.cpp：near_60、display_near_60、display_sync、KernelVblank、D3DDevice_Swap、recover_device
window thread：WM_ACTIVATE、WM_SIZE、WM_DISPLAYCHANGE、Alt+Enter
```

三个线程：

```text
游戏线程
vblank 线程
窗口线程
```

另一个 AI 的说法有可能，最像：

```text
near_60 每 300 tick 才更新
g_pp / g_dev_exclusive / g_exclusive_now 短暂不一致
KernelVblank handle 在模式切换后是否仍对应正确 source
```

但它和现有 log 不完全吻合：

```text
如果只是刷新率值带错，tick 可能变成 165 / 120 / 60
但实际是 47 / 57
```

**判断：** 刷新率值带错是次要因素，不是主因；主因仍是 kernel vblank / Present 状态被拖慢。

## 15. 打开开关就正常，关掉马上复现，说明什么？

**问：** 打开固定帧率开关后就不会发生，要靠频繁切窗口恢复的问题也没了；关掉马上复现。

**答：** 这是因果级证据。

```text
开 timer → 正常
关 timer → 复现
```

如果只是刷新率变量带错，开 timer 也应该被那个错误值影响；但开 timer 就正常，说明问题在 tick 的来源，不在某个刷新率值。

**结论：**

```text
主因：游戏 tick 跟 display / kernel vblank 耦合
不是主因：刷新率值带错 / near_60 / g_pp
```

## 16. frame pacing、Present、tick、vblank 是什么？哪些要解耦？

**问：** frame pacing、Present、tick、vblank 都是什么？哪些要解耦？

**答：**

### tick

游戏逻辑心跳；原版 Xbox 每个 vblank 一次。

### vblank

垂直空白 / 节拍事件；PC 上可用 timer、DwmFlush、kernel vblank。

### Present

把画好的帧交给 Windows / 显示器；V-Sync 下可能等 vblank，会阻塞游戏线程。

### frame pacing

决定哪个刷新显示哪一帧，例如 120 Hz 重复两次、30fps 影片重复上一帧。  
它属于呈现层，不应改变游戏 tick。

### 要解耦的

```text
已解：tick ← 显示器（timer 开关）
未解：Present ← 游戏线程
未解：焦点 / Reset ← 游戏循环
未解：frame pacing ← tick
```

目标：

```text
tick 固定 59.94
Present 独立
frame pacing 由呈现层决定
焦点 / Reset 由呈现层处理
```

## 17. 其他未解耦是从始至终都存在吗？

**问：** 其他未解耦的从始至终都存在吗？

**答：** 要分清楚。

| 耦合 | 从什么时候开始 | 性质 |
|---|---|---|
| Present ↔ 游戏线程 | 原版游戏就是这样 | 原本设计 |
| frame pacing ↔ tick | 原版就是 vblank / Swap | 原本设计 |
| 焦点 / Reset ↔ 游戏循环 | 移植到 PC 后就有 | D3D 移植本质 |
| tick ↔ 显示器 | 2026-10-05 才改 | 上游后加 |
| 60 Hz 模式切换 | 2.2.34 才加 | 后来的功能 |

原版主机固定 60 Hz、没有 VRR、没有 Alt+Tab、没有显示模式切换，所以这些耦合没有暴露。

## 18. 60 Hz 关掉就等于没加吗？

**问：** `exclusive_60hz` 关掉就等于没加吗？

**答：** 对“切 60 Hz”这件事来说，是。

```text
exclusive_60hz = 0
→ exclusive_mode() 不再找 60 Hz 模式
→ 直接用桌面刷新率
```

行为等于 2.2.34 之前。

但它只是不切模式，不是把整个 D3D 显示层还原；V-Sync、低延迟、tick 来源仍照旧。

如果桌面本来就是 60 Hz，开或关没有差别。

## 19. 这个 60 Hz 是把什么改成 60 Hz？

**问：** 这个 60 Hz 是把什么改成 60 Hz？

**答：** 把**独占全屏的显示模式刷新率**改成 60 Hz。

```text
1920×1200 @ 165 Hz → 1920×1200 @ 60 Hz
```

改的是：

```text
D3DDISPLAYMODEEX.RefreshRate
D3DPRESENT_PARAMETERS.FullScreen_RefreshRateInHz
```

不是：

```text
解析度
游戏 tick
渲染帧率上限
```

目的是让 165 Hz 下 60fps 的 3/3/3/2 刷新变成每帧一次。

## 20. 开关的历史：哪个版本之前默认就是开的？

**问：** 这个新开关在哪个版本之前默认就是开的？是我们移植黑之章时关了吗？

**答：** 不是我们关的。

```text
2026-10-05 之前：black-pc 默认自由运行 59.94 Hz timer
2026-10-05 commit 16e9bc2：
  vblank 改成跟 display（DwmFlush）
  加 --timer-vblank 作为回退
```

commit 原因：

```text
timer 59.94 vs 螢幕 59.95
→ 漂移
→ 畫面偶爾晚一個刷新 / 跳帧
→ 100% 速度但看起來不順
```

所以：

```text
16e9bc2 之前：timer 是預設
16e9bc2 之後：跟 display 是預設
```

我们的 2.x 全部继承“跟 display”；`--timer-vblank` 一直存在，只是没有启动器开关。

2.2.34 又加 `exclusive_60hz`，让独占 60 Hz 走 kernel vblank，进一步强化了跟 display。

新开关等于恢复 2026-10-05 之前的 timer 预设。

## 21. 新开关会实时生效吗？关掉不开始游戏会怎样？

**问：** 新开关会实时生效吗？改完不开始游戏，下次打开按钮会怎样？

**答：**

- 切换开关会**立即写入** `black.ini` 的 `timer_vblank = 1/0`；
- 游戏只在启动时读取 `black.ini`，运行中不会实时切换；
- 关掉启动器、不开始游戏，也会保留选择；
- 下次打开启动器按钮显示新状态；
- 下次启动游戏生效。

它不像图形页其他开关那样进入 pending；它像 CPU 核心分配一样立即写。

## 23. 开关关掉后 tick 一定跟 vblank 吗？

**问：** 定死速度的开关关了，tick 就跟随 vblank 了对吧？

**答：** 只在 60 Hz 时跟随；高刷仍然用 timer。

```text
timer_vblank = 0
```

### 60 Hz / 独占 60 Hz

```text
tick 跟 vblank
```

- 独占 60：kernel vblank；
- 窗口 60：DwmFlush。

### 120 / 144 / 165 / 240 Hz

```text
tick 仍用 59.94 timer
```

因为 display 不是 59–61 Hz，2.2.37.3 本来就不跟 vblank。

### 120 Hz + exclusive_60hz = 1

```text
切成 60 Hz
→ tick 跟 kernel vblank
```

### 程序路径

```text
if (timer_vblank)
    timer
else if (near_60 && exclusive)
    kernel vblank
else if (near_60)
    DwmFlush
else
    timer
```

**结论：** 关掉开关只会在 60 Hz 时把 tick 交回 vblank；120/165/240 仍然用 timer。

## 24. DwmFlush 是什么？谁设计的？

**问：** DwmFlush 是什么？跟随它又是谁设计的？

**答：** `DwmFlush` 是 Microsoft Windows 的 API：

```text
DwmFlush()
→ 等 Windows 桌面合成器（DWM）合成下一次画面
→ 60 Hz 下约 16.7 ms 一次
```

它不是显示器的垂直空白，也不是 timer。

真正决定“让游戏 vblank 跟 DwmFlush”的是：

```text
black-pc 原作者 Spark198rus
commit 16e9bc2
2026-10-05
"Smooth 60 fps: vblank follows the display"
```

当时原因：

```text
timer 59.94 Hz
螢幕 59.95 Hz
→ 漂移
→ 畫面偶爾晚一個刷新 / 跳帧
→ 100% 速度但看起來不順
```

所以 60 Hz 視窗模式改成跟 DwmFlush。  
2.2.34 的獨佔 60 Hz → kernel vblank 則是我們這個移植後來加的。

```text
→ flush = nullptr
```

```text
tick 來源固定 59.94
```

## 26. DwmFlush 適合什麼情況？

```text
視窗 / 無邊框
固定 60 Hz
沒有 VRR
遊戲 tick 尚未跟呈現解耦
```

目的：

```text
讓遊戲節拍對齊桌面合成
```

## 27. 若想让画面丝滑不跳帧，还要解决什么架构问题？

**问：** 若想让画面丝滑不跳帧，还要解决什么架构问题？

**答：** 固定时钟只保证游戏速度正确，不保证画面丝滑。

### 1. 把 Present 从游戏线程拆开

现在：

```text
游戏线程画完 → 自己 Present
```

Present 一卡，游戏线程就卡。

目标：

```text
游戏线程 → 最新帧 queue → Presenter thread → Present
```

第一优先。

### 2. 帧的交接与丢弃策略

```text
queue 深度 1 或 2
只保留最新完整帧
Presenter 落后 → 丢旧帧
Presenter 超前 → 等 / 重复上一帧
```

不能无限加深 queue，否则延迟越来越大。

### 3. Frame pacing

现在没有真正的 frame pacing：

```text
游戏 tick 固定 59.94
但「哪一帧在哪个刷新显示」没有独立控制
```

Presenter 要对每个刷新决定：

```text
有帧 → 显示最新
没帧 → 重复上一帧
两帧 → 丢旧的
```

### 4. 59.94 与 60 / 59.95 的漂移

```text
游戏 tick：59.94
屏幕：59.95 或 60.00
```

长期一定会漂。  
不能靠“每次刚好对上”，要有重复帧 / 丢帧规则，而且要在呈现层做，不能改游戏 tick。

### 5. 高刷 / VRR 的呈现方式

```text
120 / 180 / 240
→ 同一帧允许重复刷新
→ 不能让 tick 跟着变

VRR
→ 准备好就送
→ 不能假设 n×60
```

需要 Presenter 自己判断，不是 `exclusive_60hz` 切模式就能解决。

### 6. Swap chain / 显示模式

D3D9Ex 的限制：

```text
没有 DXGI ALLOW_TEARING
没有 waitable swap chain
Present / Reset 不能并发
```

Presenter 要自己选：

```text
视窗 / 无边框 → DwmFlush / FLIPEX
独占 → flip + vblank
VRR → 驱动决定
```

### 7. 不要让 D3D Reset / 焦点拖 Presenter

```text
Alt+Tab
模式切换
OCCLUDED
```

Presenter 要能：

```text
丢帧
暂停
重建
不影响游戏 tick
```

这和焦点状态机是同一层。

### 8. 消除长帧

就算 tick 固定，如果某一帧花 50 ms：

```text
→ Present 错过刷新
→ 重复 / 跳帧
```

所以要：

```text
shader 预编译
贴图预热
避免执行中大量上传
控制 render scale / MSAA
```

### 9. 输入延迟 vs 丝滑

```text
queue 越深 → 越平滑
但输入延迟越大
```

通常选：

```text
深度 1
丢旧帧
```

### 10. 不可能的保证

```text
59.94 游戏
60.00 屏幕
```

数学上不可能永远每帧刚好一次刷新。  
一定会有：

```text
偶尔重复
偶尔丢帧
```

目标是：

```text
不是「零重复」
而是「节奏稳定、没有突发长停顿」
```

### 优先顺序

```text
1. Presenter / Present 解耦
2. latest-frame queue
3. frame pacing
4. 焦点 / Reset 不拖 Presenter
5. shader / 资源预热
6. 高刷 / VRR 呈现策略
```

**结论：** 固定时钟只让游戏时间不乱；要丝滑，还要让 Present 不拖游戏、由 Presenter 按刷新节奏选帧 / 重复帧 / 丢帧，并且把长帧和 Reset 挡在呈现层。

## 28. 60 Hz 显示模式下开固定时钟反而不如关闭顺，165 Hz 却很好？

**问：** 把屏幕刷新率改成 60 Hz 后，打开固定帧率开关反而没有关闭流畅；165 Hz 下非常丝滑。

**答：** 因为 `timer_vblank` 只固定游戏时钟，没有固定 Present。

### 60 Hz 模式

```text
显示模式：60.00 Hz
timer_vblank = 1
→ tick：59.94 Hz
```

两者只差 0.06 Hz，但会慢慢漂：

```text
tick 59.94
螢幕 60.00
→ 相位逐渐错开
→ Present 偶尔晚一帧
→ 看得到轻微不順
```

关闭开关：

```text
tick 跟 display / DwmFlush
→ 和 60 Hz 刷新对齐
→ 每帧比较容易刚好一次
→ 更顺
```

### 165 Hz

```text
60fps 在 165 Hz
→ 每帧有 2.75 次刷新机会
→ 相位误差不容易看出
→ 固定 timer 更稳
```

### 实務建議

```text
60 Hz：没有速度问题 → 关掉
60 Hz：CG 变慢 / 速度不对 → 才打开
165 Hz / VRR：打开
```

## 29. 为什么关了开关后，窗口模式 60 Hz 也很顺？

**问：** 为什么关了开关后，在窗口模式下显示器 60 Hz 也非常丝滑？

**答：** 窗口 60 Hz 正是 `DwmFlush` 最適合的情況。

关闭开关后：

```text
60 Hz 窗口
→ display_near_60 = true
→ vblank_thread 跟 DwmFlush
```

`DwmFlush` 等的是：

```text
Windows 桌面合成器（DWM）下一次合成
```

而窗口画面本来就是 DWM 合成的：

```text
tick 跟着 DWM
Present 也交给 DWM
→ 同一條節拍
→ 每帧比较容易刚好显示一次
→ 很顺
```

打开开关后：

```text
tick：独立 59.94 timer
Present：还是 DWM
→ 59.94 vs 60.00 又开始漂
→ DWM 偶尔重复 / 晚一帧
```

### 为什么独佔 60 没窗口顺

```text
窗口：DWM 合成，DwmFlush
独佔：DWM 不参与，kernel vblank
```

DwmFlush 对窗口 60 Hz 很成熟；  
kernel vblank 在模式切换 / 30fps CG 下可能被拖慢。

## 30. 窗口模式下 Present 是不是不适合解耦？

**问：** 窗口模式下 Present 是不是又不能、也不适合解耦了？

**答：** 不是不适合，是呈现路径不同。

窗口现在：

```text
游戏线程 → Present → DWM 合成 → 显示
```

DWM 本身有 buffering / frame pacing，  
所以 60 Hz 窗口关闭开关已经很顺。

解耦后应变成：

```text
游戏线程 → 画到 offscreen → latest-frame queue

Presenter
→ 用 DwmFlush / DWM 节奏
→ Present
```

也就是：

```text
DwmFlush 从「游戏 tick」搬到「Presenter」
```

不是不能用，而是不该再驱动 tick。

窗口解耦的难點：

```text
D3D9Ex windowed swap chain 绑 window
Present 和 Draw 不能共用同一 device 并发
DWM 已经有 queue
```

所以不能只把 Present 丢到另一个线程，  
还是要 offscreen / 共享 surface / presenter device。

### 优先级

```text
60 Hz 窗口：DWM 已经很顺 → 不急
60 Hz 独佔：kernel vblank 不穩 → 需要修复
高刷 / VRR：需要 timer + Presenter
```

## 31. 是不是所有模式都不需要 Present 耦合？

**问：** 是不是所有模式都不需要 Present 耦合？

**答：** 概念上是：

> 所有模式都不应该让游戏 tick 依赖 Present。

但不是「不需要 Present」：

```text
tick 不应该等 Present
Present 卡住不应该改变游戏时间
```

### 60 Hz 窗口

```text
DWM 已有 buffering / pacing
→ Present 通常不会严重卡
→ 不急，但概念上一样要解耦
```

### 60 Hz 独佔

```text
kernel vblank / Present 可能被模式切换拖慢
→ 最需要解耦
```

### 高刷 / VRR

```text
刷新率不固定
→ tick 必须 timer
→ Present 由 Presenter pacing
→ 必须解耦
```

### 最小目标

```text
Present 卡 1 秒
→ 游戏 tick 仍然前进
→ 只是画面掉帧 / 重复
```

### 准确说法

```text
所有模式：不应该有「tick 依赖 Present」的耦合
60 Hz 窗口：DWM 让耦合不明显，但不代表不需要
60 Hz 独佔 / 高刷 / VRR：必须解
```

**结论：** 所有模式都不需要「Present 驱动 tick」；但所有模式仍然需要 Present，只是应该由呈现层负责，而不是拖住游戏时间。

## 32. 窗口模式运行中切换刷新率，为什么速度有时跟屏幕、有时不跟？

**问：** 窗口模式运行中切换屏幕刷新率，游戏速度有时变成屏幕刷新率，有时又不变；关掉固定时钟开关也一样。

**答：** 因为程序只在**启动时看一次**屏幕是不是 60 Hz。

### 通俗说法

```text
出门前看一次天气
决定今天带不带伞
```

之后天气变了，它不会重新看。

程序也是：

```text
启动时 60 Hz
→ 决定「跟桌面合成 DwmFlush」

启动时 100 / 165 Hz
→ 决定「用固定 timer」
```

启动之后，即使刷新率变了，这个决定不会更新。

### 60 → 100

```text
启动 60
→ 选择 DwmFlush
→ 后来切 100
→ 还是 DwmFlush
→ 跟着 100 Hz 合成
→ 游戏速度变 100
```

### 100 → 165

```text
启动 100
→ 选择 timer
→ 后来切 165
→ 还是 timer
→ 游戏速度仍 60
```

### 不是“不绝对”

```text
不是随机
是看你启动时是多少 Hz
```

### 程序原因

```cpp
DwmFlushFn flush = display_sync();  // 只在 vblank_thread 启动时调用一次
```

`flush` 为非 null 后，windowed 分支就一直用它：

```cpp
else if (flush && SUCCEEDED(flush()))
```

没有在切换刷新率后重新判断。

`near_60` 虽然每 300 tick 更新，  
但 windowed 分支没有用 `near_60` 去关掉 `flush`。

### 正确行为

```text
显示 59–61 Hz → 才用 DwmFlush
显示 >61 Hz      → 用 timer
切换刷新率 → 立即重新判断
```

### 修法

```text
1. 不要只在启动时决定 flush
2. 每个循环或 WM_DISPLAYCHANGE 重新检查 display_near_60()
3. 非 59–61 Hz → 改 timer
4. 从高刷切回 60 → 可重新启用 DwmFlush
```

### 和新开关的关系

```text
timer_vblank = 1
→ flush = nullptr
→ 一律 timer
→ 不会发生这个 bug
```

但这只是避开，不是修好原本的 `flush` 逻辑。

**结论：** 窗口模式切换刷新率后速度跟屏幕，是 `DwmFlush` 只在启动时决定一次；启动 60 再切 100 会跟 100，启动 100 再切 165 仍是 timer 60。这是真 bug，不是“不一定”。

## 33. 为什么从 60 启动、切到 165，速度却没有变？

**问：** 从 60 启动，切到 165，游戏速度没有变；但 60 → 100 时速度变成了 100。为什么？

**答：** 这修正了“切到高刷就一定跟高刷”的说法。

`DwmFlush` 跟的是 **DWM 合成节奏**，不是直接跟面板刷新率。

```text
面板切 165 Hz
≠ DWM 一定用 165 Hz 合成
≠ DwmFlush 一定 165 次/秒
```

### 程序还有一层判断

```cpp
if (flush && SUCCEEDED(flush())) {
    synced = now - last > period / 2;
}
if (!synced) {
    timer 59.94
}
```

所以：

```text
DwmFlush 回来太早
→ synced = false
→ fallback timer 60
```

### 60 → 100 变 100

```text
DWM 实际合成真的变成 100
→ DwmFlush 每 10 ms 回来
→ synced = true
→ tick 100
```

### 60 → 165 没变

可能是：

```text
DWM 仍用 60 Hz 合成
或 DwmFlush 回来太早
→ synced = false
→ fallback timer 60
```

### 原本的 bug 还在

```text
启动 60
→ flush 被设成 DwmFlush
→ 之后切 165
→ 没有重新判断 flush
```

但实际结果取决于 DWM：

```text
DWM 真的跑 165 → tick 165
DWM 还是 60 → tick 60
DwmFlush 太早 → timer 60
```

### 更准确的说法

```text
不是「速度一定变成屏幕刷新率」
是「速度可能跟着 DwmFlush 的实际节奏」
```

`DwmFlush` 的节奏和面板 Hz 不是同一个东西。

### 要确认只能量

```text
切换后实际显示模式
DwmFlush 每次耗时
synced 是 true 还是 false
tick 是 100 还是 60
```

没有这些，只能說「可能」。

**结论：** 60 → 100 变快，是 DWM 合成真的变 100；60 → 165 不变，可能是 DWM 仍用 60 或 DwmFlush 太早而 fallback timer。`DwmFlush` 跟的是 DWM，不是面板 Hz，所以不能直接推成「切 165 就会 165」。

## 34. 高刷下窗口和独占全屏一样顺吗？

**问：** 高刷的窗口和独占全屏一样顺吗？

**答：** 稳定状态下通常都顺，但不完全一样。

### 高刷窗口 / 无边框

```text
游戏 → Present → DWM 合成 → 显示
```

优点：

```text
DWM 有 buffering，late frame 比较容易吸收
不需要切显示模式
Alt+Tab 风险较低
不会 tearing
```

缺点：

```text
多一层合成，延迟通常高一点
DWM / overlay 可能影响 pacing
```

### 高刷独占全屏

```text
游戏 → Present → flip → 显示
```

优点：

```text
bypass DWM，延迟最低
没有桌面合成干扰
```

缺点：

```text
切模式 / Alt+Tab 有 Reset / 黑屏风险
exclusive_60hz 开著會切成 60，失去高刷
焦點 / OCCLUDED 目前處理不完整
GPU 重载时 late frame 更容易变成重复 / 跳帧
```

### 实际比较

```text
稳定、不切换：
  两者都顺
  独占延迟略低
  窗口缓冲略多

Alt+Tab / 切模式：
  窗口较安全
  独占风险较高
```

### 建议

```text
高刷窗口：优先，安全
高刷独占：要最低延迟才用，并且关 exclusive_60hz
```

**结论：** 高刷下两者稳定时都顺；独占延迟略低但切换风险高，窗口有 DWM 缓冲、较安全。真正要两者都完美，还是需要 Presenter 接管 pacing。

## 35. Presenter 接管 pacing 是什么意思？是解耦吗？

**问：** Presenter 接管 pacing 是什么意思？是解耦吗？

**答：** 是解耦的一部分，但不只是解耦。

### 三层

```text
1. tick 解耦
   遊戲時間固定 59.94
   不跟 display

2. Present 解耦
   遊戲執行緒不再自己 Present
   只提交帧
   Presenter 執行緒負責 Present

3. Presenter pacing
   Presenter 決定：
     哪一帧在哪个刷新显示
     没有新帧 → 重复上一帧
     落后 → 丢旧帧
     高刷 → 重复刷新
     VRR → 准备好就送
```

### 所以

```text
解耦：把 Present 从游戏线程拿走
Pacing：拿走之后，决定何时显示哪一帧
```

两者通常一起做，但不是同一件事。

### 为什么需要它

现在：

```text
tick 固定
但 Present 还在游戏线程
frame pacing 没有独立控制
```

所以 60 Hz 下 timer 59.94 和 display 60 还是会漂；  
Presenter 才能：

```text
用 59.94 的遊戲時間
搭配 60 Hz 的显示节奏
→ 该重复就重复
→ 该丢就丢
→ 不让游戏线程等
```

**结论：** 解耦是「不要让游戏线程自己做 Present」；pacing 是「Presenter 决定哪一帧什么时候显示」。Presenter 接管 pacing = 两者一起做。

## 36. ngbrecomp 最新代码解耦了什么？为什么它任何刷新都稳定 60？

**问：** 拉取 ngbrecomp 最新代码，分析它哪些解耦了，为什么它能做到任何刷新下都稳定 60、均匀丝滑？

**答：** 分析的最新代码：

```text
f218709fb5f7a268b8caff47e851939eb56d9a12
2026-11-20 16:59:22 +0000
README: 21:9 on phones, HUD Aspect Corrected's shape
```

### 解耦一：游戏 vblank ↔ 显示器

`xboxrecomp/src/nv2a_vk/host/nv2a_host.c`：

```text
vblank thread
→ 绝对时间 deadline
→ s_refresh_hz = 60.0
→ 每 1/60 秒 raise vblank interrupt
```

默认不跟显示器。

只有明确设：

```text
NGB_VBLANK_SYNC=1
```

且 V-Sync 开、屏幕 59–61 Hz，才改成跟显示器的 `IDXGIOutput_WaitForVBlank`。  
注释说这个模式在 PC 上反而让 stutter 立刻出现。

### 解耦二：Present ↔ 游戏线程

`xboxrecomp/src/nv2a_vk/host/present_sdl.c`：

```text
swapchain lives on the PFIFO thread
Mailbox presentation when the driver offers it
presenting never blocks the thread that executes the pushbuffer
```

也就是：

```text
游戏执行 pushbuffer
→ Present 只是交出去
→ swapchain 由 PFIFO thread 处理
→ 游戏线程不等 swapchain
```

### 解耦三：呈现模式 ↔ 游戏速度

`present_sdl.c` 选择：

```text
Mailbox
→ 不然 Immediate
→ 不然 FIFO
```

Mailbox 下：

```text
新画面来了就替换
旧画面可以丢
不阻塞送出的线程
```

所以高刷只是重复 / 丢帧，不改变游戏时间。

### 解耦四：Render thread ↔ Guest CPU

`src/d3d/gpu/threaded.cpp`：

```text
游戏线程把 draw / present 放进 queue
render thread 执行
frame_wait 只等上一个 render batch
```

不是等 swapchain。

### 可选：Frame interpolation

```text
120 Hz 显示器
→ 在 60 帧之间插画面
```

额外呈现功能，不改变游戏时钟。

### 为什么稳定

```text
1. 绝对 deadline，不累积漂移
2. Present 不驱动 tick
3. Mailbox 不反压游戏
4. Render thread 独立
5. 高刷只是重复刷新
```

### 但也不是魔法

```text
NGB_VBLANK_SYNC=1 会重新耦合
FIFO fallback 仍可能阻塞
GPU / render thread 太慢，frame_wait 还是可能拖
Mailbox 不保证零重复 / 零掉帧
```

## 37. 我们能照抄 ngbrecomp 吗？

**问：** 我们能照抄 ngbrecomp 吗？

**答：** 不能直接抄代码，但可以照架构自己做。

### 授权

```text
ngbrecomp 本体：GPL-3.0-or-later
xboxrecomp/：MIT
route B：GPL-2.0-or-later
```

直接把 GPL-3 的 `nv2a_host.c` / `threaded.cpp` 贴进来，  
整个专案就要按 GPL-3 处理，不能只写「参考」。

`xboxrecomp/` 虽然是 MIT，  
但它是 Vulkan + SDL，和 route B 的 D3D9Ex 不相容。

### 可以借镜的架构

```text
固定 60 Hz 绝对时钟
Present 不驱动 tick
Render / Present 在另一条线程
只保留最新帧
不让 swapchain 反压游戏
```

这些是想法，不是特定代码。

### 不能直接搬的原因

```text
ngbrecomp：静态重编译 + 自定义 Vulkan renderer
route B：原版 x86 + D3D8 HLE → D3D9Ex
```

D3D9Ex 没有：

```text
Vulkan Mailbox
waitable swapchain
```

而且游戏直接呼叫 D3D8 Swap，  
不能把 `present_sdl.c` 直接搬过来。

## 38. route B 理论上能做到和 ngbrecomp 完全等价吗？

**问：** route B 理论上能做到和 ngbrecomp 完全等价的效果吗？

**答：** 行为可以接近，所有可观测细节不能保证完全相同。

### 可以等价的

```text
遊戲速度固定 60
任何刷新率下不变速
Present 不拖游戏线程
只保留最新帧
重复 / 丢帧有规律
焦点 / Reset 不影响 tick
```

### 很难完全等价的

```text
Present 模式：Vulkan Mailbox vs D3D9Ex
延迟：可能多一次 offscreen copy
驱动 / DWM / 独占 flip 行为
D3D8 Swap 的 front / back buffer 语义
每一帧的 drop / repeat 图案
```

### 结论

```text
架构等价：可以
行为接近：可以
像素 / 延迟 / 驱动层完全等價：不行
```

## 39. ngbrecomp 能保证所有驱动 / 所有刷新都零重复吗？

**问：** ngbrecomp 能做到保证所有驱动 / 所有刷新都零重复吗？

**答：** 不能。

### 零重复在数学上就不成立

```text
60 Hz：每帧一次
120 Hz：每帧必须显示 2 次
240 Hz：每帧必须显示 4 次
165 Hz：每帧 2.75 次，一定有 3/3/3/2
```

120 / 240 的重複是必要的，不是 bug。

### 真正的目标

```text
重複是规律的
不要突然多一次
不要突然少一次
不要卡顿
```

### ngbrecomp 能保证

```text
游戏速度稳定 60
Present 不拖游戏线程
高刷下节奏稳定
```

不能保证：

```text
所有驱动
所有刷新率
零重複
零掉帧
```

它自己也有：

```text
Mailbox / Immediate / FIFO fallback
NGB_VBLANK_SYNC 可能反而 stutter
frame interpolation 可选
```

### 一句话

> **60fps 在 120/240 下本来就必须重複；ngbrecomp 保证的是「游戏速度稳、节奏稳、Present 不拖游戏」，不是「所有驱动、所有刷新率零重複」。**

## 40. 最终判断与待验证项

### 已证实

```text
2.2.37.3 在 60 Hz 跟 display / kernel vblank
165 → 60 后 kernel vblank 可掉到 47 / 57
30fps CG 变 24 = 47 / 2
timer_vblank = 1 → CG 30 / 游戏 60
关掉 timer → 问题复现
D3D9Ex 迁移解决的是 device lost / Reset / 最小化 Present 积压
不是刷新率值带错
```

### 待验证

```text
每次 kv.wait 实际等多久
47 是稳定值还是平均值（长停顿拉低）
Present / flip 与 vblank 事件的精确关系
near_60 / g_pp / g_dev_exclusive 在切换瞬间的值
```

### 建议顺序

```text
1. 量测 Present / vblank
2. 补焦點 / OCCLUDED / MODE_CHANGED 恢复
3. 固定游戏时钟成为正式路径
4. 非阻塞 Present
5. Presenter thread
6. frame pacing
```

### 一句话

> **问题不是电脑慢，也不是刷新率值带错；是游戏 tick 跟 display / kernel vblank 耦合，30fps CG 的呈现节奏让事件变少或延后，tick 从 60 掉到 47，CG 就从 30 变 24。timer 开关切断了这条耦合，所以一开就正常，一关就复现。**
