# 《忍者龙剑传 黑之章》PC 移植：呈现节拍目标架构设计

**版本：** 设计草案 v0.1  
**日期：** 2026-11-18  
**关联报告：** `NGB_呈现节拍架构问题报告.md`  
**范围：** 游戏 vblank、呈现、VRR/高刷；不改变游戏逻辑本身

---

## 1. 设计目标

### 1.1 必须满足

1. 游戏逻辑速度与原版一致：每秒 59.94 次 vblank，不受显示设备影响；
2. VRR / 120 / 180 / 240 Hz 下不得出现 80 帧、4/3 速、24 帧等速度错误；
3. 60 Hz、独占全屏、窗口、无边框行为可控；
4. 30 fps 过场影片节奏正确；
5. 音效、输入、存档、联网不因新架构改变；
6. 出现呈现异常时可以降级，不崩溃。

### 1.2 不作为目标

- 不把游戏逻辑改成多线程；
- 不改写原版 x86 游戏代码；
- 不要求 VRR 下一定达到 120/240 帧；
- 不追求零重复帧、零跳帧；优先保证游戏速度正确；
- 不在本设计内实现完整帧生成/插帧。

---

## 2. 核心原则

> **游戏 tick 只有一个时钟：固定 59.94 Hz 的 QPC 计时器。  
> 显示设备只决定“画面什么时候送出去”，绝不决定“游戏跑多快”。**

```text
游戏时钟：固定 59.94 Hz
呈现时钟：vsync / VRR / 合成，独立
```

禁止：

- 用 `DwmFlush` 的次数决定游戏 tick；
- 用 120/180/240 的 n 次刷新决定游戏 tick；
- 用 VRR 当前刷新率决定游戏 tick；
- 让 `Present` 阻塞游戏 tick。

---

## 3. 当前架构与问题

### 3.1 当前

```text
DwmFlush / D3DKMT vblank
        ↓
vblank_thread
        ↓
Xbox vblank event / callback
        ↓
游戏逻辑 + D3DDevice_Swap / Present
```

同一个节拍同时驱动：

- 游戏逻辑；
- 画面呈现。

### 3.2 问题

- VRR 改变合成节拍 → 游戏速度改变；
- 高刷 n×60 假设只在固定刷新成立；
- 2.2.35 的 80 Hz 是直接结果；
- 2.2.37.1 / 2.2.37.2-t 的 fallback 只能事后补救。

---

## 4. 目标架构

### 4.1 总览

```text
                 ┌──────────────────────────┐
                 │  Game clock thread       │
                 │  QPC, 59.94 Hz           │
                 │  never reads display     │
                 └────────────┬─────────────┘
                              │ vblank event/callback
                              ▼
                 ┌──────────────────────────┐
                 │  Game thread (original)  │
                 │  input / audio / logic   │
                 │  D3D8 HLE → D3D9         │
                 │  submit frame, no wait   │
                 └────────────┬─────────────┘
                              │ latest-frame queue (depth 1)
                              ▼
                 ┌──────────────────────────┐
                 │  Presenter thread        │
                 │  D3D9Ex swap chain       │
                 │  vsync / VRR / flip      │
                 │  drop stale frames       │
                 └────────────┬─────────────┘
                              ▼
                          Display
```

### 4.2 职责

#### Game clock thread

- 只做计时；
- 用 QPC 绝对时间表；
- 每 16.683 ms 触发一次 vblank；
- 通知 `DEV_VBLANKEVENT` 和 `SetVerticalBlankCallback`；
- 不调用 `DwmFlush`；
- 不读取 `EnumDisplaySettings` 的刷新率作为节拍；
- 不因 Present 阻塞。

#### Game thread

- 继续执行原版 x86 游戏代码；
- 每个 vblank 执行一次逻辑；
- 输入在 tick 前采样；
- 渲染到 D3D9 目标；
- `D3DDevice_Swap` 只提交当前帧，不等待显示；
- 不因为呈现落后而改变逻辑 tick 数。

#### Presenter thread

- 只负责把最新完整帧送给显示；
- 选择呈现模式：
  - 60 Hz 固定：vsync / 窗口合成；
  - 120/180/240 固定：按显示刷新呈现，不反写游戏 tick；
  - VRR：帧准备好就送，由驱动调刷新；
- 丢旧帧，不阻塞游戏；
- 记录 present 统计、丢帧数、呈现延迟；
- 可以接受重复帧/跳帧，但不允许影响游戏速度。

## 5. 时钟设计

### 5.1 游戏时钟

```text
period = 1001 / 60000 秒 = 16.683 ms
next = start + n * period
```

实现要求：

- 使用 `QueryPerformanceCounter`；
- 绝对 deadline，不用 `sleep(period)` 累加；
- 每次 tick 唤醒游戏；
- 如果醒晚了，不要用显示时间补偿；
- 不把“实际经过时间”写回游戏逻辑；
- 不做多 tick 追赶，除非原版游戏明确需要。

### 5.2 呈现时钟

呈现层可以使用：

- `DwmFlush`；
- `D3DKMTWaitForVerticalBlankEvent`；
- flip model 的 Present Statistics；
- VRR 驱动的实际刷新。

但这些只能影响：

- 何时 Present；
- 是否丢帧；
- 是否重复上一帧。

**不能影响游戏 tick。**

### 5.3 30 fps 影片

- 游戏仍然每 2 个 tick 推进一帧影片；
- Presenter 在两次影片帧之间可以重复显示上一帧；
- 不可以通过改变游戏 tick 来“凑”影片节奏。

---

## 6. 帧交接设计

### 6.1 最小方案：非阻塞 Present

第一阶段不引入新线程，只做：

1. 游戏 tick 固定 timer；
2. `D3DDevice_Swap` 用非阻塞 Present：
   - `D3DPRESENT_DONOTWAIT`；
   - flip model（`D3DSWAPEFFECT_FLIPEX`）；
   - 失败时保留当前帧，不阻塞游戏；
3. 显示节奏只在 Presenter 侧等待；
4. 测量 Present 是否仍阻塞。

优点：

- 改动小；
- 不改 D3D 设备线程模型；
- 先验证“游戏速度是否与显示解耦”。

缺点：

- `Present` 即使 DONOTWAIT 也可能在驱动内部等待；
- 设备线程仍是游戏线程；
- 如果 Present 阻塞，游戏 tick 仍会被拖慢。

### 6.2 完整方案：Presenter 线程

如果 6.1 仍阻塞，使用：

```text
Game thread 渲染到 back buffer A
        ↓
完成标记 / event
        ↓
Presenter 取最新完整帧
        ↓
Present
```

要求：

- 帧队列深度 1（只保留最新）；
- 游戏线程不等待 Presenter；
- Presenter 落后时丢旧帧；
- 设备调用串行化，避免 D3D9Ex 多线程竞态；
- 优先使用共享 surface / 双 back buffer，避免每帧全屏复制；
- 如果必须复制，先测 1080p/4K 成本。

### 6.3 D3D9Ex 注意事项

- 现有设备已使用 `D3DCREATE_MULTITHREADED`；
- flip model 使用 `D3DSWAPEFFECT_FLIPEX`；
- 窗口和独占的参数不同，Presenter 需要感知 Reset；
- 设备丢失/Reset 时，Presenter 与游戏线程必须同步暂停；
- 不要在两个线程同时调用同一个 D3D 设备的绘制方法；
- Present 与 Reset 不能并发。

## 7. 呈现模式

### 7.1 60 Hz 固定

- 游戏 tick：59.94 timer；
- Present：可以跟 vsync；
- 如果 Present 阻塞，丢帧或非阻塞；
- 不再用 `DwmFlush` 驱动游戏 tick。

### 7.2 120 / 180 / 240 Hz 固定

- 游戏 tick：59.94 timer；
- Present：每帧最多显示一次，允许显示 n 次刷新；
- 不做“每 n 次刷新走一帧”的游戏 tick；
- 高刷均匀度由 Presenter 的 frame pacing 处理，失败只影响画面。

### 7.3 VRR

- 游戏 tick：59.94 timer；
- Present：帧准备好就送；
- 不读取 VRR 刷新率作为游戏时钟；
- 允许 tearing / flip / 驱动 VRR；
- 不做 n×60 假设。

### 7.4 独占全屏

- 游戏 tick：仍固定 timer；
- 显示模式可由 `exclusive_60hz` 选择；
- kernel vblank 只能用于呈现，不得驱动游戏 tick；
- Alt+Tab / Reset 后重新建立呈现，不改变游戏时钟。

---

## 8. 失败与降级

### 8.1 呈现失败

- Present 失败：保留最后一帧，记录；
- 设备丢失：暂停呈现，游戏继续按 tick 运行或安全暂停；
- 队列满：丢最旧帧；
- 不把失败反馈成“游戏加速/减速”。

### 8.2 时钟异常

- 游戏时钟线程被系统卡住：记录，不切换到显示时钟；
- 恢复后按绝对时间继续，不补 tick；
- 不允许用显示刷新率修正游戏时钟。

### 8.3 兼容开关

保留：

- `--timer-vblank`：强制游戏时钟 timer（新架构下是默认，保留用于对照）；
- `--display-vblank`：测试用，允许呈现跟显示；
- 高低帧率 fallback：仅用于旧路径/呈现，不参与新游戏时钟。

---

## 9. 迁移步骤

### 阶段 0：观测

- 日志记录 tick 来源、tick 频率、Present 时间、丢帧；
- 用游戏内计时/固定动画验证游戏速度，不用 FPS 计数器；
- 建立 60/120/240/VRR 基线。

### 阶段 1：固定游戏时钟

- vblank_thread 只做 timer；
- 禁用 `DwmFlush` / kernel vblank 对游戏 tick 的影响；
- 保留 Present 现状；
- 验证游戏速度。

### 阶段 2：非阻塞 Present

- `Present` 加 `DONOTWAIT` / flip；
- 失败时丢帧；
- 验证游戏 tick 不被 Present 拖慢。

### 阶段 3：Presenter 线程

- 引入 latest-frame 队列；
- 游戏线程只提交；
- Presenter 负责显示；
- 验证 30 fps 影片、输入延迟、设备 Reset。

### 阶段 4：高刷呈现优化

- Presenter 内做 frame pacing；
- 不改游戏 tick；
- 恢复 120/180/240 均匀度。

| 场景 | 检查 |

| 60 Hz 窗口 | 游戏速度 60，画面稳定 |
| 60 Hz 独占 | 游戏速度 60，vblank 不依赖显示 |
| 120 Hz 窗口 | 游戏速度 60，不出现 80 |
| 120 Hz 独占 | 游戏速度 60 |
| 240 Hz 窗口 | 游戏速度 60，不出现 24/80 |
| VRR 120 窗口 | 游戏速度 60，不出现 80 |
| VRR 120 无边框 | 同上 |
| VRR 240 | 游戏速度 60，不出现 24 |

| 设备 Reset / Alt+Tab | 游戏时钟不跳变 |

## 11. 风险

1. D3D9Ex Present 的实际阻塞行为因驱动而异；
2. Presenter 线程与设备 Reset 的同步复杂；
3. 全屏复制成本可能高于预期；
4. 30 fps 影片在 60 tick 下的重复帧策略需验证；
5. 没有 120/240/VRR 实机；
6. Linux/Proton 的 D3D9Ex/flip 行为不同；
7. 高刷均匀度可能暂时退步；
8. 旧存档/联网不受影响，但需要回归。

---

## 12. 验收标准

- 任何显示模式下游戏速度 59.94 ± 0.1；
- 无 80 / 4/3 速、无 24/40 帧速度错误；
- 30 fps 影片正确；
- 输入、音频、存档无回归；
- 设备 Reset、Alt+Tab、睡眠恢复不改变游戏速度；
- 日志能区分游戏 tick 与呈现 tick。

---

## 13. 设计结论

> **游戏逻辑只认固定 59.94 Hz timer；显示设备只认呈现。  
> 允许画面丢帧、重复帧，不允许游戏速度改变。**

这是本项目的目标架构，也是与主流游戏一致的做法。

## 14. 低延迟呈现（low_latency_present）的去向

### 14.1 现在为什么在 120 Hz 视窗下不生效

2.2.37.2 后：

```text
120/180/240/VRR → 固定 59.94 Hz timer
→ g_vblank_synced = false
→ EarlyGate 认为没有可靠的屏幕相位
→ 视窗模式不提前 Present
```

所以：

```text
low_latency_present = 1
```

在 120 Hz 视窗/无边框下可能没有效果。  
这不是游戏速度问题；只是可选的输入延迟优化暂时失效。

默认：

```text
low_latency_present = 0
```

一般玩家不受影响。

### 14.2 目标：让 Presenter 自己掌握屏幕相位

未来把呈现拆到 Presenter 后：

```text
Game thread：固定 timer 驱动，只提交完整帧
        ↓
Presenter：知道当前屏幕相位 / Present Statistics
        ↓
如果帧在截止时间内准备好 → 提前 Present
否则 → 等下一次合成
```

关键变化：

- `g_vblank_synced` 不再参与游戏 tick；
- Presenter 自己维护 `present_synced` / `present_deadline`；
- `low_latency_present` 只控制 Presenter 的提前呈现策略；
- 游戏 tick 永远固定 59.94 Hz，不受 Presenter 影响。

### 14.3 不同显示模式下的策略

| 模式 | Presenter 行为 |
|---|---|
| 60 Hz 固定 | 学 Present Statistics 的 deadline，在截止前提前 Present |
| 120/180/240 固定 | 用屏幕刷新与 present stats 做提前呈现；游戏 tick 不变 |
| VRR | 帧准备好就 Present；VRR 自己调刷新，不需要“提前” |
| 独占全屏 | 可用显示器 vblank / flip stats；游戏 tick 仍固定 |
| 拿不到 stats | 用保守的固定 deadline，或关闭提前呈现 |

### 14.4 迁移要求

1. 先把游戏 tick 固定 timer（2.2.37.2 已做到高刷部分）；
2. 再把 Present 改为非阻塞；
3. Presenter 线程接管 `low_latency_present`；
4. 游戏线程不再读取 `g_vblank_synced`；
5. 低延迟开关不再影响游戏速度；
6. 保留关闭开关，允许回到普通 Present。

### 14.5 验收

- `low_latency_present = 1` 在 60/120/240 窗口下有可测的延迟改善；
- 开关打开/关闭，游戏速度都不变；
- 关闭时行为与普通 Present 一致；
- 拿不到 Present Statistics 时不崩溃、不阻塞游戏；
- VRR 下不出现 80 / 4/3 速。

### 14.6 短期处理

在 Presenter 架构完成前：

- 默认 `low_latency_present = 0`；
- 文档说明 120 Hz 视窗下该开关可能无效；
- 不为了让它生效而把显示节拍重新接回游戏 tick。

### 14.7 版本对比：为什么 2.2.34 能提前，2.2.37.2 不能

| 版本 | 游戏 tick | 提前 Present | 结果 |
|---|---|---|---|
| 2.2.34，120 Hz | 59.94 timer | 无条件，只看开关 | 能提前；但可能错过合成截止 |
| 2.2.35，120 Hz | n 次刷新的屏幕节拍 | 需要 `g_vblank_synced` + EarlyGate | 能提前；但 VRR 下游戏速度会错 |
| 2.2.37.2，120 Hz | 59.94 timer | 需要 `g_vblank_synced`，timer 下为 false | 速度正确；视窗下不能提前 |

关键结论：

> 2.2.34 不是“架构更正确”，而是它的提前 Present 没有判断自己是否赶得上合成。  
> 2.2.35 加了判断，却把游戏 tick 和屏幕节拍绑在一起。  
> 2.2.37.2 解开了游戏 tick，但没有把“呈现相位”单独提供给 Presenter。

所以不能直接把 2.2.34 的无条件提前搬回来：

- 那样会让低延迟重新生效；
- 但会重新引入“提前了却错过合成”的卡顿，尤其在 60 Hz / 内显。

正确做法仍然是：

```text
游戏 tick：固定 59.94 timer
呈现相位：Presenter 自己取得
提前 Present：Presenter 在截止时间内决定
```

这样 2.2.34 的“能提前”和 2.2.35 的“知道会不会赶上”才能同时存在。
