## 6a. 震动读错了位置（2026-10-23 修）

用户：「进入游戏后按 y 蓄力释放超杀之前，手柄都是一直震动的，但是移植版消失了……听玩家反馈说还有很多震动缺失」。

- **原因：** 加载器把 `XINPUT_FEEDBACK` 的头当成 68 字节（4 字节对齐），从 +68、+70 读左右马达。实际头是紧凑的 66 字节，
  马达在 +66（左，大马达）、+68（右，小马达）。所以以前传给 PC 的「左马达」其实是游戏的右马达，「右马达」读的是结构后面的 0；
  **游戏的左马达值从来没传出去**。
- **证据（静态）：** XAPI 的 `XInputSetState`（x2.1 0x3DBBDE）把 HID 报告号和长度写在 +0x40、+0x41，马达紧跟其后作为报告内容；
  游戏每帧发送震动的函数 0x30DE40 里，结构在 `esi-0x4D`，马达写在 `esi-0xB`、`esi-9`，即 +0x42、+0x44。
- **证据（实测，第一章读档后按住 Y）：** r464 / r465 日志（加载器新记录前 40 次马达变化）：
  - 蓄力：右马达 3277 → 52428 逐步加大，然后在 52428 / 51773 之间来回（一直震），左马达 0。
  - 放出超杀：左右都 65535；随后一下左 49151、右 0。
  - r465 同时记了旧位置读到的值：蓄力时旧代码把右马达值当左马达发，右马达一直是 0；放超杀时旧代码发「左 65535、右 0」，
    后面那下「左 49151」变成全 0。也就是只用左马达的震动以前全部丢了。
- 修好后左右马达与 xemu 一致（左 = 低频大马达，右 = 高频小马达）。蓄力震动在右边的小马达上，手感比旧版（错发到大马达）轻，这才是原机的样子。
- 性能：只改了读的位置；马达值变化的频率和以前一样，宿主调用次数不变。

## 6b. XInput 以外的手柄：SDL3（2026-10-23）

用户要求支持 DS1–DS5、Joy-Con 等常见手柄。此前只读 XInput（`xinput1_4.dll`），PS / Switch 手柄要靠 DS4Windows、Steam 输入。
做法（用户同意引入 SDL3 并下载其源码）：

- SDL3 3.4.18（2026-10-02 发布，源码包 SHA256 `9c75cf16330322c217dedd2e0609f1124f1b54b8633e763467b4684d0f4334a3`），只编
  手柄相关部分（关音频 / 视频 / 渲染 / GPU 等子系统），静态链接进 `blackrt.dll`（3.5 → 6.0 MB），新增依赖只有系统自带的
  OLEAUT32、SETUPAPI。`loader/CMakeLists.txt` 用 FetchContent 按 URL + SHA256 取源码，`-DNGB_SDL3_DIR` 用本地副本。
- `input/sdlpad.cpp`：独立线程（亲和性避开游戏所在的核，与混音线程相同），有手柄时每 2 ms、没有时每 50 ms 轮询一次；
  每 0.5 s 扫描插拔。关掉 SDL 的事件（`SDL_SetJoystickEventsEnabled(false)` 等），只轮询。游戏线程每帧只在锁内复制一份
  合并后的状态（`read_pad` 里与 XInput 手柄同样合并：按键取或、扳机取大、摇杆取推得更远的）。
- 不重复读 XInput 手柄：SDL 的 XInput 驱动保持开启（这样 DirectInput 驱动会跳过 XInput 设备），但 GUID 第 14 字节为
  `'x'`（SDL_CreateJoystickGUID 的驱动签名）的手柄跳过；RAWINPUT、WGI、HIDAPI 的 Xbox 驱动关闭。
- 按键按位置映射（SDL3 的 SOUTH / EAST / WEST / NORTH = Xbox A / B / X / Y），PS 手柄触摸板按下 = Back；Y 轴取反
  （SDL 向下为正）；扳机 0–32767 → 0–255。
- 震动：`XInputSetState` 把游戏的两个马达值交给 SDL 线程；值变化时立即发、否则每秒重发一次（每次持续 2 s）。
- `--no-sdl-pads`：只用 XInput。

验证：r474 日志 `[input] SDL 3.4.18: ...`（本机未插 SDL 手柄）。性能（集显，bench4，同一程序交替）：关 SDL r475 9.15 ms、
r477 10.70 ms；开 SDL r476 10.39 ms、r478 10.70 ms——机器本身越跑越慢，第二组完全相同，无可见开销；几次 0.3–2.4 s 的停顿都在
每 600 帧存截图的那一帧，开关两组都有。实机手柄测试待用户。

## 7. 开场 CG 字幕"放两遍"（用户报告，调查中）

机制（证据）：
- CG 字幕的提示嵌在 SFD 影片的用户数据里。`FUN_0031E180` 每帧清空 `0x9C2600`（256 字节），经 CRI Sofdec 函数 `FUN_00344420`（通道 `[0x9C2734]`=0）/ `FUN_00344AD0` 取当前帧的用户数据，内容形如 `MA000,MJ100`。
- `FUN_0019A950` 解析：语言 `[0xDB9890]`=1 时画 `MAnnn`，=0 时画 `MJnnn`；`FUN_00232D40` 用 `0x434458 + idx*8` 的表（开场 CG 的 idx = nnn + 100）得到字幕 id `0x60000|word`，`FUN_001E6AE0` 在类别表 `0x432478`（每项 {id, 语言0 串, 语言1 串}）查串。"魔刀 黑龙丸……" = id 0x60064，语言 1 串在 HANZI 区 0x00DC70A8。
- 注意：.data 区段文件偏移与 VA 相差 0xF2C0（不是 .text 的 0x10000）；r102–r104 的监视地址按 0x10000 算错，r106 改用正确地址。

实测：
- r107（`logvar:9c2600/9c2604`）：提示依次为 MA000…MA035，每个只出现一次、严格递增；MA000（魔刀 黑龙丸）显示 4103–4283 帧（3 s）。
- MA000–MA029 各指向不同的字符串，只有 MA000 指向 0x00DC70A8；没有两个提示指向同一句。
- r099 每 0.5 s 截图拼条（帧 3900–7200）：每句只出现一段连续显示，未见重复。
- r108 录音（`--wav`）：66–130 s 的能量包络没有找到高度相似（> 0.92）的重复段。

用户确认（2026-10-18）：是文字，同一句消失后紧接着又显示一次；xemu 不会；原机与 xemu 上影片是 30 帧，实时过场也是 30 帧。

根因：
- `--probe 232e1d`（`FUN_00232D40` 中"新建字幕项"分支）：r109 同一段 CG 新建 37 次，索引 100（魔刀 黑龙丸）在 70.04 s 与 72.04 s 各建一次，另有 10 余句重复，间隔 1.2–2.0 s。
- 字幕用文字槽 0（`0x8FA960 + slot*0x68`，+0x5C 占用），槽被占用时 `FUN_00231A70` 不新建；槽的计时器 +0x58 由每帧更新 `FUN_00231460` 递增 → 寿命按帧计。提示在影片用户数据里持续存在，槽到期释放后下一帧又被新建 = 消失后再显示。
- 影片期间游戏把呈现间隔从 ONE_OR_IMMEDIATE（0x80000001）改成严格 ONE（0x1）（r113 日志），且每帧先等自己的 vblank 回调 → 原机每帧两个 vblank = 30 fps，字幕寿命在实际时间上长一倍，超过提示时长。`pace_swap` 只对 BLACK 档案执行"严格间隔迟到时等下一个 vblank"，忍龙在影片里跑 60 fps，字幕寿命减半。
- 修正（`d3d/device.cpp` `pace_swap`）：严格间隔对所有档案生效。r114：影片 30.0 fps，字幕索引 100–129 各新建一次、无重复；游戏中仍是 0x80000001，不受影响。
- 实时过场：用户说原机为 30 帧，本修正是否覆盖待实测（r115 自动运行未经过实时过场）。

## 10. 声音处理器按原机重做、去掉 +6 dB（2.2.20，2026-11-11，玩家反馈 + 逐项取证）

玩家 / 用户："音乐太大""隼龙喊叫过大""刀砍中的声音发尖""偶尔爆音（例如游戏开始音）""各声音之间不平衡"。用户要求：每一处改动都要有资料或其他证据，不许凭听感猜。

**更正 §9**：(a) 混音槽余量表不是全 0：库启动时把槽 0–30 填 1、槽 31 填 0（`FUN_0037C627`，0x37C695），游戏随后对槽 0–10 调 `SetMixBinHeadroom(bin, 0)`（日志为证）；(b) HRTF 系数 /1024 是凭一次录音定的，没有资料支持，改回资料的 /2048；(c) 总输出补 6 dB 取决于采集卡的录音增益，不是原机的东西，已去掉。

**(1) 声音处理器（依 hakuX-lr #166 / `vp.c`，真机实测；库代码核对）**：`dsound.cpp mix_voice`
- 每个声音最多 8 路，一路对应混音槽表的一项。2D 声音第 k 路取声道 k % 声道数；3D 声音 0–1 路是 HRTF 左耳、2–3 路右耳、4–7 路干声。
- 一路的毫贝 = 音量 − 声音余量 + 槽音量 + 3D 项。库按 min(floor(−mB·64/100), 0xFFF) 写成 1/64 dB 的衰减寄存器（`FUN_0037F56A` 0x37F6F3），处理器查实测衰减表：整 dB 节点 round(4095·10^(−k/20))，节点间直线，48 dB 起直线到 63 dB 静音，增益按 1/16384 向下取整；再除以目标槽的 2^余量（HRTF 送出同样）。
- 每路增益在 32 个采样内从上一帧的值渐变到新值，新声音从 0 开始。
- 插值：8 点拉格朗日（抽头 −3..+4，16.16 游标，权重表 257 行、1/256 一档、按 1/65536 舍入，档间混合；小数为 0 时直接取样本）。
- HRTF 系数与延迟也在 32 个采样内过渡。

**(2) 3D 的库内项**：
- 前后分配（`0x37D6A5`，只在扬声器为环绕或杜比数字时；`FUN_0037BA5E`）：W = 0.5 + (1 − |仰角|/90)(|方位|/90 − 1) 夹 [0,1]，近距离（听者距离系数 × 声音距离系数 × 距离 < 0.5）向 0.5 收拢；前 = pow_mb(1 − W)，后 = pow_mb(W)。立体声：前 0、后 −10000。
- 中置分配 `GetCenterVolume`（0x37D774，第 5 个槽为 2 时，`FUN_0037B87B`）：|方位| 或 |仰角| ≥ 45° 时前对 0 dB、中置静音；否则用库表 0x383DB8 / 0x383D00（正前方：中置 0.707、前对 0.5）。按指令特征在镜像里找表。
- 每槽附加：6/7 = 中置分配的前项 + 前 + 距离；8/9 = 后 + 距离；2 = 中置项 + 前 + 距离；10 = 房间项（0）+ 距离；其余 = 距离。

**(3) 多普勒（新增）**：游戏给 3D 声音传了非零速度（诊断日志：挂机自动过场里最大约 75 m/s，多半是镜头切换 / 瞬移造成的跳变；听者速度始终为 0）。
库的做法：方向 = (声源 − 听者) 单位化（`0x37D277` / `0x37EB29`）；x = (声源速度 − 听者速度)·方向（头部相对模式只用声源速度，`0x37D4B9`）× 听者与声源的距离系数 × 多普勒系数（`GetVoiceData` 0x37B397）；
变调 = round(4096·log2(1 − x/342))，x ≥ 342 时 −32767，x ≤ −342 时 +4096（`0x37D816`）；加到声音的音高上，夹 [−32767, 8191]（0x37F81F）。

IRQL 的内核导入）由派发器保持原样（`dsound_native_code`：按入口特征找，通配 rel32；7 个版本各唯一命中，2004 在 0x351A05）。
游戏用过的 3 组参数，换算结果与先前诊断（临时恢复入口字节调用）逐字相同。x87 控制字：见 §12 (6)，换算所在线程原机与移植版都是 24 位精度。

**(5) 接入混音器**：声音的各路先加到混音槽 0–10（浮点），每 32 样本转 24 位（满刻度饱和，同声处理器）跑效果 0–5，取槽 0–5：
5.1 直接输出；双声道按 EP 下混表折叠。EP 程序（XBE DOLBY 段）里读到两组下混系数：立体声 L = FL + 0.7071 (C + Ls)、
R = FR + 0.7071 (C + Rs)，无 LFE（与 hakuX-lr、我们一致）；单声道 0.5 L + 0.7071 C + 0.5 R + 0.3536 (Ls + Rs)（= 我们的左右平均）。
EP 写完下混表后若参数块（`x:$0700` 所指）第 16 字段非 0 会把系数整体乘第 17 字段：库写参数块的代码里未见这两字段的写入、
参数块与 `x:$0700` 的对应也未核实——只影响双声道整体电平，记为未决。11 号以上混音槽无效果读取：不出声（同原机）。
`black.ini gpfx`（默认 1）、`cfg:gpfx:0/1` 可切回旧路径（自写 FDN、跳过效果 0–3 / 5）。非标准镜像（如 BLACK 的）走旧路径。

**(6) 测量**：
- 性能（集显第 1 章）：效果每 10 ms 块约 115–126 µs（一个核的 1.2%，混音线程，不在游戏核上）；渲染线程中位数 gpfx 开 4.97 / 5.37、
  关 5.55 / 5.76 ms，差在误差内。（早先几轮测到 240–590 µs，换掉 `lrintf`、补 `<intrin.h>` 后稳定在上述值，未完全解释。）
- 自动过场（挂机 ~120 s）：限幅前峰值 1.34，0.04% 采样超满刻度（3D 声道 ×2 后部分时刻到顶；2.2.19 为 0.39%，2.2.20 为 0）。
- 输出模式：单声道、杜比环绕、杜比数字、DTS 各 135 s 无崩溃；5.1 下过场段六声道 −19.7 / −19.6 / −22.5 / −28.4 / −15.2 / −15.5 dB
  （后对含混响与 3D 后方成分；LFE 含 3D 声音默认送槽 3 的 −20 dB）。2004 启动约 2 分钟正常，效果与换算均生效。

**未决**：真机对比（地窖录音：混响后段、刀声相对背景、11 kHz 以上）。杜比环绕编码、EP 下混缩放字段、x87 控制字见 §12。

## 12. 杜比环绕编码照原机 EP 程序（2026-11-11）

**(1) 程序从哪来**：XBE 的 DOLBY 段（美版 VA 0xDBA600，0x716C 字节，明文；8 个支持的版本含 2004、2004 TU 逐字节相同）。库
`FUN_00383AA8` 把引导代码（段首 0x320 字节）、EP 内核（0xDBA920 起 0x5FC 字节，P:0x180 起）、6 个模块和 24 字的参数块（0xDC1720，
段内只有前 19 字，余下按虚拟大小补 0）装进 EP 临时内存。引导代码按参数块字 1/2/3 决定跑哪些模块：字 1 非 0 → 模块 0（模拟输出编码），
字 2 → 模块 1–3（AC3），字 3 = 1 / 2 → 模块 4 / 5（单声道 / 立体声下混）。库唯一写参数块的地方（`0x3827ED`）：扬声器设为环绕或开了
杜比数字时不写（字 1、2 保持 1），否则字 1 = 字 2 = 0、字 3 = 1 或 2。所以杜比环绕模式的模拟输出由模块 0 产生。

**(2) 模块 0 做什么**（0xDBAF20，0x2F2 字，装在 P:0x300、入口 P:0x304；每帧 256 样本，读 GP 送来的 L C R Ls Rs，LFE 不用）：
- `p:03D4`：五路输入都乘增益表里第 p[7] 项。p[7] = 0x1F，先用 IFlt / IFgt 夹在 1–0x1F，表在 `p:0305–0323`（31 项，−30…0 dB 每 1 dB），
  基址却是 0x305，0x1F 号读到 `p:0324`——模块自己的第一条指令字 0x607000 = 0.7534（**−2.46 dB**）。真机执行同一程序读同一个字，
  所以原机杜比环绕输出就比立体声低 2.46 dB。立体声模块 5 没有这一步（`x:(r2+16)` = 0 时不缩放，第 16 字段库从不写）。
- `p:0469`：S = 0.7071 Ls + 0.7071 Rs；`p:047F`：L' = L + 0.7071 C，R' = R + 0.7071 C。
- `p:04A7`：L'、R' 各过 4 节二阶滤波（相位网络），S 过 5 节（同一网络再加限带）；子程序 `p:05CA` 是直接型二阶节，
  y = −2c0 y1 − c1 y2 + c2 x + 2c3 x1 + c4 x2，每个输出被截掉的余数加到下一个（误差反馈），余数帧末存成 48 位。
- `p:04EC`：Lt = L' + 0.7071 S'，Rt = R' − 0.7071 S'。
- 系数在 `p:0533` 起 0x5A 字（拷到 Y:0）；按 `x:$0608` 第 12–13 位选两组之一，该字由模块自己写 0，另一组不用。

**(3) 测量**（xemu 内核跑原模块，`project/tools/gpfx_check/ep_measure.c`）：L → 只到 Lt、R → 只到 Rt，−2.46 dB、全频平坦（全通）；
C → 两边 −5.47 dB 同相；Ls、Rs → 合成 S，两边反相，1 kHz −8.7 dB，50 Hz −17.2、100 Hz −11.7、200 Hz −9.5、15 kHz −8.7、20 kHz −23.2 dB，
相对 L 的相位 −90°（Lt）/ +90°（Rt）（100 Hz −89°、1 kHz −90°、10 kHz −95°）。即标准杜比环绕编码：Lt = L + 0.707 C − j 0.707 S，
Rt = R + 0.707 C + j 0.707 S。以前的公式缺 90° 相移、S 限带和 −2.46 dB。

**(4) xemu 跑不了这个模块**：它没有 `extractu`（模块读标志字用，DSP56300 Family Manual），把 IFcc（`0x2020xx–0x203Fxx`，条件运算）
当成无条件运算加一个错误的寄存器传送。测试平台按手册补了 `extractu`；IFcc 在 p[7] = 0x1F 时两种解释结果相同。

**(5) 实现**：`loader/src/audio/ep_surround.cpp`，逐样本翻译（DSP56300 定点：56 位累加器、小数乘法、收敛舍入、写回饱和；SR 复位值，
引导代码不改 SM / RM），每 256 样本把各节余数截成 48 位（同原机帧末保存）。验证（`ep_surround_test.cpp`）：噪声 0.1 / 0.5 / 1.0 / 2.0 / 8.0
倍满刻度与正弦，各 400 帧，翻译每次喂随机长度的块：**逐字相同**。有意改坏两处检验比对：舍入去掉"逢半取偶"→ 约 58% 的字不同；
去掉帧末 48 位截断 → 8.0 倍（削顶）时不同。
接入：杜比环绕模式（`audio_mode = 2`，无数字输出）的最后一步，5.1 混音转 24 位（满刻度饱和）按 L C R Ls Rs 送编码器，输出 Lt Rt。
GP 效果关着时同样经过编码器。原机模拟输出截成 16 位（DMA 格式 1，`v >> 8`），我们与其他模式一样保留 24 位。
性能：32 位构建每 10 ms 块约 40 µs（混音线程，不在游戏核上）。集显第 1 章、杜比环绕模式，渲染线程中位数：旧公式 5.46 / 5.45 ms，
编码器 5.38 / 5.39 ms（同一路径固定集显；先前一轮旧版落在独显上测得 3.9 ms，作废）。游戏内（自动过场 135 s）：输出比旧公式低约 2.5 dB，
峰值 0.77（旧 1.0）。

**(6) x87 控制字（同日，用户在 xemu Debug → Monitor 读 `info registers`）**：原机标题画面时 FCW = 0x003F（精度 24 位、就近舍入、
异常全屏蔽；第 6 位是保留位，真 CPU 读回为 1，QEMU 显示为 0），MXCSR = 0x1FA4（无 FTZ / DAZ）。来源是游戏自己的初始化：
`0x30E090` 调 `_controlfp(_PC_24, _MCW_PC)`（CRT 先在 `0x373102` 设 `_PC_53`）。全 XBE 的 `fldcw` 只在 CRT 里（`_controlfp` / `_control87`
与数学函数的保存 / 恢复）。移植版这段游戏代码原样运行：临时诊断读到主线程 xbox-1（渲染、`SetI3DL2Listener` 都在它上面）为 0x007F，
即同为 24 位精度；其余 5 个游戏线程（CRI 工作线程 0x33E3E0 / 0x332FF0 / 0x333070 / 0x332C90 与 0x1DA500）起始为 Windows 默认 0x027F。
原机内核给新线程的初值未知，但这 5 个线程的直接调用树（共约 300 个函数）里没有 x87 运算（间接调用未追）。结论：无需改动。
