# 呈现节拍：现有架构修复与后续重构方案

**日期：** 2026-11-20  
**状态：** 方案，不是已实现  
**关联文档：**

- `project/docs/14_呈现节拍架构问题报告.md`
- `project/docs/15_呈现节拍目标架构设计.md`
- `project/docs/16_呈现节拍问答.md`

> 本文把“先修现有架构”和“以后再重构”分开写清楚。  
> Phase 1 不是曲线救国，也不是完整重构；它是把现有架构里缺的 D3D 状态恢复补正确。  
> Phase 3 才是 Presenter / tick-present 解耦的架构重构。

---

## 1. 目标

```text
游戏时间：固定 59.94，不跟显示设备
呈现：由呈现层独立决定
焦点 / 模式 / Reset：不再拖慢游戏逻辑
30fps 影片：仍按游戏 tick 每 2 tick 一帧
```

不改：

```text
游戏原始 x86 逻辑
D3D8 → D3D9 绘制语义
输入 / 音频 / 存档 / 联网
```

---

## 2. 现状（2.2.37.3 / 2.2.37.3-t）

### 已证实

```text
高刷（120/144/165/240）默认走 59.94 timer
60 Hz 跟 display / kernel vblank
exclusive_60hz 会把独占显示模式切成 60 Hz
30fps CG 在 tick 47 时变成 23.5 ≈ 24
timer_vblank = 1 时 CG 30 / 游戏 60
关掉 timer_vblank 问题立即复现
```

### 已处理

```text
DEVICELOST / HUNG / REMOVED / OUTOFVIDEOMEMORY → recover_device
窗口模式 MODE_CHANGED 连续 30 帧 → Reset
Alt+Enter / 解析度 / 显示设置 → Reset
D3D9Ex 下 Alt+Tab 不把 OCCLUDED / MODE_CHANGED 当 device lost
最小化也 Present，避免命令积在 driver
```

### 未处理

```text
独占全屏 MODE_CHANGED
OCCLUDED 的明确恢复
焦点回来后 CheckDeviceState / ResetEx
焦点回来后重套 60 Hz
swap chain / back buffer 状态恢复
Present 仍可能阻塞游戏线程
frame pacing 仍跟 tick 同一条链
```

---

## 3. 两个阶段要分清

```text
Phase 1：修现有架构
  目标：切模式 / Alt+Tab 后不留下持续错误状态
  性质：正确性修复
  不改变 Present 所有权

Phase 2：重构架构
  目标：Present 不再拖游戏 tick
  性质：Presenter / 线程模型重构
  需要新的帧交接
```

Phase 1 不能取代 Phase 2；  
Phase 2 也不能省掉 Phase 1，因为 Presenter 仍然要处理焦点 / Reset。

---

## 4. Phase 0：量测

### 目的

在改行为前，先知道到底卡在哪。

### 记录

```text
tick 来源：timer / DwmFlush / kernel vblank
每次 kv.wait 耗时
Present 开始 / 结束 / 耗时
Present HRESULT
CheckDeviceState
MODE_CHANGED / OCCLUDED
WM_ACTIVATE / WM_ACTIVATEAPP / WM_DISPLAYCHANGE
Reset 原因 / 耗时 / 结果
near_60 / display_near_60
g_exclusive_now / g_dev_exclusive
g_pp.FullScreen_RefreshRateInHz
```

### 判断

```text
16.7 ms：正常
33 ms：错过一次 vblank
100 ms+：Present / driver / mode
1000 ms+：Reset / occlusion
```

### 输出

```text
一份 165 → 60 + 30fps CG 的逐次日志
一份 60 Hz 窗口 / 独占对照
```

## 5. Phase 1：修现有架构

### 5.1 目标

```text
Alt+Tab 回来不再持续 45 / 24
切 60 Hz 后能恢复
OCCLUDED 不会一直卡
模式切换黑屏仍然存在，但只黑一次
```

### 5.2 状态

```text
FOREGROUND
OCCLUDED
MODE_CHANGED
MINIMIZED
DEVICE_LOST
RESETTING
```

### 5.3 事件

```text
WM_ACTIVATEAPP
WM_ACTIVATE
WM_DISPLAYCHANGE
WM_SIZE（minimized / restored）
Present 回传
CheckDeviceState
Reset 完成
```

### 5.4 规则

#### OCCLUDED

```text
不要每帧 Reset
记录状态
等视窗真的回到前景
再检查 / 必要时 Reset
```

#### MODE_CHANGED

```text
独占全屏也要处理
debounce 2–3 帧 / 100 ms
CheckDeviceState
必要时一次 ResetEx
重套 exclusive_mode()
```

#### DEVICE_LOST / HUNG / REMOVED

```text
走现有 recover_device()
```

#### MINIMIZED

```text
不 Reset
保持 Present 把命令送出去
还原后再检查
```

#### 焦点回来

```text
CheckDeviceState
若 mode / 尺寸不符
ResetEx
验证 vblank / 模式
```

### 5.5 防護

```text
Reset 只在窗口线程
Reset 前後暂停 / 恢复游戏线程
Reset 冷却时间
Reset 失败要记录，不要无限循环
Reset 中不要重入
```

### 5.6 固定时鐘

```text
timer_vblank 成为正式路径或启动器可选项
60 Hz 也走 timer
display vblank 只用于呈现，不驱动 tick
```

### 5.7 完成标准

```text
Alt+Tab × 10 后仍 60
165 → 60 后 30fps CG 正确
OCCLUDED 不会永久卡
模式切换只黑一次
```

## 6. Phase 2：非阻塞 Present

### 目的

先不引入新线程，验证 Present 是否还会拖住 tick。

### 做法

```text
D3DPRESENT_DONOTWAIT
或 FLIPEX
Present 失败时保留上一帧
```

### 限制

```text
DONOTWAIT 可能仍在 driver 内部等
设备线程仍是游戏线程
如果 Present 阻塞，游戏 tick 仍会被拖
```

### 判断

```text
不阻塞 → Phase 2 可能就够
仍阻塞 → 进入 Phase 3
```

## 7. Phase 3：Presenter 重构

### 7.1 边界

```text
Game thread
  → 画到 offscreen frame
  → 放进 latest-frame queue（深度 1）
  → 立刻回去跑下一个 tick

Presenter thread
  → 取最新完整帧
  → 复制 / 共享 surface
  → 自己的 swap chain
  → Present
  → 旧帧直接丢
```

### 7.2 规则

```text
queue 深度 1
只保留最新帧
Presenter 落后时丢旧帧
游戏线程不等 Presenter
Reset / 焦点由 Presenter 处理
30fps 影片重复上一帧，不改 tick
```

### 7.3 D3D9Ex 限制

```text
不能两个线程共用同一个 device 同时 Draw / Present
Present 和 Reset 不能并发
需要 shared surface 或 offscreen copy
D3D9Ex 没有 DXGI ALLOW_TEARING
```

### 7.4 需要先验证

```text
shared surface 是否可用
1080p / 4K 每帧 copy 成本
Alt+Tab / Reset 时 queue 是否安全
输入延迟是否可接受
```

### 7.5 完成标准

```text
Present 卡 1 秒，游戏 tick 仍前进
30fps 影片节奏正确
Alt+Tab 后只掉帧，不改变游戏速度
```

---

## 8. Phase 4：Frame pacing

Presenter 自己决定：

```text
60 Hz：每帧一次刷新
120 / 180 / 240：允许重复刷新
VRR：准备好就送
30fps 影片：重复上一帧
```

游戏 tick 永远固定 59.94。

## 10. 风险

```text
Reset 回圈
Reset 时黑屏更久
焦点事件重复
D3D9Ex shared surface 不支援
copy 成本太高
输入延迟增加
```

### 回退

```text
Phase 1 用开关保留旧路径
Phase 2 Present 失败保留上一帧
Phase 3 Presenter 可切回同步 Present
```

---

## 11. 建议顺序

```text
Phase 0 量测
→ Phase 1 状态机
→ Phase 2 固定时鐘
→ Phase 3 非阻塞 Present
→ Phase 4 Presenter
```

### 一句话

> **Phase 1 是把现有架构修正确，Phase 2 是止血，Phase 3–4 才是架构重构；先做 Phase 1，成本最低、回报最大。**
