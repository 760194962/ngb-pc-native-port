## 1. 改动（每项的理由）

| 改动 | 文件 | 证据 / 理由 |
|---|---|---|
| 纤程栈至少 1 MB | `kernel/k_ngb.cpp` | 游戏向 `MmCreateKernelStack` 要 16 KB；在 HLE 的 `SetRenderTarget` 里调用宿主 D3D9 时进程无声死亡（日志在 SetRenderTarget 之后中断，没有任何异常行）。栈扩到 ≥1 MB（游戏看到的 StackBase/StackLimit 仍按它要的 16 KB）后不再发生 |
| 线程退出要写 ETHREAD | `kernel/k_thread.cpp`、`xthread.cpp` | 游戏用 `GetExitCodeThread` 轮询工作线程退出（XAPI 读 KTHREAD+4 `HasTerminated`、ETHREAD+0x120 `ExitStatus`）；没写时 Warnings 画面后永远等待。`xthread_mark_terminated` 在 `PsTerminateSystemThread` 和线程函数返回后各写一次 |
| `BlockUntilVerticalBlank` 真等下一次垂直同步 | `ngb/d3d_ngb.cpp`、`d3d/device.cpp` `wait_next_vblank()` | 工作线程 0x332FF0 / 0x333070 在 `BlockUntilVerticalBlank` 上循环；它等的内核事件是通知事件、无人复位，HLE 立即返回 → 单核绑定下自旋，Warnings 前要 33–86 s。改为等 `g_vblank_count+1` 后游戏速度 97% |
| `pace_swap` 不再为非 BLACK 构建多等一帧 | `d3d/device.cpp` | 幻魔教训 §05：游戏自己等垂直同步再 Swap，black-pc 又等一次 → 30 fps（每帧 2 次垂直同步）。只对 BLACK 保留 |
| `DrawIndexedVertices` 参数源保持 BLACK 的 `s s s` | `tools/gen_ngb_hle.py` | XbSymbolDatabase 对非 LTCG 名字也标了 `eax VertexCount`，按它生成后 `pIndexData` 读到 0xC2 崩溃；非 `__LTCG` 名字一律沿用 BLACK 的参数源 |
| 设备对象里的灯光数组 | `d3d/device.cpp` `D3DDevice_SetLight` / `LightEnable` | §3.1：游戏 `FUN_0019E150+0x4C4` 读 `device+0x7A4` 得空指针崩溃。程序库自己的 `SetLight`（0x3C7490）按需分配该数组（每项 0x90 字节）、`LightEnable`（0x3C7850）分配 8 个硬件灯槽；HLE 照同样布局维护 |
| `SetRenderTarget` 把视口重设为整个新目标 | `d3d/device.cpp` | §3.2：程序库的 `SetRenderTarget`（0x3C6A80）末尾调 `D3D_CommonSetMultiSampleModeAndScale`，后者 `+0x316` **尾跳到 `SetViewport`**（0x3C7270）；黑之章每帧只对 128×128 阴影目标调一次 SetViewport，之后靠这个重设 |
| `RunPushBuffer`：解析为索引绘制 | `ngb/d3d_ngb.cpp` | §3.3：第一章载入时的 35 个不同推送缓冲只含 `SET_BEGIN_END` / `ARRAY_ELEMENT16` / `ARRAY_ELEMENT32` 三种方法，即 `DrawIndexedVertices` 录下的索引流；解析索引后走同一条 HLE 路径。其他方法 / 跳转 / fixup 表记录一次并跳过（到目前没出现） |
| XAPI `SwitchToFiber` 替换：TEB 栈边界跟着纤程走 | `fiber.cpp`、`fiber.h`、`build_profile.h`、`kernel/k_ngb.cpp` | §3.4：XAPI 的 `SwitchToFiber`（0x32A293，63 字节）只换 esp 与 fs:[0]，Windows 的 TEB 仍描述线程原栈；纤程上一旦异常，向量处理器打印寄存器后进程被系统直接终止（退出码 0xC0000005，没有 UNHANDLED 行，`timeout` 报 Segmentation fault）。替换后同一崩溃给出完整回溯（§3.4 日志） |
| 索引绘制：索引减去最小值，指针指向块首 | `d3d/draw.cpp` `draw_indexed_up` | §3.5：D3D9On12 的 `DrawIndexedPrimitiveUP` 从顶点指针起复制 `MinVertexIndex + NumVertices` 个顶点，black-pc 的"指针倒退 mn 个顶点"写法越界读 |
| 索引绘制前检查顶点页可读 | `d3d/draw.cpp` `pages_readable` | 黑之章把游戏堆（`NtAllocateVirtualMemory`，宿主任意地址）里的顶点缓冲交给宿主复制；越界会在 d3d9 内部崩溃。对转换块以外的来源做 `VirtualQuery` 检查，不可读则跳过并记录（到目前没触发） |
| 崩溃回溯走 16 KB、列出所有模块帧；纤程栈上也能走 | `hooks.cpp` | 之前只走 2 KB 且只列游戏 / blackrt 帧，d3d9 内部的崩溃一帧都列不出 |
| `game_callers` 的游戏代码上界按 XBE 的 D3D 段 | `d3d/draw.cpp` | 原值 0x269000 是 BLACK 的 D3D 段起点，黑之章 `.text` 到 0x3C5xxx |
| 记录最近 4 次索引绘制，崩溃时打印 | `d3d/draw.cpp`、`hooks.cpp` | §3.5 的定量证据就来自它 |
| 固定管线绘制前从设备对象取矩阵 | `d3d/device.cpp` `sync_transforms_from_device`、`d3d/draw.cpp` `begin_draw` | §3.6：游戏把矩阵直接 `rep movsd` 进 `device+0xC60+State*0x40`（程序库 `SetTransform` 0x3C7160 的存放处），不经 SetTransform；762 处游戏代码写脏位字 0x3D83D0。r019 起首顶点落在屏幕内的绘制从 37 次变 178 次，场景出现 |
| 固定管线绘制前从设备对象取材质 | `d3d/device.cpp` `sync_material_from_device` | §3.6：游戏内联的 SetMaterial（`FUN_0030D630+0x76`）把 68 字节 D3DMATERIAL8 拷进 `device+0xF00`；程序库 `FUN_003D1610` / `FUN_003D1520` 从那里读。r021 起隼龙有颜色 |
| `--no-fog` 诊断开关 | `common.h`、`main.cpp`、`d3d/draw.cpp` | r017 对照实验：雾不是全黑的原因（关雾后背景从雾色变纯黑） |

## 3. 关键证据

### 3.1 灯光数组（r006 崩溃）

### 3.2 视口重设（r007 追踪、r008 验证）

第 14999 帧（r007 `[rt]` 行）：`Clear → SetRenderTarget 008CE000 data 0 128x128 → SetViewport 0,0 128x128 → Clear → SetRenderTarget 背缓冲 720x480 → … 12 次 2D 绘制`，整帧只有这一次 SetViewport。
程序库：`D3D_CommonSetMultiSampleModeAndScale`（0x3C6490）末尾 `003c67a6  jmp 0x3c7270 ; D3DDevice_SetViewport`，而 `SetRenderTarget`（0x3C6A80）在 `+0x2E9` 调它。`SetViewport` 的游戏调用者只有 3 处（0x1D4692、0x1D54DC、0x30C2E1）。
结论：Xbox D3D8 的 SetRenderTarget 会把视口重设为整个目标（与 PC D3D8 文档一致），HLE 原来只"把已请求的视口夹到新目标里"。BLACK 每帧自己设 640×480 视口，所以没暴露。

### 3.3 推送缓冲内容（r005）

35 个不同缓冲（`[pb] RunPushBuffer #N` 行），全部：`17fc:2`（SET_BEGIN_END 开/关）、`1800:N`（ARRAY_ELEMENT16，每 dword 两个 16 位索引）、可选 `1808:1`（ARRAY_ELEMENT32，奇数个索引的最后一个）；无其他子通道、无跳转、fixup 表指针为 0。
`D3DDevice_RunPushBuffer` 的游戏调用者 6 处（0x1D209E、0x1D494B、0x24DA04、0x2BE7E9、0x30C079、0x30C11C）。x2.1 的符号表里**没有** `BeginPushBuffer` / `EndPushBuffer`。来源已证实为**磁盘数据**：r016 把第一个缓冲（6560 字节，物理地址 0x80A76F80）dump 成 `run\r016_fvf\shots\pb_first.bin`，`tools/find_bytes.py` 在 `game\x21\cmn.afs` 偏移 0x13DF780 找到**逐字节相同的 6560 字节**（含 NV2A 命令头）。即关卡模型的索引流在光盘里就是 NV2A 推送缓冲格式，游戏读进内存直接 `RunPushBuffer`。

### 3.6 LTCG 内联的设备状态写入（r018 → r021）

黑之章的 D3D8LTCG 把 `SetTransform`、`SetMaterial` 等内联进游戏代码：游戏直接写设备对象，再或上脏位（`work\asm\inline_state.txt`）：

### 3.8 用户实机试玩第二轮（2026-10-18 下午，r034–r044）：四个根因

(a) **预变换顶点的贴图坐标**。r036 黑屏帧（11089）：最后一个全屏四边形取样 512×512 渲染目标 0x02A86000，而 r031 连拍末帧的该目标整张橘色、发光链第一步 0x02B86000 整张黄色，r036 的则整张深灰——所有"用 XYZRHW 四边形把线性贴图（720×480 背缓冲 / 深度缓冲，像素坐标 0..720×0..480）复制到小目标"的绘制都只取到边缘一点。原因：D3D9 对 XYZRHW 顶点跳过顶点管线，`D3DTS_TEXTUREn` 的缩放矩阵从未生效（`apply_fvf_texture_scale` 原先对 flags==0 用矩阵、r032 的"flags!=0 合成矩阵"修法也因此无效）。改为在 `scale_rhw` 复制顶点时直接把 uv 乘 1/宽、1/高（游戏自己的贴图矩阵若开着则一并合成），并对 XYZRHW 绘制关闭宿主贴图变换。副产物：序章 CG（影片帧也是线性贴图 + XYZRHW 四边形）从"全黑只有字幕"变为正常播放，警告页进标题的"闪烁"其实是一段影片，也一并正常。

(b) **常数 alpha 混合**。r037 帧 14748：撿道具时对话框（45 个字形四边形 + 底框）先画，随后一个全屏四边形取样快照，混合 `0x8003/0x8004`，BLENDCOLOR `0x00FFFFFF`。Xbox 的 D3DBLEND 值就是 GL 枚举：0x8001/0x8002 = CONSTANT_COLOR / ONE_MINUS，**0x8003/0x8004 = CONSTANT_ALPHA / ONE_MINUS_CONSTANT_ALPHA**。该层 alpha 为 0 本应完全不可见，当成颜色因子就是 100% 盖掉对话框。画面复制用同一组模式但 BLENDCOLOR `0xFFFFFFFF`（alpha 1），不受影响。D3D9 只有 BLENDFACTOR，`blend_factor` 在任一因子为 0x8003/0x8004 时把混合色的 alpha 复制到四个通道。

(c) **深度格式贴图头的取样语义**。r040 重攻击帧 3713：光爆 draw（`FUN_003187e0`，fvf 0x242，MODULATE2X）第 0 层贴图头 0x039763E0 → 数据 0x02B86000，即发光链第一步"深度缓冲 → 256×256"的复制结果；复制时用的贴图头 0x00C0EAE0 格式 **0x2E = D3DFMT_LIN_D24S8**，数据 0x02934000（主深度缓冲）。此前 `depth_view` 不分头格式一律按 BLACK 的用法（A8R8G8B8 头盖 Z24S8 内存，A=Z[23:16]、R=Z[15:8]、G=Z[7:0]、B=模板）拆字节，R/G 通道的低位就是整屏绿橙条纹（`f3716_screen.png`、r038 `burst_*.png`）。NV2A 对深度格式贴图返回深度值本身；现按头格式 0x2A..0x31 走新的 `kZDepthPS`（四通道都是深度，alpha 也是深度——与原字节拆法里 alpha≈高 8 位的行为一致，发光链用 alpha 的部分不变）。深度接近 1，乘上去就是用户记忆中的"透明白光"。过程中排除了普通贴图：从进程内存倒出 0x00C6F000（DXT1 256×256）与 0x001D4A00（DXT1 64×64）解码（`tools/dxt_decode.py`）均正常；贴图缓存按整段 dword 做哈希，内容变化会重传。

(d) **Z bias / polygon offset 没有映射**。r041：静止 6 张连拍逐像素一致，走动时 `seq_01/02/04` 同一块岩面上交替出现一层亮斑（`crop_seq_*.png`）。灯光 / 材质 / SetLight 逐帧一致（r041 六帧）；执行期关 specular、抗锯齿、接缝填补、宿主雾各一次仍闪（r042/r043）。追踪帧（r043/r044）：每帧 128 个 `fvf 0x142/0x152, z 1 LEQUAL, write 0, blend 1` 的贴花 draw 与 108+38 个不透明岩石 draw 共面；岩石 draw 的 `SOLIDOFFSETENABLE=1, POLYGONOFFSETZSLOPESCALE=1.0`（另有 2 个 `ZBIAS=7` 的 draw）。`draw.cpp` 原先对 `XRS_ZBIAS` 与三个 polygon offset 状态都没有 `on_change`。映射：ZBIAS 一级 = DEPTHBIAS −0.000005（d3d8to9 的经验常数）、polygon offset 偏移 = 1/2^24 深度单位、斜率直接给 SLOPESCALEDEPTHBIAS。r044 用户确认不闪。

**仍未解决：隼龙没有影子**（用户指出）。已查明机制（§4 第一条）：游戏把隼龙画进 128×128 深度目标（颜色面 0x008CE000 的 Data 故意为 0、`cwrite 0`；深度贴图头 0x03866A80 = LIN_D24S8 128×128，数据 0x02CAE000），接收面材质由 `FUN_001d6e20` 设置：`ShadowFunc = 0x206 (GEQUAL)`、`ZWRITE 0`、`BLENDOP REVSUBTRACT`、`SRC INVSRCCOLOR / DST SRCCOLOR`、`ZBIAS 3`、`SetTexture(0, 影子深度)`、专用顶点程序（句柄 0x0F5716B1 等）与像素程序 0x03866AB0、深度 0.8（`[0xBCDF14]`）。但追踪里从未出现取样 0x02CAE000 的 draw：接收面节点（回调 0x1D7690）由 `FUN_001d69a0` 经 `FUN_001d6180`（按矩阵变换角色位置并与 `[edx+0x154]` 比较高度）判定后挂到延迟绘制表 0xD21E80（本帧 44 个节点全是 0x1B5EC0）；条件没过的原因待查。即使过了，还需要在像素程序翻译里实现 NV2A 的深度比较（SHADOWFUNC 对 r/q 与深度贴图比较，返回 0/1）。

### 3.9 用户实机试玩第三轮（2026-10-18 下午，r045–r056）：影子、特效与固定管线

(a) **rdtsc**。影子驱动 `FUN_001d63a0` 只在 `[0x8CDA5C] < 0` 时画玩家影子；该计数器由 `FUN_001d5e30` 按帧时间 `[0xD21698]` 驱动：> 94 递增到 10（淡出），否则递减到 −5。帧时间来自 `FUN_0030E140`：`rdtsc` 差值 × 0.113（Xbox TSC 733.33 MHz）。进程里读到 242.6（宿主 TSC 约 3 GHz），影子永远淡出。capstone 扫描全部可执行段的 `0F 31`：游戏 5 处（0x30CA3F/0x30CAA1/0x30E060/0x30E284/0x30E58E）+ XAPI `QueryPerformanceCounter` 0x376E44（D3D 0x3CF970、DSOUND 0x39374F 在 HLE 替换段，不动）。改为 ud2 陷阱，向量异常处理器按 QueryPerformanceCounter 换算成 733.33 MHz 计数（r045 日志 `rdtsc: 6 sites trap`）。之后帧时间 78–99：因为宿主 D3D 调用在游戏线程同步执行，引擎量到的"CPU 时间"贴近整帧，计数器在 −5..0 摆动，影子闪（r045）。引擎位点再除以 `--tsc-divisor`（默认 4）后帧时间 21–29、计数器稳定 −5（r046）；XAPI 的 QPC 保持原速。这是渲染改成异步之前的替代方案。

(b) **深度格式贴图的取样语义**。xemu `psh.c`（`psh_append_shadowmap`）：深度格式贴图一律按 SHADOWFUNC 比较，PROJECT3D 比 r/q，2D 模式与 0 比，NEVER→0、ALWAYS→1。照此实现（r047）：游戏每帧的 256×256 深度复制在 ShadowFunc=NEVER 时成全 0，刀光 / 光爆 / 发光链全消失；影子接收面（`FUN_001d6e20`，ps 0x38B68D0，**texmodes 0x1 = PROJECT2D**，ShadowFunc GEQUAL）在 2D 模式下与 0 比较恒为 1，影子也没了。游戏显然依赖"2D 取样得到深度值本身，再在 combiner 里和顶点色比较"，故 2D 模式回传深度（四通道），PROJECT3D 才做比较（`nv2a_psh.cpp`）。进程里 ShadowFunc 每帧在 0x200（NEVER）与 0x206（GEQUAL，接收面）之间切换，接收面节点 `FUN_001d7690` 画完后复位 NEVER。

(c) **未绑贴图的层**。双截棍扫击 draw（fvf 0x242，`FUN_003187e0`）第 1 层 alpha MODULATE(current, texture) 但第 1 层没绑贴图；宿主取样成 (0,0,0,0)，alpha 0 被 alpha test（GREATER 0）砍掉。Xbox 上该特效可见，故按不透明白处理。

(d) **宿主固定管线的缺陷与自生成着色器**。龙剑刀光 draw：fvf 0x242，第 0 层 MODULATE2X(diffuse, 深度复制)，第 1 层颜色 SELECTARG1(current)、alpha MODULATE(current, 128×128 DXT5 刀光贴图)，顶点色 0xE5E5E5F7。r050 向宿主查询：层状态与贴图都正确，画出来却整条不透明。改为自生成 ps_2_0（`ffp_ps.cpp`，D3D8/9 层语义、未绑贴图为白、`cfg:ffpdebug` 可直接输出第 1 层取样）。首版把影片乘黑：影片四边形 XYZRHW|TEX1 没有 DIFFUSE 且 LIGHTING 开着，D3D 规定预变换顶点不打光、缺 DIFFUSE 为不透明白（r055→r056 修正）。`cfg:ffpdebug:2` 连拍（r056 `dbg_*.png`）：刀光带上贴图 alpha 只有刀尖端是黑，其余白——取样正确，贴图本身大部分 alpha≈1。所以在"深度复制=1"的语义下，刀光本来就是 2×0.9 的白色不透明带；用户记忆中的"透明色轨迹"若属实，意味着深度复制在原机上不是 1，这取决于 (b) 的硬件细节，无法离线核实。

(e) **线宽**。击墙火花是 `DrawVerticesUP` 线段（prim 4，fvf 0x42，加色，`FUN_00318410`），LINEWIDTH 恒 1.0；宿主在渲染倍率下仍画 1 像素。`draw_wide_lines` 用当前 world/view/proj 在 CPU 投影，按线宽 × 倍率展开成四边形。

**仍未解决**：刀光外观（见 (d) 末）；影子偏淡（接收面 REVSUBTRACT 混合 + 8 位深度比较的精度，与 (b) 相关）；渲染同步执行导致的帧时间虚高（(a) 的除数是权宜）。

**xemu 参考（用户 14:46–14:47 截图，`run/xemu_ref/xemu_swing_1..3.png`）**：原版龙剑刀光是**半透明、带背景纹理的拖影**——刀光区域里能看到后面的岩壁与水面，像被拉伸 / 折射过的场景，颜色偏紫灰，没有纯白。我们的是不透明白带。对照追踪（r050 帧 2746）：刀光第 0 层取样 256×256 目标 0x02B86000，该目标在本帧开头由一次全屏复制写入，复制源是贴图头 0x00C0EAE0（格式 0x2E LIN_D24S8，数据 0x02934000 = 我们分配的主深度缓冲），复制发生在场景绘制之前。xemu 的画面说明 0x02B86000 在原机上装的是**场景颜色**而不是深度：要么 0x02934000 在原机内存布局里是另一块颜色缓冲（前缓冲 / 上一帧），要么复制的语义另有所在。下一步：查游戏构造 0x00C0EAE0 时 Data 字段的来源（GetDepthStencilSurface / GetBackBuffer(-1) / 硬编码），以及原机 D3D 的帧缓冲与深度缓冲地址布局。

证据链：
- r088：相机矩阵 `0x977CE0` 在闪黑帧（2847）已是新房间的值，下一帧画面亮度与它完全相同 → 从这一帧起画的是转场快照的淡出。
- r089（`--probe 1caca0/1cace7/1cad47`，闪烁监视按帧记命中增量）：闪黑帧 8188 提交函数被调用 96 次，与前几帧旧房间相同，过视锥剔除 65 次；下一帧才变成新房间的 101 次。即游戏自身在相机切换那一帧仍遍历旧房间的物件表，配新相机大半被剔除——这是游戏逻辑，Xbox 上同样发生。
- 转场：`FUN_003221A0` 用 device+0x1A18 的表面建贴图头 0x00C0EAC8，用 +0x1A14 建 0x00C0EAE0；转场把 0x00C0EAC8 复制成快照，再以 CONSTANT_ALPHA 0xE5（≈90%）盖在画面上淡出。
- 程序库原版 Swap（0x3CBC60，D3DSWAP_COPY 路径）：SetRenderTarget(+0x1A18)、SetTexture(0, +0x1A14) 后绘制 → **+0x1A14 是游戏绘制的后缓冲，+0x1A18 是前缓冲（上一帧）**；三缓冲时 +0x1A18 与 +0x1A1C 互换 Data。SetViewport（0x3C7270）在渲染目标为 +0x1A14 时取 +0x1A18 的尺寸，也说明 +0x1A14 是颜色目标。
- HLE 原先把后缓冲放在 +0x1A18、深度缓冲放在 +0x1A14：快照取到的是当帧（半黑）而不是上一帧的完整旧房间，于是半黑画面被淡出几帧 = "闪一下"。原机上 90% 不透明的旧画面盖住了这一帧。

修法（`d3d/device.cpp`、`d3d/xd3d.h`）：+0x1A14 = 后缓冲，+0x1A18 = 独立的前缓冲（`g_frontbuffer`，720×480），每次 Swap 在呈现后把后缓冲复制进前缓冲（`copy_to_frontbuffer`，即 D3DSWAP_COPY）。r090：游戏中最大的单帧变暗从 +37%（r087/r088）降到 +4%（正常淡出）；用户确认开门不闪，刀光、光爆、读档页 / Game Over 正常。

连带：0x00C0EAE0 现在是后缓冲上的颜色贴图头（原来因 +0x1A14 放了深度缓冲而成为 LIN_D24S8）。§3.11 的 `cfg:zmode=3`（固定管线读深度格式贴图头时返回后缓冲颜色）正是对这一点的经验补偿；现在该头不再是深度格式，zmode 是否还有调用者待查。

附带发现：闪烁监视本身很重（每帧回读画面强制 CPU 等 GPU、每个 draw 回溯调用栈）。r089 现场开关对照：开 37–41 fps、关 56–59 fps；r077 起"进游戏前"最低帧率由 50 多降到 25 左右即由此而来。它只是诊断工具，正常游玩不开。

### 3.15 点精灵：火把击碎的火星与烟（2026-10-19，r167–r171）

### 3.17 四条"按案例凑出的规则"对照原版（2026-10-19，r183–r189，核显）

**(1) 深度偏移（ZBIAS）— 原规则错，已改。** 原版 `D3DDevice_SetRenderState_ZBias`（0x3C5920）：z → POLYGONOFFSETZSLOPESCALE = −z·0.25（常数 0x4149C0 = 0.25）、POLYGONOFFSETZOFFSET = −z（深度单位），POINT / WIREFRAME / SOLIDOFFSETENABLE = (z≠0)，ZBIAS 只是存值。HLE 原先只存 ZBIAS，绘制时按 d3d8to9 的每步 −0.000005 换算（≈ 84 个深度单位，且无斜率项）。现 `ngb/d3d_ngb.cpp` 的 `SetRenderState_ZBias` 照原版写齐五个状态；绘制时只看多边形偏移（单位 = 1/2^24），斜率按目标倍率放大（斜率是每像素深度变化，宿主像素小 k 倍）。游戏另在 `FUN_001D45C0`、`FUN_001D5420` 内联写这些状态（影子一遍：斜率 1、偏移 0），本来就从数组读。r183 帧 6600：50 次 `ZBIAS 3` 绘制换算为 −3 单位、斜率 −0.75，与原版公式一致；r189 每 30 帧截图，镜头静止段相邻两张变化 0.65–2.3%（角色待机动作），无闪烁（42% 的单帧是攻击命中）。

**(2) 深度格式贴图的固定管线取样（zmode）— 规则已失效。** zmode=3（读成后缓冲颜色）当初是实测选的；其原因已在 §3.13 找到：贴图头 0xC0EAE0 由 `FUN_00321e40` 从设备 +0x1A14 复制，而原机 +0x1A14 是后缓冲（颜色），HLE 当时错放了深度表面。0e54460 修正后，r170 / r171 / r183 三段追踪里固定管线读深度格式贴图 0 次；r183 里的 50 次全是影子接收面（可编程顶点 + 像素着色器，128×128 D24S8 影子图），不走 zmode。代码保留，触发时写日志。**另立待查**：影子接收面的"2D 取样回传深度值"与 xemu（`psh_append_shadowmap`：2D 与 0 比较、3D 与 r/q 比较，结果只有 0/1）不同，是另一条凑出的规则，与"影子偏淡"有关。

**(3) 火花线段加宽 — 与原版一致。** 原版 `SetRenderState_LineWidth`（0x3C56A0）：NV2A 线宽 = round(LW·[设备+0x964]·8 + 0.5)（1/8 像素，上限 0x1FF，方法 0x380）。[设备+0x964] 由 `D3D_CommonSetMultiSampleModeAndScale`（0x3C6714）写入：渲染目标为后缓冲时取设备的取样倍率，未开多重取样为 1.0；黑之章建设备用 0x11 = D3DMULTISAMPLE_NONE，故 Xbox 上线宽 = LW 像素（720×480）。我们画 LW × 宿主倍率，相同；点精灵不缩放时的大小同理（§3.15）。

**(4) `--tsc-divisor 4` — 不再需要，默认改回 1。** 换算成 733.33 MHz 有依据（Xbox CPU 时钟，引擎 `FUN_0030E140` ×0.113）。÷4 是当年 HLE 慢、引擎量到 78–99 贴着影子门槛 94 时的权宜。核显实测（`logvar:d21698`，第 1 章 4185 帧）：÷4 时中位 10.6 / 最大 52（r185）；÷1 时中位 42.2、p90 49.3、p99 62.2、最大 152，超过 94 的 0.17%（零星单帧），影子计数器 `[0x8CDA5C]` 几乎一直是 −5、影子始终绘制（r186），平均帧时间 9.20 ms 不变。94 约对应 18.8 ms 的游戏线程帧时间（掉到 60 fps 以下）；真跑慢时引擎按原版规则降细节，这正是原版行为。

**(5) 2026-10-30 更正 (4) 的结论：D3D 的时间不再算进引擎的负载（`game_load.cpp`，照 ngbrecomp #50 / #96）。** (4) 说「真跑慢时降细节是原版行为」，但引擎量的是从帧开始（`[0xD21680]`）到交出这一帧（`FUN_0030E140` → `[0xD21698]`）的时间：在 Xbox 上 D3D 调用只是往 GPU 队列里塞命令，这里每次调用都在游戏线程上同步翻译、绘制，于是弱电脑上明明还跑满 60 帧，引擎也以为超负荷，丢影子（>94）、丢 HUD（约 >95，上游 #96）。现在：游戏线程上「重」的 D3D 调用（绘制、`RunPushBuffer`、清屏、等待、交换、贴图绑定、着色器载入，按名字挑，约每帧几百次）用 `rdtsc` 计时，帧开始时间往后挪同样多（换算比例每帧在 Swap 校准一次，并且不超过「现在」）；交出时的数字封顶 80；GPU 回调（`0x30E060`）当场返回 0。`--original-load` 恢复引擎原来的测法。
- 第一版给每个 D3D 调用都计时，结束时还读一次系统时钟：每帧多 2.6 ms，游戏速度 90.8%（r650）。改用 `rdtsc` 估算「现在」后，仍给所有调用计时，中位数 8.74 / 8.96 ms（r652 / r653）；只给重调用计时后为 8.55 / 8.83 ms（r654 / r655），同一程序不计时的对照为 8.30 / 9.09 ms（r651 / r656），1.1.8-t 为 8.05–8.63 ms：测不出开销。

### 3.18 影子接收面：深度贴图一律按 3D 比较（2026-10-19，r191，照原版库）

用户要求影子照原版实现。§3.9(b) 的"2D 取样回传深度值"是凑出来的规则（照 xemu 的 2D 与 0 比较时影子消失，于是改成回传深度）。原版依据：
1. `D3DDevice_SetTexture`（0x3C7B00）：贴图格式字段为 0x2A..0x31（全部深度格式）时，在该层的标记字上加 0x40000000。

### 3.21 像素着色器绘制不再叠加宿主雾（2026-10-19，r214–r216）

规则（xemu psh.c）：NV2A 上雾只经合成器生效——像素着色器的 FOG 寄存器为（雾色.rgb，顶点雾系数），被合成器 / 最终合成器引用时才起作用，之后不再另行加雾。Direct3D 9 则在 ps_2_0 之后仍按 FOGENABLE 叠加固定雾。
证据：新增检测（像素着色器 + 开雾时记日志，`--trace-fog-ps` 追踪下一帧）。第 1 章 r214 帧 5963 即触发；r215 追踪：是**影子接收面**（ps 0x39189D0，128×128 D24S8，GEQUAL，REVERSE_SUBTRACT 混合，雾色 0xB47850，线性 2–250），其 4 个合成器阶段与最终合成器的输入字节都不含寄存器 3（FOG），即原机这次绘制没有雾。
改动：宿主雾只给固定管线绘制（`d3d/draw.cpp`，FOGENABLE 与是否有像素着色器一起决定，值变才发）。检测改为"像素着色器确实读 FOG 且开雾"（翻译器的 FOG.a 仍为 1，雾系数未传入），追踪场景里 0 次（r216）。近处影子几乎不变（主角约 7 m 处雾约 2%；r191 / r216 帧 7200 影子核心 19–22、地板 33–37），远处接收面不再被雾色污染。

### 3.22 光晕：夜景闪烁、重影、转视角像螺旋 / 轮胎转（2026-10-22，r414–r429）

用户报告：夜景里隼龙（银色盔甲）腿上有紫色重影、周围灯光的光晕闪烁且抖动；给出原版（xemu）同一地点截图：光晕柔和、外圈不明显。光晕链（FUN_00316AA0）：后缓冲 720×480 → 256×256 高亮提取（FUN_00315B20，合成器：限制到 0–1 的 2×(画面 + c0) − 1，c0 0xFF141433）→ 256×128 竖向、128×128 横向 4 点模糊（FUN_00314430，fvf 0x404，取样偏移 ±2 / ±6 texel，c0 × 内侧 + c1 × 外侧）→ 128×128 拉满全屏，MODULATE2X × 0xB3，加法混合（FUN_00315420）。四个原因，逐一用证据确认：

1. **源图细节过多**：高亮提取从 2880×1440 的放大画面点取样，细高光时有时无（r414 追踪帧 16978）。改为：缓冲被画进面积不到它一半的缓冲时，从它的 Xbox 尺寸 box 平均副本取样（`device.cpp` `reduced_rt`）。注意 256×256 不算"小缓冲"（高度大于 480 的一半），原规则漏掉了它（r417）。
2. **小缓冲被放大渲染**：4×3 倍下模糊的四份副本相隔 8–24 个宿主像素，成了竖条（r414 / r420 的 128×128 结果）。改为：被缩小画进的目标一律按 Xbox 原尺寸渲染（`g_xbox_size_keys`，首次遇到时 `request_render_rebuild`）。
3. **逐帧交替模糊核**：连续追踪 4 帧（r423 帧 9161–9164），模糊权重在 0.25/0.25 与 0.33/0.17 之间逐帧交替，其余常数不变——为 480i 电视设计，两帧在眼中合为一团；PC 上就是 30 Hz 的宽窄闪烁。改为每帧都用两组的平均 0.2922 / 0.2098（`pshader.cpp` `upload_ps_constants`）。曾试过"取最近两帧结果的平均"，静止不闪但转视角留下第二圈光晕（用户："像轮胎一样转"），已弃用。
4. **稀疏模糊的空隙**：最终 128×128 里四份副本相隔 1–3 texel，拉满全屏后仍是一条条（用户："外层一条一条，转视角像螺旋"）。原版靠电视糊掉。改为：原尺寸缓冲之间画出的模糊结果，被画到更大的目标（画面）时先做横竖 7 点高斯（σ 1.5 texel，`softened_rt`）。

用户确认（r427）："太漂亮了"。性能（集显第 1 章 bench）：新 96.6%（平均 9.19 ms）、上一个发布版 97.5%（9.32 ms），超时帧都是 0.2%；差的 0.9% 主要是光晕缓冲首次出现时的一次重建。附带影响：刀光拖尾 / 重击光爆用的 256×256 画面副本（0x02CD8000，FUN_00324D90）也按原尺寸渲染，和原版一致。

同类问题的侦测（每种情况只记一次日志）：`[census] … alternates its constants every frame`（同一合成器程序常数逐帧 A/B 交替 8 帧以上）、`[census] … N-tap filter reads …`（一次绘制多个阶段取样同一渲染目标）。第 1 章路线里只报出光晕本身（r428）；其他章节靠用户日常游玩时的日志收集。

### 3.23 画面到窗口：一道按窗口大小做的平均缩小（2026-11-05，玩家：10× 时主菜单显卡占用很高）

**原因**：每帧显示前的处理是按「渲染画面和窗口差不多大」设计的：接缝填补、伽马、FXAA 各在整张渲染画面上做一遍、各写一张
同样大的中间画面，最后双线性缩小到窗口。10× 时渲染画面是 8192×4800（3900 万像素），1920×1200 的窗口每帧要读约 18 亿个
texel，还多占三张 157 MB 的画面：集显标题画面 66 ms 里有 63 ms 是这几步（关掉 aa 和 seamfill 后 2.8 ms）。而且双线性缩小
每个窗口像素只取 2×2 个渲染像素，10× 时约四分之三画出来的像素没参与显示，FXAA 其实在弥补这一步留下的锯齿。

**做法**（`d3d/device.cpp` `present_backbuffer`、`kResolvePS`）：一道按窗口大小的 resolve，每个窗口像素取它覆盖的全部渲染
像素的平均（N×N 个双线性取样，每个是 2×2 的平均，N = 覆盖宽度的一半向上取整，最多 4）。每个取样先过游戏的伽马曲线和用户
的增益 / 伽马再平均：等于原机用更多像素画时各自发出的光取平均；先平均后过曲线时，曲线把画面提亮一倍并截断高光，6× 下高光
暗了最多 16 级。FXAA 移到 resolve 之后、按窗口大小做，且只在渲染画面不到窗口 2 倍时做（以上平均本身就是超采样）。接缝填补
只在不到 3 倍时做（以上一条缝缩小后最多占窗口像素的三分之一）。渲染画面不大于窗口时（1×、渲染跟随窗口）仍走原来的流程（在
较小的画面上做 FXAA 再放大，更省也更好）。执行期 `cfg:resolve:0` 切回原来的流程对照。

**画面**（同一次运行相邻帧，新旧流程对照，`cfg:resolve:0` 前后各截一张）：平均亮度在 3×、6×、10× 下都相差 0.5 级以内；
3× 下逐像素平均差 0.8（只是 FXAA 改在窗口尺寸上做）；6×、10× 边缘一样锐利或更平滑。

**性能**（集显 Iris Xe，1728×972 窗口，每帧中位数，旧 → 新）：

| | 3× | 6× | 10× |
|---|---|---|---|
| 第 1 章 bench | 5.97 → 5.43 ms | 46.1 → 23.4 ms | 110.8 → 61.1 ms |
| 标题画面 | 2.36 → 2.31 ms | 26.6 → 2.37 ms | 62.4 → 2.47 ms |

剩下的（10× 战斗 61 ms）是游戏本身在 8192×4800 上画的，随渲染倍数增长；「特效原尺寸」可以再省。没改：每帧把后台缓冲整张
复制给前缓冲（`copy_to_frontbuffer`，游戏的 D3DSWAP_COPY 要读上一帧），10× 标题画面整帧只有 2.5 ms，开销不大。

### 3.24 暂停菜单 10× 显卡占用：QuadSnap 的四次读取（2026-11-05，玩家：武器菜单 GPU 七十多，打斗四五十）

**实测**（RTX 3060 笔记本，10×，Windows「GPU 引擎 3D」占用）：打斗约 34%，暂停菜单（武器页）约 77–82%，但稳定 60 帧。一帧 133
次绘制全部来自游戏自己的菜单代码（0x308Dxx），叠起来约 10.6 个整屏的半透明 2D 层，这一半是原版的画法，按像素放大。另一半
是 QuadSnap：`cfg:quadsnap:0` 或只关加权（新开关 `cfg:quadweight:0`）都降到约 40%。

**原因**：QuadSnap 的线性过滤变体（`ffp_ps.cpp`，按 alpha 加权的四纹素）用 `tex2Dgrad` 读四次（显式梯度，避免纹素角跳变选错
mip）。显式梯度的读取在 NVIDIA 上贵得多。试过的其他做法：读一次、alpha 为 0 或 1 时跳过四次（动态分支，ps_2_x 不支持，编译失败
时 QuadSnap 等于失效，占用的「下降」是假的）；`tex2Dlod`（同样只有 ps_3_0）；按整张贴图判断 alpha 是否单一（这几张大图层多是柔和
渐变，省不下）。

**做法**：四次读取改用普通 `tex2D`。变体只在 1× 以上用，2D 都是放大的：相邻像素的纹素角最多差一个纹素，细节层级一样停在最
上层，结果相同。`cfg:quadgrad:1` 切回显式梯度对照（放进阶段着色器的缓存键）。

**核对**（同一次运行：新、新连拍量动画本底，再切 `quadgrad:1`、`quadweight:0`）：3× 原读取与新读取之差 0.92，本底 0.83；10× 差
1.35、本底 0.17，但热图上差异全在动的地方（闪烁的选中条、标签发光、流动的背景纹样和文字），静止的匕首、边框、标签、字边没有差
异；对照 `quadweight:0` 平均差 2.5–3.0、1.2–1.4% 的像素差超过 32 级。编译失败 0 次。

**性能**：暂停菜单 10× 77% → 50%（不加权 40%）；集显第 1 章 3×，新 / 2.2.4 交替四轮：6.11 / 6.89、5.74 / 5.74 ms，99% 分位 9.92 / 9.99 ms。

**着色器缓存的清理**（`shader_cache.cpp`）：缓存项按 HLSL 全文区分，生成器一改（如上），旧项永远用不到，却每次启动都被读入、
做成着色器对象一直占着；10-22 以来积到 400–457 项。现在 `cache\shaders\use.txt` 记运行次数和每项最后一次被用到的运行：30 次
运行没用到的删除，超过 3 次没用到的留在盘上但启动时不做对象，读不了的（别的格式）删除；索引每次启动压缩重写。运行中渲染线程只
在内存里记下每项第一次被用到，后台线程每 10 秒追加一次（不在渲染线程开文件：开一个约 0.9 ms，这正是启动时把缓存读进内存的原
因；第一版在渲染线程追加，集显第 1 章有一轮 6.34 ms）。第一次有索引时已有的项都算刚用过。测试（拷贝的 400 项，伪造的运行次数）：删 100、留而不做 91、照做其余，索引
305 行；索引里有乱行时照常运行。

### 3.25 着色器缓存改为全部预热（2026-11-06，用户要求以流畅为优先）

**问题**：3.24 的策略把超过 3 次运行没用到的缓存项做成“cold”：启动时不建立 shader 对象，第一次进该场景才在渲染线程
`Create*Shader`；超过 30 次运行没用到的直接删 `.bin`，第一次进该场景在渲染线程 `D3DCompile`。短会话还会丢掉最后 10 秒的
use.txt 记录，令常用项被误判为久未使用。两者都可能造成一次明显卡顿。

**改法**（`d3d/shader_cache.cpp`）：不再按运行次数做 cold / 删除。启动时把当前**产生器 epoch** 的可读、有 bytecode 的缓存
项建立成 shader 对象，放进 `g_warm`；每个 `.bin` 旁的 `.gen` 记录 epoch。旧 epoch 的项留在磁盘上但不预热，只有读不了的
（别的格式 / 截断）`.bin` 才删除。`use.txt` 与后台写入线程整套移除。

**迁移**：没有 `.gen` 的旧缓存（2.2.6 以前）第一次启动时标为当前 epoch 并预热，所以升级不会把所有旧项变成运行时工作；
之后只有产生器真的改了、`kShaderEpoch` 被手动加一，旧 epoch 才会被跳过。被跳过的项不删除；同一项第一次在游戏里用到时
重新编译并写成当前 epoch，下一轮启动即预热。首次遇到的新 shader 仍要编译一次，这是缓存尚未包含它。

**证据**（`run/epoch_226_first/black.log`，208 项旧缓存）：`read 208 entries, made 19 vertex and 175 pixel shaders ... in
334 ms; 0 old-generator kept, 208 legacy marked, 0 unreadable deleted`；第二次 `run/epoch_226_second`：99 ms，`0 legacy marked`。
把其中一项 `.gen` 改成 2（旧 epoch）后（`run/epoch_226_old2`）：`read 207 entries, made 19 + 174 ... 1 old-generator kept`，
且对应 `.bin` 仍在磁盘上，证明旧项被保留而非删除。没有按 idle 删除或跳过。

**代价**：2.2.6 迁移旧缓存时启动多约 0.2–0.3 秒（写 208 个 `.gen`）；之后启动约 0.1 秒。常见缓存只有几百项、几 MB。
首次出现的新 shader 仍要在运行时编译一次，这是缓存尚未包含它，不是本策略造成的旧项失效。

### 3.26 缓存命中不再读写 `.gen`（2.2.10，2026-11-09）

**问题**：2.2.6 起 `cached_compile` 每次查找都调用 `mark_epoch`：先 `_wfopen` 读 `.gen`，epoch 不同再写。预热过的项在内存
（`g_mem`）里命中，本不该碰文件，这一步把 2026-10-22 已量到的“打开一个文件约 0.9 ms、在渲染线程”的代价带了回来。

**证据**（集显 Iris Xe，第 1 章 3×，`build/release`，临时计时探针，未提交）：渲染线程（与 `[d3d]` 同一线程号）上 50 次查找
里 `mark_epoch` 共 18.0 ms、单次最多 1.3 ms；再跑一次共 35.3 ms，其中一次 18.0 ms。卡顿帧里“从缓存取 shader”的时间：
修前 17.0 / 15.0 ms（47 / 42 个），修后 0.0 / 0.0 ms（47 / 49 个），游戏速度不变（98.4%）。

**改法**：删去 `mark_epoch`。预热命中不碰任何文件；只有不在内存、从文件读到的旧项（没有 `.gen`）才补写一次 `.gen`；
新编译的项照旧由 `write_entry` 写 `.gen`。

### 3.27 21:9 / 16:10 下 HUD 贴到屏幕两侧（2026-11-09，玩家反馈）

**问题**：游戏只有一套 16:9 的 2D 布局。21:9 时 `squeeze_169` 把所有 2D（含游戏中的 HUD）都收进中间 16:9，血条、提示离屏幕边缘很远。

**改法**（`d3d/draw.cpp` `WideHud`，思路参考 ngbrecomp 的 HudPlace/HudGroup，按 GPL-2 项目自行重写）：
- 菜单、标题、章节卡、影片照旧整体居中（菜单调用者、影片 blit 走 `centre_only`）。
- 游戏中（本帧已向后缓冲画了 ≥30 个 3D draw）每个 HUD 元素保持 16:9 形状、贴到自己那一侧：元素 = 彼此相距几像素内的 2D 块（量表 + 端帽 + 下方文字，一行字），每帧结束（Swap）分组，下一帧按元素的侧边（左 / 中 / 右；16:10 时上 / 中 / 下）挤压；新出现的块先按自身位置（顶部的按侧边，其余居中）。
- 高窄量表（水下氧气条）单独成组；章节结算的大面板（宽 >35%、高 >45%、跨中线，连续 4 帧）内的东西随面板居中；不透明全屏底色之后（道具画面）全部居中；覆盖大部分屏幕的贴图在游戏中按原样铺满（屏幕特效）。
- `black.ini hud_centre = 1`（或 press-file `cfg:hudcentre:1`）恢复以前的整体居中。

**证据**：第 1 章 21:9（`run/hud_base` 对 `run/hud_new`，1680×720）：日志 `[hud] ... [518-662,389-465 RB] [50-224,29-96 LT]`，血条到左上角、"调查"提示到右下角，形状不变；进游戏前的标题、菜单、读档帧逐像素相同（只有菜单动画相位不同的两帧）。16:10（`run/hud1610`）同样两组，血条在上、提示在右下。暂停菜单在 21:9 下仍居中。**未测**：Boss 血条、水下量表、章节结算面板（需要相应存档）。

### 3.28 MSAA 2× / 4× / 8×（2026-11-09）

**做法**（`d3d/device.cpp` `ms_*`）：帧大小的目标（后缓冲及其成对缓冲，渲染倍数下）画进一个多重采样表面 + 多重采样深度，只有在有新绘制且有人要读纹理时才 `StretchRect` 解析（游戏取样、屏幕复制、画面输出、前缓冲复制、CPU 读、重建）；纹理被绘制以外的方式写过（前缓冲复制、CPU 像素）时，下次绘制前用全屏复制写回多重采样表面。阴影图等小目标不变。

**为什么能做**：D3D9 不能取样多重采样深度。探针（`[zprobe]`，第 1 章）显示游戏作为贴图读取的深度只有 128×128 阴影图，主深度缓冲不被读取（§3.9 之后"深度→256×256 发光源"的复制不走主深度）。唯一读主深度的是接缝填补，开 MSAA 时关闭。

**采样数**：两块显卡在 D3D9 下都只提供 2×、4×、8×（日志 `host: MSAA sample counts`），没有 10×；启动器下拉为 关 / FXAA / MSAA 2× / 4× / 8×，显卡缺某档时自动降到下一档。

**性能**（集显 Iris Xe，第 1 章，帧时间中位数）：3× 渲染：关 6.1、2× 5.7、4× 10.7、8× 23.8 ms（游戏变慢）；1× 渲染 8× 与关闭相同（4.65 ms）。4× 一开始是 23.5 ms：每帧 8 次全帧解析；改为"有新绘制才解析"后 17.6 ms（4 次），再改为"有人读才解析"后 10.7 ms（游戏每帧只读 2 次）。默认关闭，不开不增加任何开销（关闭时 6.1 ms，与 2.2.11 同）。

**证据**：1×、关 FXAA、1:1 窗口对比（`run/msn0` 对 `run/msn8`）：楼梯扶手、横梁边缘的锯齿消失。暂停菜单、2004 标题（21:9 + 4×，3780×1440 多重采样目标）、设备重建与 Reset（press-file `recreate` / `reset`，`run/msrec`）后画面正常，无异常。

**2D 不做多重采样**：屏幕空间（XYZRHW）的绘制——HUD、菜单、文字、屏幕复制——在多重采样目标上关闭 `D3DRS_MULTISAMPLEANTIALIAS`，按无 MSAA 的规则覆盖整像素。暂停菜单的 1 像素分隔线（线图元）在 MSAA 下会把半个像素渗到相邻一行（4:3、1×、8×：该行从 (74,11,9) 变成 (114,77,75)），关掉后为 (68,11,9)，与无 MSAA 的整屏差异里不再有直线（`run/p43b` 对 `run/p43d`）；3D 边缘照样平滑（`run/msn8b`）。

**与 ngbrecomp（0.9.58，Vulkan）的对照**：思路相同——只给屏幕大小的目标多重采样、复制写入的纹理在下次绘制前写回多重采样图（他们的 `ms_stale` / `FillMs`，我们的 `tex_ahead` / `ms_upload`）、显卡不支持的档位降一档。不同点：
- 解析时机：他们用 Vulkan 的 resolve attachment 在每个 pass 结束时解析（驱动内建，无额外 pass）；D3D9 只能用 StretchRect 做一次独立的全帧解析，所以我们改为"有人读才解析"（每帧 4 次降到 2 次，见上）。
- 深度：Vulkan 可以把深度按 sample 0 解析，深度仍可读；D3D9 不能，所以我们开 MSAA 时关接缝填补。
- 2D：他们 2D 也走多重采样，用 QuadSnap 把四边形贴到像素边界来避免细线；我们直接让 2D 不做多重采样，四边形和线图元都与无 MSAA 完全一致。
- 他们可在游戏里即时切换 MSAA（每个采样数一套管线，后台预热）；我们从启动器选、下次启动生效，D3D9 着色器与采样数无关，没有切换时的编译。

### 3.29 启动器"CPU 核心分配"（实验性，2026-11-09）

开始游戏页新增：单核（默认，与 Xbox 一致：游戏线程绑在一个核心上）/ 自动分配（`black.ini multicore = 1`，即 `--multicore`：不绑定，由 Windows 调度；IRQL ≥ DISPATCH 的全局锁仍保证单 CPU 互斥）。立即写入 black.ini，下次启动生效，日志 `cpu: game threads not pinned`。第 1 章集显：单核 6.1 ms / 自动 6.0 ms，游戏速度都是 98.4%，这一段没有差别。

### 3.30 A 卡上水花 / 水滴是小方块：点精灵改用顶点自带的贴图坐标（2.2.17，2026-11-10，玩家反馈）

玩家（AMD Radeon RX 9070 XT，4×，4K）：水滴和水花显示成小方块；同一玩家说火星子正常。日志里没有点精灵信息，靠协作测试定位：
用户在测试窗口里进水跑跳，临时的"每种绘制组合首次出现记一行"统计显示，进水后新出现的点精灵只有一种——
`FUN_00326e70` ← `FUN_00124f70` 的 POINTLIST（FVF 0x42 = XYZ|DIFFUSE，无贴图坐标），第 0 层是 128×128 渲染目标，
第 3 层是 32×32 DXT5 圆点，POINTSCALEENABLE（size 0.2、A/B/C = 0/0/3）、透明度测试、SRCALPHA/ONE 混合。
与 §3.15 的火把火星是同一条路径；火星最小 3 像素，方块与圆点看不出区别，所以"火星正常"不能排除坐标问题。

原因（推断，玩家实测证实修复有效）：§3.15 第 3 条给这类绘制设 `D3DTSS_TCI_CAMERASPACEPOSITION` 生成一组坐标，
着色器在 `TEXCOORD3` 读圆点；NVIDIA / Intel 会把它替换成点精灵坐标，AMD 驱动没有替换，整个点取同一个纹素。

修复（`d3d/draw.cpp`、`d3d/ffp_ps.cpp`）：
- 改成点精灵最标准的用法：固定管线顶点没有贴图坐标时，`with_sprite_tc` 把顶点复制一份，在 FVF 字段之后补一组
  float2（`D3DFVF_TEX1`），各层 `TEXCOORDINDEX` 直通第 0 组；阶段着色器的第 3 层改从 `TEXCOORD0` 读（缓存键多一位）。
- 只对**点**生效：`begin_draw` 现在收到图元类型，开着 POINTSPRITEENABLE 画别的图元仍按 2.2.16 的方式（生成坐标）。
- 走顶点程序 / 声明的点精灵（第一章与水边都没出现过）：阶段着色器同样从 `TEXCOORD0` 读；首次出现记一行
  `point sprites through a vertex program or declaration`，以便知道是否存在、A 卡上是否还要处理
  （游戏自带像素着色器的那种仍读 `TEXCOORD3`）。补坐标的路径首次生效也记一行 `point sprites without texture coordinates`。

验证：RTX 3060 上水花 / 水滴与改前一致（用户目测两次）；AMD 玩家用收紧前的测试版确认修好；
集显第一章两轮中位数 5.20 / 5.36 ms（2.2.16：5.46 / 5.33 ms），跑分路线没有点精灵，额外开销只在粒子绘制（每次几十个顶点的复制）。

### 3.31 游戏进程禁用输入法（2.2.17，2026-11-10）

2026-11-10 下午这台机器上所有程序的窗口都无法激活：游戏卡在白窗口"未响应"，已发布的 2.2.15 也一样。
用 ctypes 小窗口逐个计时：`CreateWindowExW` 6 ms、不激活的 `ShowWindow` 2 ms，激活（`SW_SHOWNORMAL` / `SetForegroundWindow`）
永不返回；先调 `ImmDisableIME(-1)` 后激活 0.1 ms。窗口获得焦点时要与输入法服务通信，输入法服务（系统里二十多个搜狗进程）卡住就一起卡。
`d3d/host.cpp` `open_window` 在建窗口线程之前对整个进程 `ImmDisableIME(-1)`（动态取 imm32）：游戏里没有文字输入，
启动器是另一个程序不受影响；顺带玩家按到切换输入法的键也不会弹候选框。自动测试遇到这种卡住可加 `--background`（不激活、静音）。

### 3.32 第二章水塘远处的条纹：NaN 的 LOD 偏移按原机给 -16（2.2.18，2026-11-10，玩家反馈）

玩家：第二章水塘远处的水面有一条条亮斑；1× 和 3× 渲染、不开各向异性过滤时出现，6× + 16× 各向异性时正常（截图：`错误的水面.webp` / `正确的水面.webp`）。
ngb-recomp 修过同一问题（ngbrecomp #16，提交 040bfb3 → 6780b06 / 2bde5f2）：先也按"NaN 转整数得 0"处理，
后用 xemu 的寄存器模型（原版 D3D 代码自己写进 GPU 的值）读到水塘这次绘制的 TEXFILTER0 = `E2063000`，LOD 偏移字段（低 13 位，有符号 5.8 定点）是 `0x1000` = -16。
游戏只填了波纹贴图的最高一级，其余级别是残留数据；偏移 -16 让硬件永远读最高级。我们按 0 处理，渲染倍数低时远处选到粗的级别，读到残留数据，成了条纹。

- 范围：capstone 扫描 `.text` 对第 0 层 LOD 偏移影子 `0x3D5D28` 的写入只有两处：`FUN_00129b60`+0x96D（0x12A4CD，水面设置：刚设完顶点常量 c117/c118，写 NaN）和通用贴图层状态函数 `FUN_0030ba30`（正常数值）。
- 修复（`d3d/draw.cpp` 贴图层状态转发）：NaN → -16；其他非有限值仍 → 0，有限值仍钳在 [-16, 15.99]。水面像素着色器用普通 `tex2D` 读波纹贴图，采样器偏移直接生效。
- 验证：第二章水塘，1×、各向异性 1，RTX 3060：远处水面平滑，无条纹（截图 `run\pond1\shots\pond_fixed.png`，用户目测确认）。§3.16(2) 的旧结论已标错，docs/07 E3 同步改。

### 3.33 柔和阴影改在实际阴影图的格子上滤波（2.2.18，2026-11-10，玩家反馈）

玩家：开"超高"阴影时柔和阴影仍有锯齿，看起来像低分辨率；Series X 与 ngb-recomp（10× 阴影）的边缘平滑。
原因：`shadow_pcf` 默认 2，2×2 比较滤波的四个点落在**原机 128×128 阴影图**的格子上（`nv2a_psh.cpp`，`g = 1 / rectScale.xy`），
为的是柔化宽度与原机相同；代价是阴影分辨率再高，边缘也只有 128 的精度，成了插值过的台阶。
ngb-recomp 的做法是在实际绘制的阴影图上用比较采样器做 2×2（`SampleCmpLevelZero`，即我们的模式 1）。

- 修复：默认改为 1（`common.h`；`black.ini shadowsoft = 1` 也映射到 1）。阴影分辨率为原始（1 倍）时两种模式完全相同；更高时边缘随分辨率变细变平滑。模式 2 仍可用 `cfg:shadowpcf:2` 调出对比。启动器说明补一句"在所选阴影分辨率上柔化"。
- 对比（3× 渲染、阴影 4 倍，RTX 3060，同一处地毯上的隼龙影子，`cfg:shadowpcf:2/1/0` 各截一张）：模式 2 轮廓成台阶，模式 1 平滑细致，模式 0 清晰但硬。
- 性能：两种模式都是 4 次读取；集显第一章中位数 5.23 ms（2.2.17：5.07 ms，噪声范围内）。

- 退出时宿主线程 `blackrt.dll+0x5352d` 连续 ACCESS_VIOLATION（r006/r011/r016 timeout 退出路径）：llvm-symbolizer 指向 `log_stack_trace_ex`——是栈回溯用 `safe_read` 探测挂起线程的栈时的**预期缺页**，`__except` 会吞掉，但向量处理器先一步把它当崩溃打印（每次最多 20 条）。已改：`safe_read` 期间向量处理器直接放行（r017 起验证）。

- (c) 里"深度格式取样四通道都返回深度"是按 NV2A 行为与发光链既有效果推断，没有逐位对照；xemu 的 `psh.c` 对 depth 格式的处理可作核对。

- §3.9(b)(d)：深度格式贴图在非阴影模式下的真实回传值（深度值 / 字节拆分 / 比较结果）决定刀光与光爆的最终外观；请用户在 xemu 对照龙剑刀光的颜色与透明度，再定。
