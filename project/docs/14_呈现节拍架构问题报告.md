# 《忍者龙剑传 黑之章》PC 移植：呈现节拍与游戏速度问题报告

**日期：** 2026-11-18  
**项目：** 路线 B，原生加载器 + HLE  
**当前版本：** 2.2.37.1（另有未提交的高帧率保护测试）  
**报告性质：** 技术评估与改进建议，供决策参考

---

## 1. 摘要

当前移植在 **VRR（G-SYNC / FreeSync）120 Hz** 环境下出现游戏速度错误：帧率从 60 变成 80，游戏逻辑跑到 **4/3 速**。窗口和无边框模式均可复现。

直接原因不是渲染变快，而是：

> **游戏逻辑的 vblank 节拍被绑定到了显示器的合成节拍。**

Xbox 原版游戏把 vblank 当作游戏时钟。移植层用 `DwmFlush` 模拟 vblank。2.2.35 为改善 120/180/240 Hz 的均匀度，改成“每 n 次屏幕刷新走一帧”。在固定刷新下这等于 60 Hz；但在 VRR 下，合成节拍可能变成 80 Hz，游戏于是跑到 80 Hz。

现有 2.2.37.1 只防“节拍变慢”，没有防“节拍变快”；临时补丁 2.2.37.2-t 增加了“高于 110% 连续 2 秒回退 timer”，但仍有两个问题：

- 前约 2 秒游戏仍然是 4/3 速；
- 这是止血，不是架构修复。

**建议：**

1. **立即**提供“固定 60 Hz 节拍”的安全模式，保证游戏速度正确；
2. **中期**把“游戏逻辑 tick”和“画面呈现节拍”彻底拆开；
3. 不以“猜 VRR”作为长期方案。

---

## 2. 背景

### 2.1 项目架构

本项目采用路线 B：

```text
32 位 Windows 原生加载器
+ 原版 Xbox x86 游戏代码直接执行
+ Xbox kernel / D3D8 / DirectSound / XAPI 由 HLE 取代
```

游戏逻辑本身是原版代码，不改写；移植层负责模拟 Xbox 的 vblank、图形、音频、输入和内核。

### 2.2 为什么 vblank 重要

原版 Xbox 游戏通常每 60 次 vblank 更新一次逻辑。vblank 不只是“画面刷新”，还是：

- 游戏主循环节拍；
- 动画、计时、AI、输入采样；
- 30 fps 过场影片的节奏。

因此 **vblank 频率就是游戏速度**。

---

## 3. 现象与影响

### 3.1 现象

| 环境 | 结果 |
|---|---|
| 2.2.34，120 Hz | 稳定 60 |
| 2.2.35，120 Hz 固定刷新 | 约 60，画面更均匀 |
| 2.2.35，120 Hz + VRR | **80 帧，游戏 4/3 速** |
| 2.2.37.1，120 Hz + VRR | 已修“变慢”，但未修“变快” |
| 2.2.37.2-t，120 Hz + VRR | 约 2 秒后回 60，仍非根治 |

窗口、无边框均出现；不是单一全屏模式问题。

### 3.2 影响

这不是“画面更流畅”，而是：

- 敌人、动画、计时、输入全部变快；
- 过场和游戏节奏错误；
- 玩家会认为“游戏坏了”；
- 对高刷/VRR 用户是明确的体验回归。

---

## 4. 根因分析

### 4.1 2.2.35 的假设

2.2.35 在 120/180/240 Hz 下采用：

```text
每 n 次屏幕刷新 → 触发一次游戏 vblank
```

固定刷新时：

```text
120 Hz ÷ 2 = 60 Hz
```

这个假设在固定刷新成立，在 VRR 下不成立。

### 4.2 VRR 下发生什么

VRR 的刷新率不是固定的 120 Hz，而是跟着呈现内容变化。实际合成节拍可能变成 80 Hz：

```text
120 Hz VRR
→ 实际合成 80 Hz
→ 每 2 次合成走一帧
→ 游戏 vblank 80 Hz
→ 游戏 4/3 速
```

### 4.3 为什么现有检查没拦住

2.2.37.1 的检查是：

```text
连续 2 秒低于 59.94 的 90% → 回退 timer
```

它只处理“变慢”，没有处理“变快”。80 Hz 高于阈值，所以被放过。

### 4.4 当前临时补丁

2.2.37.2-t 增加：

```text
连续 2 秒高于 59.94 的 110% → 回退 timer
```

能止血，但：

- 前 2 秒仍错误；
- 如果显示来源变化，可能重新尝试跟屏；
- 没有从架构上解除耦合。

---

## 5. 架构问题

### 5.1 当前结构

```text
显示器 / DWM 合成
        ↓
DwmFlush / D3DKMT vblank
        ↓
Xbox vblank
        ↓
游戏逻辑 + 画面呈现
```

问题：

> **同一个节拍同时驱动“游戏跑多快”和“画面什么时候显示”。**

显示器是输出设备，不是可靠时钟。VRR、桌面合成、窗口状态、驱动负载都会改变它。

### 5.2 目标结构

```text
固定 59.94 Hz timer
        ↓
Xbox vblank / 游戏逻辑
        ↓
独立渲染
        ↓
呈现：vsync / VRR / 窗口合成
```

原则：

- **游戏速度只由固定 timer 决定；**
- **VRR 只决定画面何时送出，不决定游戏逻辑；**
- 高刷均匀度在呈现层处理，不回写游戏节拍。

### 5.3 与主流游戏的一致性

主流游戏通常：

- 固定 timestep 更新逻辑；
- 渲染和呈现分离；
- VRR 交给驱动/呈现层；
- 不把 `DwmFlush` 当作游戏时钟。

本项目目前是反过来的，这是问题根源。

---

## 6. 为什么不能“直接读 VRR”

Windows 没有稳定、跨厂商的公开 VRR 查询：

- `EnumDisplaySettings` 只给名义刷新率（如 120）；
- `DXGI_OUTPUT_DESC1` 没有 VRR 开关；
- 即使读到 VRR 开启，也不知道 DWM 当次合成间隔；
- 厂商 API（NVAPI / ADL）不跨显卡。

所以只能观察 `DwmFlush` 的实际间隔，需要时间采样；这就是“判定时间”的来源。

**但正确的架构不需要猜 VRR：游戏节拍根本不应该跟显示节拍。**

---

## 7. 方案比较

| 方案 | 做法 | 优点 | 缺点 | 风险 |
|---|---|---|---|---|
| A. 安全模式 | 固定 59.94 timer | 立即保证 60，简单 | 失去 120/180/240 均匀度 | 低 |
| B. 目标架构 | 游戏 tick 与呈现分离 | 速度正确，保留高刷/VRR | 改动大，需实机验证 | 中 |
| C. 继续加判定 | 高低帧率 fallback | 改动小 | 仍有延迟/误判，治标 | 中 |
| D. 完全回退 2.2.34 | 去掉 2.2.35 pacing | 稳定 | 失去高刷改进 | 低 |

### 推荐

- **立即：A**（安全模式/启动器选项）；
- **中期：B**（目标架构）；
- **C 只作为过渡保护**；
- **D 不作为长期方案**。

---

## 8. 建议实施路线

### 第一阶段：安全模式（短期）

- 启动器增加“VRR / 高刷：固定 60 Hz 节拍”选项；
- 或对 VRR/高刷默认使用 timer；
- 行为等同 `--timer-vblank`；
- 验收：VRR 120 下稳定 60，不再 80。

### 第二阶段：拆分游戏 tick 与呈现（中期）

- vblank 线程固定 59.94 Hz 驱动游戏逻辑；
- Present 独立跟显示/VRR；
- 处理 30 fps 影片、音频同步、输入延迟；
- 验收：60/120/240/VRR 下游戏速度均为 60。

### 第三阶段：高刷均匀度（后续）

- 在呈现层做 frame pacing；
- 不让 pacing 反写游戏节拍；
- 保留 120/180/240 的均匀度。

---

## 9. 风险与未验证项

1. 当前没有 120 Hz + VRR 实机，80 Hz 结论来自玩家报告与代码路径，需日志确认；
2. 现有玩家日志是 2.2.35 独占全屏 60 Hz，不包含 VRR 场景；
3. 拆分 tick/呈现会影响 D3D9Ex Present、影片、音频、输入；
4. 固定 timer 在高刷下可能有重复帧/跳帧；
5. 需要 Windows + Linux/Proton 两套回归。

---

## 10. 验收标准

- VRR 120 / 240、固定 120 / 240、60 Hz 下游戏速度均为 60；
- 不再出现 80 帧 / 4/3 速；
- 30 fps 影片节奏正确；
- 音频、输入、过场无回归；
- 帧时间不显著变差；
- 日志能明确写出当前节拍来源。

---

## 11. 结论

2.2.35 的出发点是改善高刷均匀度，但把“显示节拍”当成了“游戏时钟”，在 VRR 下导致游戏速度错误。

**短期**应先用固定 60 Hz 节拍保证正确性；  
**长期**应把游戏逻辑 tick 和画面呈现解耦，让 VRR 只影响呈现，不影响游戏速度。

这是架构问题，不是单个参数问题。
